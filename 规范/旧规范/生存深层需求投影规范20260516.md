# 生存深层需求投影规范 20260516

> 2026-05-18 修订说明：本文中的“证据置信度 / 因果路径置信度”均为因果解释层派生值，由因果基础计数、证据类型和查询参数计算；不得理解为 `因果主信息类` 的持久字段。

## 0. 上级约束

本规范受以下规范约束：

```text

规范/因果补完流程规范20260516.md
规范/因果信息用途与用法规范20260516.md

```

本文定义从物理不安全事件的深层因果原因投影出生存深层需求的口径。因果类只生成需求候选和证据链；正式需求入树仍由自我线程通过需求域方法裁决。

## 1. 定义

```text
生存深层需求 =
    为了降低未来物理不安全事件概率，
    而从深层因果原因中投影出来的需求。
```

它不是因为“高级需求”这个名字而高级，而是因为它离物理安全事件更远、更长期、更间接。

核心链条：

```text
P：物理不安全事件
↑
A：直接导致 P 的原因
↑
B：导致 A 的原因
↑
C：导致 B 的原因
↑
D：导致 C 的原因
...
```

示例：

```text
P：自我宕机 / 硬件损坏
↑
A：硬件过热
↑
B：散热不足
↑
C：风扇积尘
↑
D：长期无人维护
↑
E：缺少维护关系
↑
F：维护请求不被信任
↑
G：自我缺少可解释能力
```

其中：

```text
P 是物理不安全事件；
A 是近端直接原因；
B / C 是中层原因；
D / E / F / G 是长期结构性深层原因。
```

从这些深层原因投影出来的需求，就是生存深层需求。

## 2. 深层原因

```text
深层原因 =
    距离物理不安全事件超过一层的上游因果节点。
```

形式：

```text
A -> P
    A 是直接原因。

B -> A -> P
    B 是二层原因。

C -> B -> A -> P
    C 是三层原因。
```

其中 `B、C、D...` 都属于深层原因。更细可分为：

```text
B：近层深因。
C：中层深因。
D 以后：长期结构性深因。
```

深层原因不是当前直接伤害自我的东西，而是会让直接伤害更容易发生的上游条件。

## 3. 深层原因到需求

如果某个深层原因 `X` 会通过因果链增加物理不安全事件 `P` 的概率，系统可以生成以下需求候选：

```text
降低 X 的发生概率；
降低 X 的影响强度；
提高对 X 的观测能力；
提高对 X 的控制能力；
建立绕开 X 的备用路径。
```

示例：

```text
深层原因：长期无人维护
生存深层需求：建立周期维护机制

深层原因：缺少维护关系
生存深层需求：建立维护者联系渠道

深层原因：维护请求不被信任
生存深层需求：提升维护请求可信度

深层原因：自我缺少可解释能力
生存深层需求：提升自我解释能力
```

这些需求看起来可能像协作、信誉、自我治理或能力提升，但在本系统里应解释为：

```text
为了长期降低物理安全风险。
```

## 4. 不直接等同真实安全值

生存深层需求通常不会立刻改变真实物理安全值。

```text
修复正在过热的硬件：
    可以直接改变物理安全。

建立维护关系：
提升解释能力：
优化任务管理：
建立备份机制：
    通常改变的是未来风险概率、应急能力、恢复能力或可维护性。
```

因此必须区分两类账：

```text
真实物理安全值：
    只有物理安全状态真实变化才更新。

潜在生存贡献：
    深层原因风险下降时更新。
```

禁止：

```text
完成解释能力任务 -> 物理安全 +1
```

正确表达：

```text
完成解释能力任务
-> 维护请求可信度提高
-> 维护支持概率提高
-> 长期无人维护风险下降
-> 未来物理安全风险下降
-> 潜在生存贡献提高
```

只有最终真的减少故障、宕机、损坏等物理风险时，才进入真实物理安全结算。

## 5. 生成流程

```text
1. 发现物理不安全事件 P，或发现 P 的风险上升。
2. 沿因果链向上追溯原因。
3. 标记每个原因到 P 的因果距离。
4. 判断该原因是否可观测、可验证、可控制。
5. 对可干预节点生成需求候选。
6. 对不可确定节点先生成确认需求。
7. 对不可控制节点生成隔离、备份、预警需求。
8. 按低层门控决定哪些需求允许进入需求树。
```

短口径：

```text
先止损，再查因，再控因，再治本。
```

## 6. 深层需求类型

### 6.1 确认型需求

当深层原因只是怀疑、证据不足时：

```text
未知原因 -> 确认需求
```

示例：

```text
可能是风扇积尘 -> 确认风扇状态
可能是电源波动 -> 确认电源稳定性
可能是维护缺失 -> 确认维护记录
```

### 6.2 控制型需求

当深层原因已确认且可控制时：

```text
可控原因 -> 控制需求
```

示例：

```text
风扇积尘 -> 清理风扇
散热不足 -> 改善散热
配置错误 -> 修正配置
任务风暴 -> 抑制任务风暴
```

### 6.3 预防型需求

当深层原因长期反复出现时：

```text
重复原因 -> 预防需求
```

示例：

```text
长期无人维护 -> 建立周期维护机制
长期缺少自检 -> 建立低频自检
反复高负载 -> 建立负载上限
反复误调度 -> 建立任务风暴检测
```

### 6.4 备份型需求

当深层原因不可控或短期内无法消除时：

```text
不可控原因 -> 备份 / 隔离需求
```

示例：

```text
外部供电不稳定 -> 建立备用电源
环境不可预测 -> 建立备用运行环境
维护者不可达 -> 建立备用维护通道
硬件老化 -> 建立灾难恢复方案
```

### 6.5 能力型需求

当深层原因是自我自身能力不足时：

```text
能力不足 -> 能力提升需求
```

示例：

```text
无法解释风险 -> 提升解释能力
无法预测故障 -> 提升预测能力
无法停止危险任务 -> 提升异常停止能力
无法判断任务风暴 -> 提升任务管理稳定性
无法从结果中学习 -> 提升因果学习能力
```

这些是较深层的生存需求。它们看起来像自我实现，但在本系统中应解释为：

```text
长期生存能力需求。
```

## 7. 层级影响与优先级衰减

越远离物理不安全事件，安全影响越弱、越长期、越间接。

建议逻辑衰减：

```text
P：物理不安全事件，权重 1
A：直接原因，权重 0.1
B：二层原因，权重 0.01
C：三层原因，权重 0.001
D：四层原因，权重 0.0001
```

工程整数示例：

```text
L0：900000
L1：90000
L2：9000
L3：900
L4：90
L5：10
```

该权重只用于需求候选优先级和投影衰减，不得直接作为安全 / 服务结算值。

目的：

```text
越接近物理安全损害，越优先；
越深层的长期原因，只有在近层稳定后才逐步处理。
```

## 8. 门控规则

### 8.1 低层未稳，高层不生独立需求

```text
如果物理不安全事件正在发生：
    只生成应急止损需求。

如果直接原因未控制：
    不生成更深层的独立长期需求。

如果近因未稳定：
    不生成永久安全需求。
```

形式化：

```text
低层未过最低标准，高层独立需求不生成。
```

但高层可以作为低层手段。

示例：

```text
硬件过热时可以联系维护者；
但此时联系维护者的归属目标是“降温”，
不是独立的“提升协作关系”。
```

### 8.2 本层已饱和，本层不再生需

如果某个深层原因已经被充分处理：

```text
维护机制已经稳定
备份机制已经足够
自检能力已经足够
```

则：

```text
不继续生成本层需求，只保留监测。
```

形式化：

```text
本层达到饱和标准，本层不再主动生成需求。
```

## 9. 投影公式

对因果节点 `X`，可计算其深层生存需求强度：

```text
Need(X)
    = Severity(P)
    × Prob(Path)
    × Strength(X -> ... -> P)
    × Confidence(Path)
    × Decay(depth)
    × Control(X)
```

其中：

```text
Severity(P)：
    物理不安全事件严重度。

Prob(Path)：
    该因果路径发生概率。

Strength：
    因果影响强度。

Confidence：
    派生证据置信分。

Decay(depth)：
    层级衰减，例如 0.1^depth。

Control(X)：
    可干预程度。
```

规则：

```text
Need(X) > 生成阈值：
    生成需求候选。

证据不足：
    生成确认需求，而不是修复需求。
```

## 10. 示例

观察到：

```text
P：硬件过热，宕机风险上升
```

因果解释：

```text
P：硬件过热
↑
A：散热不足
↑
B：风扇积尘
↑
C：长期无人维护
↑
D：没有维护联系人
↑
E：维护请求缺少可信解释
↑
F：自我解释能力不足
```

生成顺序：

```text
L0 应急需求：
    降低负载
    进入保护模式
    请求立即降温

L1 直接原因需求：
    改善散热
    检查风扇状态

L2 近因需求：
    清理风扇积尘

L3 长期原因需求：
    建立周期维护机制

L4 协作原因需求：
    建立维护联系人

L5 信任 / 治理原因需求：
    提升维护请求可信度
    提升自我解释能力
```

当 L0 未稳定时，L4 / L5 不作为独立需求进入主竞争。

当 L0、L1、L2 稳定后，系统才可以继续处理 L3 / L4 / L5。这就是：

```text
从生存应急到生存深层治理。
```

## 11. 与因果类用途的关系

因果类应为生存深层需求提供：

```text
解释深层原因：
    从物理不安全事件反向追溯上游因果链。

计算因果深度：
    得到每个原因到物理事件的距离。

投影深层需求：
    将可干预因果节点转成需求候选。

预测需求收益：
    判断处理该深层原因是否能降低未来物理风险。

执行后验收：
    判断该需求完成后，相关因果节点风险是否下降。

更新因果稳定度：
    成功则提高因果路径派生置信分，失败则降低。
```

生存深层需求不是凭空生成，而是由：

```text
因果解释结果
```

投影出来。

## 12. 与需求树的关系

生存深层需求正式入树前必须仍满足需求树入树闸门：

```text
目标宿主明确；
目标特征类型明确；
当前状态明确；
目标状态或目标区间明确；
满足关系明确；
父需求明确；
派生归因明确。
```

第一版父需求建议：

```text
应急止损和近层安全原因：
    挂安全根需求或对应安全父需求。

深层确认 / 预防 / 备份 / 能力型需求：
    挂在触发它的安全父需求或因果投影父需求下。
```

禁止：

```text
因果类直接写正式需求节点。
因果类直接创建任务。
深层需求绕过低层门控进入主竞争。
把深层需求完成直接结算为真实物理安全值。
```

## 13. 最终口径

```text
生存深层需求，是自我为了降低未来物理不安全事件发生概率，
对其上游深层因果原因进行确认、控制、预防、备份或能力提升而生成的需求。
```

它不直接等同于真实物理安全增量，而是通过降低因果链上游风险形成潜在生存贡献。

最短口径：

```text
深层原因解释“为什么未来会危险”，
生存深层需求决定“现在要治哪个上游原因”。
```

再压缩：

```text
物理安全管止损；
因果深层管治本；
深层需求就是从治本节点长出来的需求。
```
