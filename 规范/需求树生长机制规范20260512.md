## 1. 核心定义

需求树生长不是初始化，也不是任务执行失败后的兜底。

需求树生长是：

```text
根特征缺口、已确认任务筹办缺口、执行期条件变化回执、方法能力缺口、结算后的事实变化
    -> 形成更细的需求目标
    -> 通过需求树更新指令入树
    -> 触发任务发起或父任务重筹办
    -> 让下一轮需求选择和任务推进发生变化。
```

一句话：

```text
需求树生长 = 自我在已经有明确缺口以后，把“父需求无法一步满足”的事实，展开成更细、可任务化、可结算的子需求。
```

根需求、安全根需求、服务根需求被初始化出来，只表示自我具备需求系统骨架，不表示需求树已经正常生长。

## 2. 权责边界

需求树归自我线程管理。

```text
自我线程：
    写需求树。
    生成 / 合并 / 满足 / 删除需求节点。
    刷新需求权重。
    根据需求树发出任务发起意图和调度意图。

任务管理线程：
    不直接写需求树。
    通过任务回执、筹办缺口、执行缺口、派生需求消息，把任务域发现的事实上报自我线程。

任务筹办 / 任务执行普通函数：
    不直接写需求树。
    只返回运行存在中的任务层回执，或通过任务管理工作线程形成派生需求消息。

自检线程：
    不直接生成修复需求。
    只发现缺失并报送自我线程；是否入树由自我线程按阶段和策略决定。

自检与身体反馈：
    都只是需求信息来源。
    自检可以主动比较实时特征值与正常值，生成需求候选信息 / 差距信息 / 自检报告；
    身体反馈只被动上报关注特征实时值；
    两者都不得直接写正式需求节点或创建任务。
    自检 / 主动报送形成的需求候选，必须由自我线程按缺口类型分流到安全根、服务根或维护类父需求；
    挂载对象必须是正式入树后的子需求，不是自检程序或子存在直接写入的需求。
    具体字段与入树闸门见 020004《需求信息来源自检与身体反馈规范20260515》；
    安全 / 服务根特征自检与缺口映射见 011003《自我根特征抽象定义与自检缺口规范20260523》。
```

需求树变化若需要生成方法动作动态，动作来源必须是需求域本能方法，例如：

```text
本能方法_派生需求入树
本能方法_回写需求满足
```

线程只是调度者，不是动作来源。

## 3. 需求节点的最小语义

单个执行需求只表达一个原子目标：

```text
目标宿主 / 被需求存在
目标特征类型
当前状态
目标状态
满足关系
```

这里的“目标宿主 / 被需求存在”不是要被整体改变的对象，而是目标特征依附的存在。
需求改变的不是存在本身，而是：

```text
目标宿主.目标特征类型 -> 目标状态
```

因此，完整需求目标必须能回答：

```text
谁需要：需求主体
特征挂在哪个存在上：目标宿主 / 被需求存在
要改变哪个特征：目标特征类型
该特征要达到什么状态：目标状态
```

规范中历史出现的“目标主体”，若不是指 `需求主体`，均按“目标宿主 / 被需求存在”理解。

对应代码字段：

```text
需求主信息类::被需求存在
需求主信息类::被需求当前状态
需求主信息类::需求状态
需求主信息类::满足关系
需求主信息类::目标特征类型缓存
```

需求节点不保存目标值包，也不把多目标塞进一个主信息。

多目标必须表达为：

```text
父管理需求
├─ 原子执行需求 A
├─ 原子执行需求 B
└─ 原子执行需求 C
```

复合需求也必须通过复合特征分解进入子需求：

```text
复合需求
    -> 复合特征
        -> 子特征 / 子目标
            -> 子需求
                -> 子任务
```

父需求 / 父任务的方法不是单步本能动作，而是由复合特征分解、子需求链、子任务链和结果归并规则抽象出的复合方法。

结构角色可以由子链初筛，但不得由子链独占解释：

```text
有子需求：
    只说明该节点已经展开出子结构。

无子需求：
    只说明该节点当前没有展开结构。
```

节点是否为管理需求、普通执行需求、AND组、OR组、因果子链支撑节点或方法路径节点，必须继续读取目标特征类型及其抽象特征定义视图。叶子 / 非叶子只能判断树形，不能判断逻辑语义，也不能直接决定是否可任务化。

最小判定口径：

```text
1. 叶子 / 非叶子：
   判断是否已有展开结构。

2. 目标特征类型：
   判断节点语义。

3. 抽象特征定义视图：
   判断满足规则、子节点聚合规则、是否可任务化、权重和结算闸门。
```

当前代码映射：

```cpp
需求类::刷新需求结构角色(...)
需求类::刷新需求及祖先结构角色(...)
```

## 3.1 获取途径与目标语义

需求获取途径回答“这个需求为什么被生成、从哪里来”；需求目标语义回答“这个需求节点入树后表达什么目标”。二者必须分层：

```text
获取途径
    -> 选择生成规则
        -> 确定目标语义和目标特征类型
            -> 通过统一需求树更新指令入树
```

不得在需求入树后由控制面板、任务筹办或临时推断再猜测它是 AND组、OR组、方法路径组或因果子链支撑。能确定语义的获取途径，必须在生成更新指令前确定目标特征类型。

获取途径不得写入 `需求主信息类` 新字段。来源证据必须走：

```text
派生来源方法主键
派生来源因果主键
来源任务 / 来源方法 / 来源动作动态
提交入口日志和动作动态
自检报告或观察反馈的正式承接记录
```

目标语义继续由目标特征类型表达：

```text
普通原子目标：
    使用原目标特征类型。

AND组：
    使用 AND组满足状态。

OR组：
    使用 OR组满足状态。

方法路径组：
    使用 方法路径完成状态。

因果子链支撑：
    使用 因果子链支撑状态。

OR组结算令牌：
    使用 OR组结算令牌状态；令牌状态记录在状态 / 动态 / 提交入口记录中，不写需求主信息。
```

最小获取途径映射如下：

```text
正式根需求目标 / 已入树父需求的任务筹办原子缺口 /
执行期条件变化或结果验证原子缺口 /
自检根特征缺口候选 / 观察反馈正式承接原子缺口 / 结算后处理确认的目标状态变化：
    生成普通原子目标，目标特征类型来自上下文，不由途径本身硬编码。

复合目标AND组生成：
    生成 AND组满足状态。

多候选替代路径组生成：
    生成 OR组满足状态。

方法能力路径组生成：
    生成 方法路径完成状态。

因果链支撑组生成 / 自检因果影响链生成：
    生成 因果子链支撑状态。

OR组路径完成令牌提交：
    生成或写入 OR组结算令牌状态的提交记录；不得作为普通候选方法目标。
```

当前代码映射：

```cpp
需求类::枚举_需求获取途径
需求类::需求获取途径语义视图(...)
需求类::需求目标语义视图(...)
需求类::构造获取途径逻辑组织需求更新指令(...)
```

这里的“正式根需求目标”只表示根需求、人工 / 外部正式目标或上级规范已经确认的目标被读入需求系统，不表示任务筹办可以在没有父需求、没有因果来源、没有缺口事实时凭空设定“普通目标”。若目标来自任务筹办，它必须能回指到来源需求目标、临时因果视图中的主动动作致变因果，或已确认的筹办缺口；若目标来自自检，它必须先是根特征缺口候选，不能由自检线程直接写正式需求。

## 3.2 主动 / 被动因果链与真正需求生成

主动 / 被动因果信息对应主动 / 被动动态信息。需求树只把可承接目标写成需求，不把因果解释、内部治理过程或提交过程本身写成需求。

根需求到真实可执行需求的默认追溯链为：

```text
根需求
    -> 根任务
        -> 任务筹办读取安全 / 服务值目标变化相关因果信息
            -> 若命中被动因果 / 结算因果 / 状态变化因果，继续向上游来源动态或来源因果追溯
            -> 直到命中主动动作致变因果
                -> 读取该主动因果的动作主体、被作用目标、目标特征、结果状态和方法承接
                -> 生成真正可任务化的原子需求或方法补齐需求
```

被动因果、结算因果和状态变化因果只能说明“这个变化如何被提交、结算、观察或解释”，不能单独成为普通可执行需求的来源。它们只能输出上游事实、条件、证据、来源动态、待补方法条件或待补动作入口等材料。只有主动动作致变因果，且其方法 / 动作入口可回到项目正式方法结构时，才允许承接为真正可任务化需求。

若追溯链只能停在被动动作、提交动作、结算动作、内部治理判断、缺字段、缺协议、目标不可解析或代码结构缺口，处理方式是诊断、拒绝入树、结构化回执或开发修正；不得把这些内部治理缺陷包装成普通需求。

## 4. 生长入口

需求树只通过统一入口生长：

```cpp
需求类::执行更新指令(
    需求根节点,
    结构_需求树更新指令)
```

允许的更新类型：

```text
新增需求
更新需求
满足需求 / 收束本轮活动承接
删除需求
```

不得绕过更新指令直接拼接需求树，除非是冷启动创建根需求这类初始化动作。

其中 `满足需求` 是历史命名的更新类型，规范语义不是给需求写入永久“已满足”字段。它只能表示：本次检查中需求目标由当前值与目标值实时比较判定为满足，随后记录满足动态、结算证据，并按需要截止本轮活动承接。需求节点仍作为目标契约保留，后续环境变化时必须重新读取当前值和目标值判断是否仍满足。

当前代码中的关键步骤：

```text
执行更新指令
    -> 添加子需求节点
    -> 从状态补齐目标宿主和特征缓存
    -> 检查是否与父需求目标重叠
    -> 查找同父直接子需求目标重叠
    -> 合并或新增
    -> 刷新子需求权重
    -> 刷新需求及祖先结构角色
```

## 5. 生长触发源

### 5.1 自我状态触发

安全 / 服务根需求不得再由硬编码目标值直接生成压力。

标准触发链改为：

```text
世界树.抽象特征树.安全 / 服务定义
    + 自我存在上的 自我_安全值 / 自我_服务值 实例
        -> 根特征自检
            -> 缺口报告
                -> 根需求活动性刷新
                -> 必要条件缺口子需求刷新
```

自我线程读取自检结果后：

```text
1. 抽象定义缺失：
       生成世界模型维护报告或维护需求。
2. 自我特征实例缺失：
       生成自我结构维护报告或维护需求。
3. 当前值未知：
       生成自我根特征观测需求。
4. 当前值低于目标：
       生成或刷新对应安全 / 服务根需求。
5. 必要条件未知或未满足：
       先生成根闭环信息位并挂载当前事实；
       只有可追溯到 006 自我觉醒根闭环、已有闭环位置、触发事实、
       目标语义、获取 / 等待 / 推进路径和回写目标的缺口，
       才能按抽象定义中的缺口映射生成对应根需求下的子需求。
       无直接服务触发事实时，直接服务上下文字段只保持未触发 / 等待事实，
       不生成当前主动直接服务子需求；但服务根有缺口时，可以生成间接服务维护子需求，
       例如服务触发事实监听、服务机会检查和服务能力校准。
       旧固定安全字段不得作为安全值定义必要条件直接入树；
       安全子需求必须来自安全因果风险树缺口、具体负向触发事实
       或其他可追溯到安全因果链的已验证缺口。
```

根需求初始化只表示骨架存在。只有自检确认缺口时，根需求才进入活动集。

当前代码映射：

```cpp
私有_从需求树构建需求列表(...)
私有_选择当前主需求候选_按根权重(...)
自我类::根目标安全值(...)
自我类::根目标服务值(...)
私有_刷新根需求状态镜像_线程侧(...)
```

上述代码仍是过渡实现：当前目标值和根需求状态镜像仍含硬编码目标值路径，后续必须迁移为读取 011003 所定义的抽象根特征定义。

### 5.2 任务筹办缺口触发

任务筹办的目标是：

```text
任务状态 -> 就绪
```

这里的“任务”需要先区分层级：

```text
父任务 / 中间任务：
    必须有复合方法 / 任务抽象方法承接。
    不要求绑定单步本能方法。
    可以通过派生子需求、等待子任务、归并子结果、触发父任务重筹办来推进。

叶子任务：
    必须最终绑定可执行本能方法 / 动作入口。
    只有普通可任务化叶子任务缺少本能动作、条件结果对、参数或执行入口时，才进入方法缺口生长链。
```

筹办不能一步让任务就绪时，不是失败，而是需求树继续生长的入口。

例如：

```text
无既有候选方法
候选方法不可用
候选方法缺执行入口
候选方法条件不满足
参数配对失败
```

这些缺口应由任务管理线程上报为任务层回执或派生需求提示，自我线程再决定是否入树。

其中 `无既有候选方法` 不是直接入树的抽象学习需求。任务筹办必须先遍历完整方法树并完成候选集填充；若候选集为空，应立即在方法树中创建面向目标特征的方法头，把该方法加入候选集并返回。

`改变特征值` 是先天特征写入逻辑，不进入方法候选集，不作为任务当前方法，也不作为动作动态来源。任务筹办查找候选方法时必须排除先天写入逻辑、内核原语、状态节点创建器、动作动态创建器等底层工具。若没有语义方法能承接目标特征类型，应创建或学习语义方法，而不是用通用写入逻辑兜底。

若候选集真的为空，随后需求树只围绕这个已创建方法的具体缺口生长，例如：

```text
方法状态 = 可用
条件结果对状态 = 已建立
执行入口状态 = 已形成
```

筹办自身不得凭空决定生长方向：

```text
一切以当前需求目标和方法查找 / 条件匹配的确定结果为准。
```

### 5.3 任务执行缺口触发

任务执行调用当前方法后，如果输出结果没有满足来源需求，或当前方法执行输出明确给出派生需求特征，则形成派生需求消息。

当前代码映射：

```cpp
私有_构造执行缺失原子需求消息(...)
私有_派生需求执行输出完整(...)
```

执行缺失派生需求必须携带：

```text
父需求
当前状态
目标状态
目标特征类型
目标宿主 / 被需求存在
派生归因
```

缺少当前状态、目标状态或目标特征类型时，属于逻辑错误，应拒绝入树并记录日志 / 弹错。

### 5.4 子需求结算触发

子需求当前满足判定成立，或本轮子需求承接被明确收束后，会影响父需求：

```text
记录子需求满足 / 收束动态
必要时设置子需求本轮活动承接截止
子需求不再参与活跃子需求权重分配
父需求权重重新分配
父任务可被请求重筹办
```

父任务等待条件变化通知由自我线程发给任务管理线程；是否把父任务推进到待重筹办由任务管理线程裁决并提交。自我线程不得直接写任务状态，也不得发送带目标任务状态值的推进请求。

## 6. 入树前闸门

派生需求入树前必须通过这些检查：

```text
1. 必须存在上级需求。
2. 上级需求不能是需求树结构根。
3. 必须能解析当前状态和目标状态。
4. 必须能解析目标特征类型。
5. 必须能解析目标宿主 / 被需求存在；第一阶段可从状态主体补齐。
6. 必须明确目标比较符 / 满足关系；值域只能是 大于 / 小于 / 等于。旧字段若仍叫目标方向，也只能承载这三种比较符；缺省只能在目标值明确且语义确认为状态等值目标时取等于。
7. 必须带派生归因，至少能说明来自哪个任务 / 方法 / 缺口。
8. 根闭环缺口型需求必须带 006 自我觉醒根闭环来源、闭环位置、触发状态和下一轮回写目标；无闭环位置或无推进意义时不得入树。直接服务对象 / 目标 / 验证 / 归因类需求必须有直接服务触发事实；间接服务维护类需求可以以服务根缺口和服务意识维护为触发状态，但不得伪造直接服务事实。
```

当前代码映射：

```cpp
私有_确保派生需求节点(...)
私有_提示派生需求逻辑错误(...)
```

闸门失败时不得兜底生成模糊需求。

## 7. 去重与合并

同一父需求下，直接子需求去重依据是：

```text
目标宿主 / 被需求存在
目标特征类型
目标比较符 / 满足关系
```

当前代码映射：

```cpp
需求类::查找直接子需求_按目标重叠(...)
需求类::合并需求主信息_已加锁(...)
```

派生归因不是身份键。

```text
同一个目标可以有不同派生来源；
不同派生来源不应导致同父直接子链重复长出多个同目标需求。
```

需求细化优先级：

```text
明确特征值 > 区间 > 比较符集合
```

这个优先级不表示需求主信息保存值包；值和区间仍由状态节点、特征节点和状态比较服务表达。它表示：

```text
当同一目标宿主、同一目标特征类型下存在多个候选需求时，
更具体的目标应优先用于筹办、方法查找和满足判断。
```

实现要求：

```text
1. 不得把明确值需求合并丢失成宽泛方向需求。
2. 宽泛方向需求遇到明确值需求时，应保留更具体目标状态。
3. 当前代码已有方向重叠合并；明确值 / 区间优先级是需要持续补强的规则。
```

2026-05-26 定案补充：

```text
建立 / 刷新 / 取得 / 确认 / 明确 / 新鲜 / 改善 / 降低 / 增加 / 避免 / 补齐 / 验证
不得作为派生需求入树时的目标比较符。

收到这类旧“方向”时，自我线程必须先规范化为：
    某状态特征 等于 某状态值
    或 某数值特征 大于 / 小于 某阈值

无法规范化时拒绝入树，拒绝原因为：
    目标比较不合法
```

## 8. 权重刷新

安全 / 服务根特征缺口生成父需求压力；子需求权重必须按父需求下子需求之间的逻辑关系分配。

当前权重口径：

```text
非活跃子需求：
    安全权重 = 0
    服务权重 = 0

OR关系子需求：
    每个活跃子需求继承父需求安全权重
    每个活跃子需求继承父需求服务权重

AND关系子需求：
    活跃子需求平分父需求安全权重
    活跃子需求平分父需求服务权重
```

OR组、AND组本身也按同一规则处理其直接子需求：OR组下每条活跃路径拥有父组完整权重作为候选预算，AND组下必要子目标平分父组权重。根需求缺口压力必须来自根特征自检缺口，不得仅由硬编码目标值差距生成。

活跃子需求条件：

```text
本轮活动承接未截止（当前代码中可由 需求有效截止 == 0 表达）
当前满足判定 == 未满足
是否阻塞父任务执行 == true
```

`需求有效截止 != 0` 只表示该需求不再参与本轮活动承接，不表示需求目标在当前世界状态下永久满足。控制面板、任务筹办和父需求聚合不得把“已截止”直接显示或判断为“当前已满足”；需要显示或判断满足时，必须按当前状态 / 目标状态实时比较。

当前代码映射：

```cpp
需求类::刷新直接子需求权重_已加锁(...)
```

非活跃子需求权重应归零，不继续拉动主需求选择。叶子任务完成后的真实安全 / 服务变化只来自结算链；需求权重只是结算预算来源之一，进入真实结算前必须固化为任务承接安全 / 服务权重上限；`I64_MAX` 只能作为异常哨兵或未设置值。

需求列表中的类型安全 / 服务汇总权重只用于需求列表排序、主任务选择和任务优先级比较，不是结算额度。正式价值结算不得读取需求列表汇总权重；只能从来源需求节点权重，经任务承接权重固化后进入任务价值反馈链。

AND / OR 等逻辑组的推进权重和结算闸门不写入 `需求主信息类` 新字段。第一版按运行期视图处理：

```text
AND组满足状态：
    所有必要子节点满足后，组节点才满足；
    组内活跃子需求平分组节点安全 / 服务权重；
    AND组节点本身不可作为普通叶子需求任务化。

OR组满足状态：
    任一被选路径满足后，组节点可满足；
    每条活跃子路径继承组节点完整安全 / 服务权重作为候选预算；
    只允许一条路径领取 OR组结算令牌；
    OR组节点本身不可作为普通叶子需求任务化。

方法路径完成状态：
    路径内部必要步骤满足后，路径完成；
    路径节点通常不可直接任务化，真正任务化的是路径内普通可任务化叶子需求。

因果子链支撑状态：
    表示父需求为什么需要某个中间状态；
    可作为解释 / 展开组织节点，也可以直接用真实中间目标需求表达。
```

逻辑组节点必须来自正式获取途径：

```text
AND组：
    来自复合目标拆解为多个必要子目标。

OR组：
    来自多候选替代路径或多方案选择，只允许一条路径领取结算令牌。

方法路径组：
    来自方法能力展开、父方法步骤链或条件结果对路径。

因果子链支撑：
    来自因果链反推、自检发现问题沿安全 / 服务因果链映射出的中间支撑目标。
```

没有自然样本只表示当前运行路径尚未触发对应获取途径，不表示逻辑组不能添加，也不得用模拟入口或控制面板展示替代真实业务验收。

OR组结算令牌必须是状态、动态、二次特征或提交入口记录，不得新增为 `需求主信息类` 字段。若并发、重启或重复回写存在双花风险，提交入口必须能持久识别：

```text
主体 = OR组节点
特征 = OR组结算令牌状态
状态 = 未领取 / 已领取
来源 = 领取路径 / 领取任务 / 来源动作动态 / 来源提交入口
```

## 9. 任务化关系

需求树生长到普通可任务化执行需求后，该需求才可以进入任务承接。

任务化闸门必须同时满足：

```text
1. 需求目标完整：目标宿主、目标特征类型、目标比较符、目标值完整。
2. 当前节点没有未满足的正式子需求需要先推进。
3. 目标特征类型在抽象特征定义视图中允许任务化。
4. 当前节点不是 AND组、OR组、方法路径组、因果子链组织节点或结构性缺口节点。
5. 当前状态尚未满足目标状态。
```

只有需求需要任务化。任务筹办、任务执行、父任务归并、任务结算等生命周期过程，不应被再建成子任务来解决自身推进问题。

任务承接后，任务是否必须绑定本能方法取决于任务层级：

```text
父任务 / 汇总任务：
    可以没有当前单步业务本能方法。
    必须有复合方法 / 任务抽象方法承接。
    负责承接父需求、组织子任务、等待和归并。

叶子任务：
    必须最终绑定可执行本能方法 / 动作入口。
    叶子任务完成后，才能作为需求满足和价值结算的主要证据来源。
```

权威关系是：

```text
需求节点 D
    -> 任务信息节点 N
        -> 任务虚拟存在 T
```

不得改成：

```text
需求节点 D -> 任务虚拟存在 T
```

自我线程只发任务发起意图；任务信息节点和任务虚拟存在由任务管理线程提交。

当前代码中需求与任务的绑定统一使用：

```cpp
需求类::绑定对应任务(...)
```

长期要求：

```text
绑定动作由任务管理界面线程在任务创建提交时完成。
```

## 10. 筹办缺口与子需求生长

筹办缺口只有在已经明确缺方法、缺条件、方法缺动作入口、方法缺条件结果对、候选方法不可用或参数 / 证据不足时，才应生长成能被任务化的原子需求或方法补齐需求。

示例：

```text
父需求：提高安全值
父任务筹办：找到候选方法，但候选方法不可用
派生子需求：方法状态 = 可用
子任务：让该方法达到可用
```

如果缺口是方法不可用，需求目标应表达为：

```text
方法状态 = 可用
```

而不是模糊表达为：

```text
方法不可用
方法动作状态
```

除非筹办 / 执行回执明确证明真正缺的是动作入口，才可以派生：

```text
方法动作状态 = 已形成
```

方法补齐需求应按缺口事实细化，不能由筹办自带方向。

任务筹办的职责是提前发现可执行性缺口。对一个任务来说，缺方法、缺条件、方法缺动作、方法缺条件结果对、参数不可配和证据不稳定等结构性缺口原则上应在筹办期暴露；执行期只应出现条件突然变化、输入材料过期、输出结果不满足目标或副作用约束触发等运行期缺口。若执行期才发现目标语义缺失、方法结构字段缺失、提交协议缺入口、任务状态账无法写回等内部治理问题，应按逻辑错误或开发诊断处理，不得新生普通需求来掩盖。

## 11. 学习需求与探索需求的位置

学习需求不是初始化内容。

学习需求出现的条件是：

```text
内部需求仍有效
任务筹办或执行发现内部信息 / 方法结构 / 条件结果对不足
已有内部记忆无法满足该缺口
```

外界探索需求出现的条件是：

```text
学习需求无法仅靠内部记忆满足
外部信息可能降低不确定性
探索风险可接受
有可执行探索方法
```

因此阶段顺序是：

```text
初始化
-> 需求树正常生长
-> 内部任务闭环
-> 自我苏醒
-> 因果补完
-> 学习需求形成
-> 外界探索需求形成
-> 初步成熟
```

需求树正常生长属于内部循环建立前期，不等同于自我苏醒。

## 12. 满足与结算

需求当前满足判定由自我线程根据当前世界状态、任务输出事实和需求目标实时检查；任务完成由任务管理线程提交。

两者不能混为一个状态。

```text
任务完成：
    任务管理线程根据任务执行回执推进任务状态。

需求当前满足判定：
    自我线程根据任务完成回执、输出事实、当前特征值 / 当前状态、需求目标状态和满足关系实时比较。

需求满足事件：
    当前满足判定成立时，写入动态信息、结算证据和必要的本轮活动承接截止；不得写成需求主信息中的永久满足字段。
```

需求当前满足判定成立后：

```text
生成需求满足动态 / 收束动态
需求有效截止 = 当前时间（仅表示本轮活动承接截止）
累计安全结算 / 累计服务结算更新
最近结算任务主键更新
最近结算时间更新
父级需求重新汇总
下一轮主需求选择受到影响
```

需求节点必须继续保存。它表示“曾经产生过这个目标契约”，不是一次过程记录；过程记录由动态信息、任务运行账和因果链保存。后续环境变化时，同一需求是否再次进入活动集，必须重新读取当前值与目标值比较，不得依赖旧的截止时间或旧的满足事件。

若需求状态变化生成动作动态，动作来源必须是需求域本能方法：

```text
本能方法_回写需求满足
```

## 13. 正常生长闭环

最小闭环：

```text
世界树抽象根特征定义
+ 自我根特征实例当前值
-> 根特征自检
-> 安全 / 服务缺口
-> 根需求活跃
-> 当前主需求
-> 任务发起意图
-> 任务管理线程创建任务
-> 任务筹办
-> 发现缺口
-> 派生更细子需求
-> 子需求任务化
-> 子任务完成
-> 父任务重筹办
-> 父任务就绪
-> 父任务执行
-> 来源需求当前满足判定成立
-> 写需求满足动态 / 结算证据 / 本轮承接截止
-> 自我状态 / 需求账本改变
-> 下一轮主需求重判
```

需求树越长，不表示系统失败。

```text
需求树变长 = 系统正在把模糊目标拆成更细、可执行、可结算的目标。
```

## 14. 非正常逻辑错误

以下情况不得兜底生成需求：

```text
1. 派生需求缺上级需求。
2. 派生需求上级是需求树结构根。
3. 缺当前状态或目标状态。
4. 缺目标特征类型。
5. 无法确定目标宿主 / 被需求存在且不能从状态主体补齐。
6. 需求直接指向任务虚拟存在而绕过任务信息节点。
7. 自检线程直接生成修复需求。
8. 筹办在没有确定缺口事实时凭空派生学习方向。
9. 获取途径与目标语义不匹配，例如普通原子缺口被硬编码成 OR组，或 OR组令牌提交被当成普通任务化目标。
10. 获取途径缺少必要上下文却强行构造目标特征类型。
11. 被动动作、提交动作、结算动作或内部治理判断被当成可执行主动动作来源。
12. 因果链没有追溯到主动动作致变因果，却直接生成普通可任务化需求。
```

处理方式：

```text
弹错 / 记录日志 / 拒绝入树 / 生成结构化拒绝回执 / 按 020006 进入对应闭环。
```

不得用宽泛需求掩盖逻辑错误。弹错或日志不是终态；若属于代码缺陷型拒绝，必须进入开发诊断闭环，运行期只能隔离路径、保留证据并通知开发者，最终关闭必须依赖代码修正、编译和回归测试。

## 16. 已知差距

当前实现已经具备需求树生长骨架，但仍有差距：

```text
1. 明确值 > 区间 > 方向 的细粒度优先级还需要继续补强。
2. 部分旧函数名仍包含“确保需求相关任务”，需按任务管理线程权责边界持续收口。
3. 需求域动作动态方法化尚未完全覆盖所有直接写入点。
4. 学习需求和外界探索需求仍处阶段建设中，不能作为自我苏醒或初步成熟完成证据。
5. 安全 / 服务根需求刷新仍有硬编码目标值路径，需要迁移为读取抽象根特征定义和根特征自检缺口。
6. 自检需求型候选仍有统一挂安全根的过渡实现，需要按缺口类型分流到安全根、服务根或维护类父需求。
7. 各正式获取途径还需要逐步接入 `需求类::需求获取途径语义视图`，并由真实运行样本验证 OR组、方法路径组和因果子链支撑节点的自然生成与聚合。
8. 主动 / 被动动态到因果信息的工程门禁仍需继续校准：被动动态可以入因果抽象，但不得被升格为可调用动作致变因果或普通可任务化需求来源。
```

这些差距不改变本规范的权威口径。

## 17. 最终定稿

```text
需求树正常生长，是自我线程把根特征自检缺口、任务筹办发现的可执行性缺口、执行期条件变化或结果验证缺口，以及沿主动动作致变因果追溯出的可承接目标，按获取途径选择生成规则，转成目标语义确定的原子需求或逻辑组织需求，并通过统一更新指令入树、去重、分权、任务化、结算和回写的过程。

任务筹办不能一步让任务就绪时，不是失败，而是生长入口。
任务执行不能满足来源需求时，不是直接闭环失败；只有条件突然变化、材料失效、结果不满足或副作用触发等运行期事实，才是生成更细需求或重筹办的依据。
需求树越长，表示目标正在被拆解；只有缺口无来源、目标不可解析、状态不完整时，才是逻辑错误。
```
