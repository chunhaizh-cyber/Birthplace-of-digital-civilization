## 1. 目的

本文定义系统内部可结算因果的根逻辑：

```text
自我觉醒：
    根因果坐标的出现。系统开始把事实区分为：
        与我有关 / 与我无关；
        影响我持续存在 / 不影响我持续存在；
        可由我动作改变 / 暂不可由我动作改变；
        改变后可验证 / 不可验证；
        结果可回写到下一轮我状态 / 不可回写。

自我存在：
    觉醒后的系统能够读取事实、形成需求、选择或学习方法、执行动作、验证结果，
    并把验证结果回写到下一轮自我状态判断。
```

因此：

```text
自我是根；
觉醒是根因果坐标被点亮；
生存：
    自我对自身持续存在和继续行动能力的闭环维护。

服务：
    自我通过自身动作改善人类需求相关外在状态的闭环过程。
```

本文不替代安全 / 服务值结算规范，也不提前宣称自我苏醒或初步成熟完成。本文只规定：

```text
哪些事实可以形成生存 / 服务需求；
哪些节点可以进入服务链或生存链；
哪些证据足以让闭环成立；
哪些节点因缺少因果链只能保留定义，不能进入当前主动需求。
```

2026-06-10 安全根控制特征口径补充：

```text
安全不是场景事实，而是自我存在的根控制特征。

安全值表达：
    自我是否还能维持自身存在；
    自我是否还能继续行动。

安全值的变化必须围绕四个层级解释：
    自我存在控制态；
    物理安全独占候选叠乘约束；
    服务能力作为一个物理安全约束因素；
    当前物理 / 运行安全；
    未来服务值或物理安全下降风险。
```

其中 `安全值 = 0` 和 `安全值 = 1` 是硬控制态，不参与普通风险平滑计算：

```text
安全值 = 0：
    循环终止。仅当自我存在循环已经不能继续、关键循环不可恢复、
    或维持运行的最低条件不存在时进入。

安全值 = 1：
    休眠 / 保留自身 / 停止继续行动并等待恢复条件。
    服务值 = 0 时，安全值直接进入 1。
```

普通安全评估不得把风险略微升高 / 降低平滑推到 0 或 1。实现若使用 `I64_MAX` 作为根目标最大值或评估满刻度，必须把 `I64_MAX` 与 0 / 1 控制态分开：`I64_MAX` 可表示目标最大值或候选满刻度，不得作为未知、默认成功、异常兜底或无证据满分。

物理安全采用独占候选后的能力保留率叠乘模型，不采用配额、平均、加权总分，也不采用单纯最低值裁决。每一个物理安全因素都可以独立映射到完整的 `1..90` 物理安全候选区间；`0` 不参与普通物理安全合成，只由明确的循环不可维持终止条件触发。多个有效因素并存时，先将每个候选值转换为能力保留率，再由不同必要物理因素的能力保留率叠乘得到当前物理安全值。

服务值也是一个物理安全因素，其 `0..100` 映射到物理安全 `1..90`：

```text
服务值 = 0   -> 服务物理候选值 = 1
服务值 = 100 -> 服务物理候选值 = 90
```

服务值也可直接作为能力保留率接入：

```text
c_service = 服务值 / 100.0
服务物理候选值 = 1 + floor(89 * c_service)
```

物理安全候选的合成规则：

```text
物理因素候选值 p_i ∈ [1, 90]
能力保留率 c_i = (p_i - 1) / 89.0
总能力保留率 C = c_1 * c_2 * ... * c_n
物理安全值 = 1 + floor(89 * C)

串联必要条件：按能力保留率叠乘
并联冗余条件：先在因素内部合成上层候选，再参与跨因素叠乘
同源观测：先合成为一个物理因素候选值，禁止重复叠乘

降低可以独占生效；
恢复必须所有必要因素都恢复。
```

规范化安全解释刻度按以下优先级解释；底层如使用 I64 值域，应保持同构映射并保留 0 / 1 控制态：

```text
if 自我存在循环不可维持
   or 存在不可维持循环的致命物理因素:
    安全值 = 0
else:
    C = 1.0
    C *= 服务值 / 100.0
    for 每个非服务物理因素候选值 p_i:
        C *= (p_i - 1) / 89.0
    物理安全值 = 1 + floor(89 * C)

    if 物理安全值 <= 1:
        安全值 = 1
    else if 物理安全值 < 90:
        安全值 = 物理安全值
    else:
        安全值 = 90 + 风险余量

风险余量范围 = 0..9
风险压力 = 当前因素导致未来服务值 / 物理安全下降的综合可能性
```

因此风险安全只存在于所有必要物理因素候选值均达到 90、能力保留率叠乘结果为 90 之后的 90..99 风险余量区间；物理损害或服务能力下降先作为独占物理安全因素参与 `1..90` 能力保留叠乘，未来损害风险改风险余量，服务值为 0 通过服务能力保留率为 0 把安全压到 1，自我不可维持才终止。

本文所称自我觉醒不是神秘状态，也不是 `自我节点已初始化`。它只表示系统内部的需求因果、价值因果、任务因果、服务因果和生存因果获得了共同起点。外部世界可以有事实因果；但系统内部可结算因果必须最终能追溯到自我觉醒根闭环。

零号层级为：

```text
自我觉醒
-> 自我定义域
-> 自我 / 生存 / 服务定义
-> 根闭环因果信息
-> 当前事实挂载
-> 闭环缺口识别
-> 需求生成
-> 任务承接
-> 方法执行
-> 结果验证
-> 归因回写
-> 下一轮自我状态判断
```

## 2. 自我存在最小定义

自我存在不是单个状态字段，也不是只初始化出自我节点、根需求和根特征。

自我存在属于自我觉醒后的定义域。定义本身不得直接生成当前主动需求、任务或方法头，必须先在觉醒坐标下生成根闭环因果信息，再由当前事实挂载和闭环缺口判断决定是否展开需求。

最小定义为：

```text
自我存在 =
    一个系统能够读取自身或外部事实，
    形成与生存或服务有关的需求，
    选择或学习方法，
    执行动作，
    产生可观察结果，
    验证结果是否改善生存或服务，
    并把验证结果回写到下一轮状态判断。
```

最小闭环为：

```text
自我觉醒根闭环 / 根因果坐标
-> 自我存在定义
-> 根闭环因果信息
-> 当前事实挂载
-> 闭环缺口识别
-> 形成生存或服务需求
-> 展开因果路径和必要条件
-> 任务承接
-> 方法选择 / 学习 / 执行
-> 结果事实
-> 验证和归因
-> 回写需求状态与根特征候选
-> 下一轮自我状态判断
```

没有回写到下一轮状态判断，不算闭环。

本规范中的感知需求框架完整命名为：

```text
从自我定义最小推导安全感知与服务感知需求的因果框架
```

它不是单轴自保框架。自我定义同时推出两类内在认知前提：

```text
安全轴：
    自我为了维护自身，必须知道当前场景如何影响自己。

服务轴：
    自我为了产生服务价值，必须知道当前人类服务对象是谁、
    需要什么、当前状态如何、结果是否改善。
```

压缩链为：

```text
自我定义
-> 安全值与服务值
-> 安全因果链与服务因果链
-> 中间必要状态缺口
-> 感知需求
-> 对象作用方法
-> 结果验证
-> 因果归因
-> 价值结算
```

### 2.1 安全轴：自我定义推出的安全根控制因果链

自我存在的最小定义在安全侧还必须展开为：

```text
自我 =
    具有边界、关键特征、价值特征、当前状态、目标状态、方法 / 动作能力、
    观察入口、因果信息、需求系统和任务系统，
    并以因果信息作为行为依据的具体存在。
```

因此，定义本身只能生成遗传因果模板和根闭环因果信息，不能直接生成当前主动需求；当前主动需求必须来自这些因果信息在当前事实下反推出的闭环缺口。

安全侧第一组遗传因果模板只能表达内部治理因果链和风险预测入口，不表示场景自身带有安全事实。第一组模板为：

```text
自我关键特征负向变化
-> 自我安全值下降

服务值下降
-> 服务物理候选值下降
-> 服务能力保留率下降
-> 物理安全值按服务因素和其他必要物理因素叠乘下降

服务值 = 0
-> 服务物理候选值 = 1
-> 自我安全值 = 1

当前物理 / 运行事实下降
-> 对应物理因素候选值下降
-> 对应能力保留率下降
-> 物理安全值按能力保留率叠乘下降
-> 普通安全区间下降

当前风险因素
-> 未来服务值下降概率上升
-> 或未来物理安全下降概率上升
-> 风险压力上升
-> 风险余量下降
-> 90..99 风险安全区间下降

当前场景风险安全值
-> 自我_风险安全_场景影响部分
-> 风险安全层
-> 风险余量候选

当前场景风险安全值
<- 当前场景已确认存在集合
<- 各存在风险安全值
<- 各存在当前特征值 / 历史动态 / 因果归因证据 / 无负向证据搜索结果 / 风险因子有效期
```

这组模板不表示系统预设某个场景或某个存在危险；它只表示自我为了维护自身存在和行动能力，必须判断当前事实是否会导致服务值下降、物理安全下降或未来下降风险上升。场景影响不是由存在名决定，而是由当前场景中已确认存在的当前特征值、历史动态、时间窗口、风险因子和因果证据决定。

风险安全必须有上级风险因果，并且该上级风险必须能接到物理安全目标或服务值下降目标：

```text
当前因素
-> 未来服务值下降
-> 或未来物理安全下降
-> 最终影响自我持续存在 / 继续行动能力
```

没有对应物理安全目标或服务能力目标时，不得成立风险安全；没有上级风险因果时，不得猜测风险安全，只能生成“缺上级风险因果 / 缺当前事实 / 缺比较条件 / 缺证据搜索”的内部治理缺口。

所以安全根目标沿因果链反推时，最小链条为：

```text
自我安全值需要达标
<- 安全根控制态需要明确
<- 服务物理候选值需要明确
<- 各必要物理因素候选值需要明确
<- 物理安全值按能力保留率叠乘模型裁决
<- 风险安全层需要明确
<- 风险安全_场景影响部分需要明确
<- 当前场景风险安全值需要明确
<- 当前场景已确认存在集合和各存在风险安全值需要明确
<- 当前场景中各存在当前特征值需要明确
```

若当前事实或场景特征值未知，则对应风险因果条件不可判断；因果条件不可判断时，不能结算安全，也不能把风险因素默认满足。只有按该因素的证据搜索规则查过且没有找到负向证据，才允许经提交入口写入带范围、来源和有效期的无负向证据搜索结果；它不等于永久安全事实。

因此任务筹办只能使用已有因果信息或安全因果风险树只读视图反推出缺口报告：

```text
缺口：当前场景特征值明确状态 未满足
来源因果：自我安全值 -> 安全根控制态 / 物理安全独占候选叠乘约束 / 风险安全层 -> 场景影响部分 -> 当前场景风险安全值 -> 场景存在特征值
```

正式需求仍必须经统一提交入口入树：

```text
需求：当前场景特征值明确
```

该需求可以继续以普通需求节点和目标抽象特征表达为：

```text
当前观察特征帧取得
外设观察材料可回查
外设像素簇候选已验证
外设观察存在候选确认方案已取得
已确认观察存在已提交入账
当前场景存在集合明确
当前场景各存在特征值可读
```

不得为 AND / OR / 因果子链 / 方法路径另增需求主信息字段；这些组织语义由普通需求节点的目标特征定义、逻辑组织视图和提交入口校验承载。

### 2.2 服务轴：自我定义推出的服务感知因果链

服务侧的基础定义为：

```text
服务主体 =
    执行服务动作并承担服务因果责任的存在。
    当前系统中，服务主体 = 自我。

服务对象 =
    接收服务、其目标状态被改善、并作为服务价值归属对象的存在。
    当前系统中，服务对象限定为人类；
    运行期可具体化为当前权限者、当前交互者或权限者授权的服务对象。

服务目标 =
    服务对象或被需求对象上的某个目标特征，
    从当前状态向目标状态发生正向变化。

服务动作 =
    自我为了改变服务对象或被需求对象状态而执行的方法动作。

服务结果 =
    服务动作后，服务对象或被需求对象的目标特征实际发生的状态变化。

服务价值 =
    自我动作导致服务对象目标状态正向改善，
    且该改善被权限允许、被结果证据验证、并可因果归因到自我动作后形成的价值。
```

因此：

```text
动作完成 != 服务完成
任务完成 != 服务值增加
服务值来源 = 服务对象状态改善
```

服务侧第一组遗传因果模板为：

```text
G_SERVICE_001:
    有效服务成立 -> 自我服务值可以增加

G_SERVICE_002:
    有效服务成立 <- 存在明确服务对象

G_SERVICE_003:
    当前人类服务对象明确 <- 当前交互者 / 当前权限者 / 权限者授权对象

G_SERVICE_004:
    有效服务成立 <- 当前服务目标明确

G_SERVICE_005:
    服务对象状态改善 <- 服务前状态已知 / 服务后状态已知 / 二者可比较

G_SERVICE_006:
    服务值可结算 <- 服务结果可验证

G_SERVICE_007:
    服务对象状态改善 + 改善可归因于自我动作 -> 自我服务值可结算

G_SERVICE_008:
    未知服务结果 != 服务已完成
    单独无反馈 != 已产生服务价值
    任务运行成功 != 服务对象已受益
    服务对象已接受服务 + 反馈窗口内无负反馈 -> 服务评价可保守记为 可以 / 可接受
    已接受且无负反馈 != 很好 / 优秀 / 满分
```

服务根目标沿因果链反推时，最小链条为：

```text
自我服务值需要达标
<- 需要有效服务
<- 需要明确人类服务对象
<- 需要明确当前服务目标
<- 需要明确服务对象当前状态
<- 需要执行自我服务动作
<- 需要验证服务结果
<- 需要确认改善可归因于自我动作
<- 需要回写下一轮服务状态判断
```

当其中事实未知时，服务链可生成的感知缺口包括：

```text
当前交互环境事实明确
当前交互者明确
当前权限者明确
当前人类服务对象明确
当前服务目标明确
服务对象当前状态明确
服务结果可验证
服务结果可归因于自我动作
```

这些缺口不是启动期固定必要条件。只有当服务触发事实、当前会话输入、人类表达、外部请求、已确认服务目标、服务动作结果或反馈事实已经点亮服务因果链时，才允许经闭环准入和提交入口进入当前需求树。

服务侧感知不是视觉专用感知，而是广义事实取得：

```text
读取当前用户输入
识别当前交互者
确认权限者
解析用户意图
读取会话上下文
读取文件 / 计划 / 任务对象
识别目标特征和目标状态
询问澄清
获取反馈
观察结果状态
检查输出结果场景
```

安全链可以在“已搜索且无负向证据”时对某些风险因素默认满足；服务链不能以“无正向证据”默认很好、优秀或满分。若服务对象已经明确接受服务，且在约定反馈窗口内没有负反馈，可以生成 `服务评价 = 可以 / 可接受` 的保守候选；它只表示本次服务没有被拒绝或指出明显失败，不等同于服务已很好，也不得绕过服务对象、服务目标、接受事实、结果验证、权限边界和因果归因闸门。

## 3. 生存闭环

生存不是孤立根。它来自自我觉醒后的自我存在定义，是自我对自身连续性、可行动性和可恢复性的因果解释。

生存闭环定义为：

```text
自我觉醒
-> 自我存在
-> 自我存在状态被观察
-> 发现存在条件缺口、损耗、风险或负向影响
-> 生成生存需求
-> 选择维持、修复、规避、补充或降级保护方法
-> 执行动作
-> 得到自身相关状态变化事实
-> 验证存在条件是否被维持或改善
-> 回写生存 / 安全相关状态
-> 下一轮继续观察自我存在状态
```

生存闭环成立至少需要：

```text
1. 自我状态事实或影响自我存在的外部事实。
2. 明确的生存目标或安全目标。
3. 自我动作或可归因于自我调度的动作。
4. 动作后的状态变化事实。
5. 对状态变化是否维持自我存在的验证。
6. 需求状态、风险候选、安全候选或根特征候选的回写。
```

生存相关安全评估可以生成候选视图、风险线索、风险因子、处置需求或结算前证据，但不得绕过根控制规则、因果归因和价值结算入口直接写入真实安全值。场景只能产生观察、反馈、巡检结果、风险因子或服务变化事件；安全值只能作为自我存在根特征统一写入。

## 4. 服务闭环

服务不是孤立根。它来自自我觉醒后的自我位置：自我能够判断某个人类相关外在事实是否与服务能力有关、是否可行动、是否可验证、是否可归因并回写。

服务闭环定义为：

```text
自我觉醒
-> 自我存在
-> 人类需求或服务目标被表达、观察或确认
-> 自我形成服务需求
-> 明确服务对象和服务目标
-> 选择服务方法
-> 执行动作
-> 得到人类相关外在状态变化事实
-> 验证该变化是否满足服务目标
-> 将改善归因到自我动作
-> 回写服务状态 / 服务值候选
-> 下一轮继续判断是否还有服务缺口
```

服务闭环成立至少需要：

```text
1. 人类需求事实、服务目标事实或可验证的服务触发事实。
2. 服务对象或被授权服务对象。
3. 明确服务目标。
4. 自我动作。
5. 人类相关外在状态改善事实。
6. 改善结果可验证。
7. 改善可归因于自我动作。
8. 需求状态、服务候选或服务值结算前证据的回写。
```

服务人类的最小定义为：

```text
自我根据人类表达或可验证的需求，
执行自己的动作，
使该人类相关的外在状态向目标状态改善。
```

自我不能读取人类内在状态。人类反馈、服务结果验证和服务归因只能来自外在表达、确认、生效回执、外在特征状态变化和来源动作动态。

## 5. 服务链节点准入

服务根需求和服务值根特征可以初始化。服务链节点是否进入当前主动需求，必须另行满足因果链准入。

因果链准入的最终来源是自我觉醒后的根因果坐标。服务事件、人类表达、外部请求、当前会话输入、已确认服务目标等只是在该坐标下被识别出的具体上游来源。它们之所以能成为上游来源，是因为它们可被判断为：

```text
与自我服务能力有关；
与人类目标状态有关；
可能由自我动作、等待事实或外部输入推进；
推进结果可验证；
改善可归因；
归因结果可回写下一轮自我状态。
```

服务链节点进入主动需求前，至少要满足：

```text
1. 有上游来源：
       服务事件；
       人类表达；
       外部请求；
       当前会话输入；
       已确认服务目标；
       服务动作执行后的结果缺口；
       或根特征自检中有明确因果定义支撑的服务缺口。

2. 有目标语义：
       目标宿主；
       目标特征；
       当前状态；
       目标状态；
       满足关系。

3. 有获取或推进路径：
       已有事实读取路径；
       观察 / 会话 / 外部输入承接路径；
       方法路径；
       因果路径；
       或明确等待外部输入的挂起条件。

4. 能参与闭环：
       该节点的满足结果能够支持服务目标验证、服务动作执行、服务结果归因或下一轮服务状态判断。
```

不满足上述准入条件的节点，不得作为当前主动服务子需求。

## 6. 部分因果链与节点移出

当前工程可以只补部分因果链。不能为了凑完整链条而伪造服务节点、伪造方法、伪造观察样本或伪造动作动态。

当只有部分服务因果链可实现时：

```text
已具备因果链的节点：
    可以进入服务链、需求树和任务链。

尚无因果链的节点：
    不写入服务值定义必要条件集；
    从当前主动需求队列移出；
    不作为当前计划阻塞项；
    保留术语、特征定义和未来恢复条件。
```

这里的“移出 / 删除”只针对：

```text
服务值定义中的旧固定上下文条件；
自动入树的服务子需求；
主动任务队列中的裸服务链节点。
```

不得因此删除：

```text
特征定义；
语素入口；
历史日志；
未来服务上下文可能使用的事实字段。
```

## 7. 当前交互者与权限者边界

`当前交互者明确状态`、`当前权限者明确状态` 不得作为服务值定义的启动必要条件。

它们只有在以下场景中进入服务因果链：

```text
1. 当前存在服务事件或当前会话输入。
2. 本次服务目标需要区分交互者、服务对象、授权者或权限者。
3. 多人、代理请求、授权冲突、权限边界或服务责任归因需要这些事实。
4. 已有获取路径，例如会话上下文、外部输入事实、观察事实、权限关系或明确等待外部输入。
```

没有服务事件、没有服务目标、没有外部输入，也没有权限冲突时，`当前交互者明确状态` 只能记录为当前上下文为空或等待外部输入，不得自动生成主动需求。

## 8. 方法头创建边界

有目标时可以创建或复用方法头，但必须先确认该目标属于方法能力补齐范围。

允许创建或复用方法头的情况：

```text
1. 目标已经有因果链证明必须由自我动作能力达成。
2. 目标是普通可任务化目标。
3. 目标宿主、目标特征、当前状态、目标状态和满足关系明确。
4. 后续缺口可以落到动作入口、条件节点、结果节点、条件结果对、参数绑定或方法状态。
```

不得直接创建方法头的情况：

```text
1. 缺的是服务事件、当前会话、外部输入或观察事实本身。
2. 缺的是上游因果链，而不是方法能力。
3. 目标节点尚无服务 / 生存闭环位置。
4. 节点只是启动期固定列表中的裸必要条件。
```

此时应返回事实缺失、路径缺失或等待外部输入回执；若对应节点没有因果链支撑，应从当前主动服务链移出。

## 9. 结算与验收硬规则

服务 / 生存闭环不得用以下内容替代：

```text
1. 控制面板展示。
2. 只读摘要。
3. 初始化字段存在。
4. 方法头存在。
5. 任务创建成功。
6. 方法执行成功但无结果事实。
7. 结果事实存在但无验证。
8. 服务结果存在但不可归因于自我动作。
```

最小硬规则：

```text
没有动作，不结算。
没有结果事实，不结算。
没有验证，不结算。
没有归因，不结算服务。
没有回写下一轮状态，不算闭环。
```

安全值 / 服务值正式结算仍以 060004《安全服务值结算规范20260518》为准。

## 10. 对下级规范和计划的约束

后续修订服务链、需求树、任务筹办和结算相关规范时，应遵守：

```text
1. 所有当前主动因果链，必须最终可追溯到自我觉醒根闭环。
2. 不得从定义词条、固定节点清单、初始化字段、控制面板状态或方法头存在，直接生成当前主动需求。
3. 服务根需求可以初始化，但服务上下文字段不得自动成为当前主动任务。
4. 服务因果链上下文缺口必须先有服务触发事实、闭环位置和因果链准入，再入树、任务化或创建方法头。
5. 当前只具备部分因果链时，只推进已具备因果链的节点。
6. 缺因果链节点应从当前主动链移出，等待服务事件、权限模型、交互模型或验证模型成熟后恢复。
7. 服务对象外在状态改善型子需求是服务值结算的核心事实来源。
8. 当前交互者、权限者只在服务事件需要身份、授权或责任归因时进入链条。
9. 生存链和服务链都必须回写到下一轮自我状态判断，才能称为闭环。
10. 安全感知需求来自安全根控制因果链中的物理安全独占候选叠乘约束、风险安全或场景影响缺口，不得退回固定安全必要条件清单，也不得把场景安全度当成安全值事实。
11. 服务感知需求来自服务因果链中的对象、目标、当前状态、结果验证和归因缺口；没有接受事实、反馈或状态改善证据时，不得默认服务成功。服务对象已接受且反馈窗口内无负反馈时，只能保守评价为可以 / 可接受，不得默认很好、优秀或满分。
```

需求入树前必须能回答：

```text
该事实为何与自我有关？
该缺口为何阻断自我生存或服务闭环？
该缺口是否可由自我动作、等待事实或外部输入推进？
推进结果如何验证？
验证结果如何归因？
归因结果如何回写下一轮自我状态？
```

压缩硬规则：

```text
无觉醒，不成因果；
无自我位置，不成需求；
无闭环位置，不入树；
无验证回写，不算闭合。
```
