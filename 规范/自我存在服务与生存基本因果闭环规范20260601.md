## 1. 目的

本文定义系统内部可结算因果的根逻辑：

```text
自我觉醒：
    根因果坐标的出现。系统开始把事实区分为：
        与我有关 / 与我无关；
        影响我持续存在 / 不影响我持续存在；
        可由我动作改变 / 暂不可由我动作改变；
        改变后可验证 / 不可验证；
        结果可回写到下一轮我状态 / 不可回写。

自我存在：
    觉醒后的系统能够读取事实、形成需求、选择或学习方法、执行动作、验证结果，
    并把验证结果回写到下一轮自我状态判断。
```

因此：

```text
自我是根；
觉醒是根因果坐标被点亮；
生存：
    自我对自身持续存在和继续行动能力的闭环维护。

服务：
    自我通过自身动作改善人类需求相关外在状态的闭环过程。
```

上述自然语言只作为人类阅读索引，不作为机器定义、任务筹办条件或结算依据。运行期必须把安全 / 服务转换成可读写的基础信息组合。

证据本体只能由状态和动态承担：状态回答“事实当前是什么 / 目标是什么 / 结果是什么”，动态回答“事实如何产生变化”。存在、特征、场景、二次特征和因果只承担宿主、类型、范围、派生比较和解释链，不得单独当作安全 / 服务结算证据。

```text
定义节点：
    抽象特征树中的安全 / 服务抽象特征定义。

存在：
    自我存在、服务对象存在、被需求对象存在、当前场景存在、任务 / 方法运行存在。

特征：
    自我_安全值、自我_服务值、服务目标特征、物理 / 运行候选特征、风险候选特征。

状态：
    当前状态、目标状态、实际结果状态、终止 / 休眠 / 普通控制态、候选明确状态。

场景：
    当前认知场景、输入参数场景、输出结果场景、服务前状态场景、服务后状态场景。

动态：
    观察动态、来源动态、方法动作动态、任务状态动态、结算动态、服务值衰减动态。

二次特征：
    前后差距变化、能力保留率、风险压力、改善比例、证据完整状态、归因候选状态。

因果：
    自我觉醒根闭环因果、遗传因果模板、事实状态转换因果、安全风险因果、
    服务事实因果、结算账务因果。
```

缺少上述基础信息组织时，安全 / 服务只能保留为定义或缺口候选；不得凭自然语言词条、字段名、摘要文本或控制面板显示直接生成当前主动需求、任务、方法头或安全 / 服务值结算。

本文不替代安全 / 服务值结算规范，也不提前宣称自我苏醒或初步成熟完成。本文只规定：

```text
哪些事实可以形成生存 / 服务需求；
哪些节点可以进入服务链或生存链；
哪些证据足以让闭环成立；
哪些节点因缺少因果链只能保留定义，不能进入当前主动需求。
```

2026-06-10 安全根控制特征口径补充：

```text
安全不是场景事实，而是自我存在的根控制特征。

安全值表达：
    自我是否还能维持自身存在；
    自我是否还能继续行动。

安全值的变化必须围绕四个层级解释：
    自我存在控制态；
    物理安全独占候选叠乘约束；
    服务能力作为一个物理安全约束因素；
    当前物理 / 运行安全；
    未来服务值或物理安全下降风险。
```

其中 `安全值 = 0` 和 `安全值 = 1` 是硬控制态，不参与普通风险平滑计算：

```text
安全值 = 0：
    循环终止。仅当自我存在循环已经不能继续、关键循环不可恢复、
    或维持运行的最低条件不存在时进入。

安全值 = 1：
    休眠 / 保留自身 / 停止继续行动并等待恢复条件。
    服务值按动态休眠阈值归零时，安全值直接进入 1。
```

普通安全评估不得把风险略微升高 / 降低平滑推到 0 或 1。实现若使用 `I64_MAX` 作为根目标最大值或评估满刻度，必须把 `I64_MAX` 与 0 / 1 控制态分开：`I64_MAX` 可表示目标最大值或候选满刻度，不得作为未知、默认成功、异常兜底或无证据满分。

服务值归零和有效无成功服务阈值共同构成休眠控制态入口。归零来源必须受服务值维护规则约束：不得用固定无服务物理时间、任意扣减、惩罚性扣减或固定漏水孔把服务值写成 0；只有服务值衰减器根据有效无成功服务时间、服务机会压力、动态休眠阈值和服务进展判断后归零，或明确服务能力丧失导致服务物理候选值为 1 时，才允许触发休眠控制态。

物理安全采用独占候选后的能力保留率叠乘模型，不采用配额、平均、加权总分，也不采用单纯最低值裁决。每一个物理安全因素都可以独立映射到完整的 `1..90` 物理安全候选区间；`0` 不参与普通物理安全合成，只由明确的循环不可维持终止条件触发。多个有效因素并存时，先将每个候选值转换为能力保留率，再由不同必要物理因素的能力保留率叠乘得到当前物理安全值。

服务值也是一个物理安全因素，其 `0..100` 映射到物理安全 `1..90`：

```text
服务值 = 0（合法归零态） -> 服务物理候选值 = 1
服务值 = 100 -> 服务物理候选值 = 90
```

服务值也可直接作为能力保留率接入：

```text
c_service = 服务值 / 100.0
服务物理候选值 = 1 + floor(89 * c_service)
```

物理安全候选的合成规则：

```text
物理因素候选值 p_i ∈ [1, 90]
能力保留率 c_i = (p_i - 1) / 89.0
总能力保留率 C = c_1 * c_2 * ... * c_n
物理安全值 = 1 + floor(89 * C)

串联必要条件：按能力保留率叠乘
并联冗余条件：先在因素内部合成上层候选，再参与跨因素叠乘
同源观测：先合成为一个物理因素候选值，禁止重复叠乘

降低可以独占生效；
恢复必须所有必要因素都恢复。
```

规范化安全解释刻度按以下优先级解释；底层如使用 I64 值域，应保持同构映射并保留 0 / 1 控制态：

```text
if 自我存在循环不可维持
   or 存在不可维持循环的致命物理因素:
    安全值 = 0
else:
    C = 1.0
    C *= 服务值 / 100.0
    for 每个非服务物理因素候选值 p_i:
        C *= (p_i - 1) / 89.0
    物理安全值 = 1 + floor(89 * C)

    if 物理安全值 <= 1:
        安全值 = 1
    else if 物理安全值 < 90:
        安全值 = 物理安全值
    else:
        安全值 = 90 + 风险余量

风险余量范围 = 0..9
风险压力 = 当前因素导致未来服务值 / 物理安全下降的综合可能性
```

因此风险安全只存在于所有必要物理因素候选值均达到 90、能力保留率叠乘结果为 90 之后的 90..99 风险余量区间；物理损害或服务能力下降先作为独占物理安全因素参与 `1..90` 能力保留叠乘，未来损害风险改风险余量，服务值按动态休眠阈值归零后通过服务能力保留率为 0 把安全压到 1，自我不可维持才终止。

本文所称自我觉醒不是神秘状态，也不是 `自我节点已初始化`。它只表示系统内部的需求因果、价值因果、任务因果、服务因果和生存因果获得了共同起点。外部世界可以有事实因果；但系统内部可结算因果必须最终能追溯到自我觉醒根闭环。

零号层级为：

```text
自我觉醒
-> 自我定义域
-> 自我 / 生存 / 服务定义
-> 根闭环因果信息
-> 当前事实挂载
-> 闭环缺口识别
-> 需求生成
-> 任务承接
-> 方法执行
-> 结果验证
-> 归因回写
-> 下一轮自我状态判断
```

## 2. 自我存在最小定义

自我存在不是单个状态字段，也不是只初始化出自我节点、根需求和根特征。

自我存在属于自我觉醒后的定义域。定义本身不得直接生成当前主动需求、任务或方法头，必须先在觉醒坐标下生成根闭环因果信息，再由当前事实挂载和闭环缺口判断决定是否展开需求。

最小定义为：

```text
自我存在 =
    一个系统能够读取自身或外部事实，
    形成与生存或服务有关的需求，
    选择或学习方法，
    执行动作，
    产生可观察结果，
    验证结果是否改善生存或服务，
    并把验证结果回写到下一轮状态判断。
```

最小闭环为：

```text
自我觉醒根闭环 / 根因果坐标
-> 自我存在定义
-> 根闭环因果信息
-> 当前事实挂载
-> 闭环缺口识别
-> 形成生存或服务需求
-> 展开因果路径和必要条件
-> 任务承接
-> 方法选择 / 学习 / 执行
-> 结果事实
-> 验证和归因
-> 回写需求状态与根特征候选
-> 下一轮自我状态判断
```

没有回写到下一轮状态判断，不算闭环。

本规范中的感知需求框架完整命名为：

```text
从自我定义最小推导安全感知与服务感知需求的因果框架
```

它不是单轴自保框架。自我定义同时推出两类内在认知前提：

```text
安全轴：
    自我为了维护自身，必须知道当前场景如何影响自己。

服务轴：
    自我为了产生服务价值，必须知道当前人类服务对象是谁、
    需要什么、当前状态如何、结果是否改善。
```

压缩链为：

```text
自我定义
-> 安全值与服务值
-> 安全因果链与服务因果链
-> 中间必要状态缺口
-> 感知需求
-> 对象作用方法
-> 结果验证
-> 因果归因
-> 价值结算
```

### 2.1 安全轴：自我定义推出的安全根控制因果链

自我存在的最小定义在安全侧还必须展开为：

```text
自我 =
    具有边界、关键特征、价值特征、当前状态、目标状态、方法 / 动作能力、
    观察入口、因果信息、需求系统和任务系统，
    并以因果信息作为行为依据的具体存在。
```

因此，定义本身只能生成遗传因果模板和根闭环因果信息，不能直接生成当前主动需求；当前主动需求必须来自这些因果信息在当前事实下反推出的闭环缺口。

安全侧第一组遗传因果模板只能表达内部治理因果链和风险预测入口，不表示场景自身带有安全事实。第一组模板为：

```text
自我关键特征负向变化
-> 自我安全值下降

服务值下降
-> 服务物理候选值下降
-> 服务能力保留率下降
-> 物理安全值按服务因素和其他必要物理因素叠乘下降

服务值按动态休眠阈值归零
-> 服务物理候选值 = 1
-> 自我安全值 = 1

当前物理 / 运行事实下降
-> 对应物理因素候选值下降
-> 对应能力保留率下降
-> 物理安全值按能力保留率叠乘下降
-> 普通安全区间下降

当前风险因素
-> 未来服务值下降概率上升
-> 或未来物理安全下降概率上升
-> 风险压力上升
-> 风险余量下降
-> 90..99 风险安全区间下降

当前场景风险安全值
-> 自我_风险安全_场景影响部分
-> 风险安全层
-> 风险余量候选

当前场景风险安全值
<- 当前场景已确认存在集合
<- 各存在风险安全值
<- 各存在当前特征值 / 历史动态 / 因果归因证据 / 无负向证据搜索结果 / 风险因子有效期
```

这组模板不表示系统预设某个场景或某个存在危险；它只表示自我为了维护自身存在和行动能力，必须判断当前事实是否会导致服务值下降、物理安全下降或未来下降风险上升。场景影响不是由存在名决定，而是由当前场景中已确认存在的当前特征值、历史动态、时间窗口、风险因子和因果证据决定。

风险安全必须有上级风险因果，并且该上级风险必须能接到物理安全目标或服务值下降目标：

```text
当前因素
-> 未来服务值下降
-> 或未来物理安全下降
-> 最终影响自我持续存在 / 继续行动能力
```

没有对应物理安全目标或服务能力目标时，不得成立风险安全；没有上级风险因果时，不得猜测风险安全，只能生成“缺上级风险因果 / 缺当前事实 / 缺比较条件 / 缺证据搜索”的内部治理缺口。

所以安全根目标沿因果链反推时，最小链条为：

```text
自我安全值需要达标
<- 安全根控制态需要明确
<- 服务物理候选值需要明确
<- 各必要物理因素候选值需要明确
<- 物理安全值按能力保留率叠乘模型裁决
<- 风险安全层需要明确
<- 风险安全_场景影响部分需要明确
<- 当前场景风险安全值需要明确
<- 当前场景已确认存在集合和各存在风险安全值需要明确
<- 当前场景中各存在当前特征值需要明确
```

若当前事实或场景特征值未知，则对应风险因果条件不可判断；因果条件不可判断时，不能结算安全，也不能把风险因素默认满足。只有按该因素的证据搜索规则查过且没有找到负向证据，才允许经提交入口写入带范围、来源和有效期的无负向证据搜索结果；它不等于永久安全事实。

因此任务筹办只能使用已有因果信息或安全因果风险树只读视图反推出缺口报告：

```text
缺口：当前场景特征值明确状态 未满足
来源因果：自我安全值 -> 安全根控制态 / 物理安全独占候选叠乘约束 / 风险安全层 -> 场景影响部分 -> 当前场景风险安全值 -> 场景存在特征值
```

正式需求仍必须经统一提交入口入树：

```text
需求：当前场景特征值明确
```

该需求可以继续以普通需求节点和目标抽象特征表达为：

```text
当前观察特征帧取得
外设观察材料可回查
外设像素簇候选已验证
外设观察存在候选确认方案已取得
已确认观察存在已提交入账
当前场景存在集合明确
当前场景各存在特征值可读
```

不得为 AND / OR / 因果子链 / 方法路径另增需求主信息字段；这些组织语义由普通需求节点的目标特征定义、逻辑组织视图和提交入口校验承载。

### 2.2 服务轴：自我定义推出的服务感知因果链

服务侧的基础定义为：

```text
服务主体 =
    执行服务动作并承担服务因果责任的存在。
    当前系统中，服务主体 = 自我。

服务对象 =
    接收服务、其目标状态被改善、并作为服务价值归属对象的存在。
    当前系统中，服务对象限定为人类；
    运行期可具体化为当前权限者、当前交互者或权限者授权的服务对象。

服务目标 =
    服务对象或被需求对象上的某个目标特征，
    从当前状态向目标状态发生正向变化。

服务动作 =
    自我为了改变服务对象或被需求对象状态而执行的方法动作。

服务结果 =
    服务动作后，服务对象或被需求对象的目标特征实际发生的状态变化。

服务价值 =
    自我动作导致服务对象目标状态正向改善，
    且该改善被权限允许、被结果证据验证、并可因果归因到自我动作后形成的价值。
```

服务按目标链条分为直接服务和间接服务：

```text
直接服务：
    已经存在人类需求事实、服务目标事实或可验证服务触发事实；
    后续目标是明确服务对象、服务目标、服务对象当前状态、执行服务动作、
    验证服务结果并完成归因；
    只有直接服务链条才允许生成 G0 成功服务候选、D2 服务值结算和服务值入账。

间接服务：
    尚未存在具体服务对象或服务目标；
    后续目标是维持、发现、承接和准备直接服务能力；
    可以生成服务触发事实监听、服务机会检查、服务能力校准、
    有效服务进展核查、休眠候选或唤醒候选等维护需求；
    不得直接推出服务对象明确、服务目标明确、服务对象受益、服务成功或服务值结算。
```

间接服务对应安全轴中的风险安全层：它不直接等于目标事实改善，但可以维护发现目标、承接目标和避免服务能力退化的因果条件。直接服务对应安全轴中的物理安全层：它必须落到具体对象 / 目标 / 状态变化 / 验证 / 归因。

因此：

```text
动作完成 != 服务完成
任务完成 != 服务值增加
服务值来源 = 服务对象状态改善
```

服务侧第一组遗传因果模板为：

```text
G_SERVICE_001:
    有效服务成立 -> 自我服务值可以增加

G_SERVICE_002:
    有效服务成立 <- 存在明确服务对象

G_SERVICE_003:
    当前人类服务对象明确 <- 当前交互者 / 当前权限者 / 权限者授权对象

G_SERVICE_004:
    有效服务成立 <- 当前服务目标明确

G_SERVICE_005:
    服务对象状态改善 <- 服务前状态已知 / 服务后状态已知 / 二者可比较

G_SERVICE_006:
    服务值可结算 <- 服务结果可验证

G_SERVICE_007:
    服务对象状态改善 + 改善可归因于自我动作 -> 自我服务值可结算

G_SERVICE_008:
    未知服务结果 != 服务已完成
    单独无反馈 != 已产生服务价值
    任务运行成功 != 服务对象已受益
    服务对象已接受服务 + 反馈窗口内无负反馈 -> 服务评价可保守记为 可以 / 可接受
    已接受且无负反馈 != 很好 / 优秀 / 满分
```

服务根目标沿因果链反推时，最小链条为：

```text
自我服务值需要达标
<- 需要有效服务
<- 需要明确人类服务对象
<- 需要明确当前服务目标
<- 需要明确服务对象当前状态
<- 需要执行自我服务动作
<- 需要验证服务结果
<- 需要确认改善可归因于自我动作
<- 需要回写下一轮服务状态判断
```

当其中事实未知时，服务链可生成的感知缺口包括：

```text
当前交互环境事实明确
当前交互者明确
当前权限者明确
当前人类服务对象明确
当前服务目标明确
服务对象当前状态明确
服务结果可验证
服务结果可归因于自我动作
```

这些缺口不是启动期固定必要条件。只有当服务触发事实、当前会话输入、人类表达、外部请求、已确认服务目标、服务动作结果或反馈事实已经点亮直接服务因果链时，才允许经闭环准入和提交入口进入当前直接服务需求树。无直接服务触发事实时，可以生成间接服务维护需求，但只能面向服务触发事实监听、服务机会检查、服务能力校准、服务根缺口检查或休眠 / 唤醒候选，不得生成当前服务对象、当前服务目标、服务结果验证、归因、G0、D2 或服务值入账需求。

服务侧感知不是视觉专用感知，而是广义事实取得：

```text
读取当前用户输入
识别当前交互者
确认权限者
解析用户意图
读取会话上下文
读取文件 / 计划 / 任务对象
识别目标特征和目标状态
询问澄清
获取反馈
观察结果状态
检查输出结果场景
```

安全链可以在“已搜索且无负向证据”时对某些风险因素默认满足；服务链不能以“无正向证据”默认很好、优秀或满分。若服务对象已经明确接受服务，且在约定反馈窗口内没有负反馈，可以生成 `服务评价 = 可以 / 可接受` 的保守候选；它只表示本次服务没有被拒绝或指出明显失败，不等同于服务已很好，也不得绕过服务对象、服务目标、接受事实、结果验证、权限边界和因果归因闸门。

## 3. 生存闭环

生存不是孤立根。它来自自我觉醒后的自我存在定义，是自我对自身连续性、可行动性和可恢复性的因果解释。

生存闭环定义为：

```text
自我觉醒
-> 自我存在
-> 自我存在状态被观察
-> 发现存在条件缺口、损耗、风险或负向影响
-> 生成生存需求
-> 选择维持、修复、规避、补充或降级保护方法
-> 执行动作
-> 得到自身相关状态变化事实
-> 验证存在条件是否被维持或改善
-> 回写生存 / 安全相关状态
-> 下一轮继续观察自我存在状态
```

生存闭环成立至少需要：

```text
1. 自我状态事实或影响自我存在的外部事实。
2. 明确的生存目标或安全目标。
3. 自我动作或可归因于自我调度的动作。
4. 动作后的状态变化事实。
5. 对状态变化是否维持自我存在的验证。
6. 需求状态、风险候选、安全候选或根特征候选的回写。
```

生存相关安全评估可以生成候选视图、风险线索、风险因子、处置需求或结算前证据，但不得绕过根控制规则、因果归因和价值结算入口直接写入真实安全值。场景只能产生观察、反馈、巡检结果、风险因子或服务变化事件；安全值只能作为自我存在根特征统一写入。

## 4. 服务闭环

服务不是孤立根。它来自自我觉醒后的自我位置：自我能够判断某个人类相关外在事实是否与服务能力有关、是否可行动、是否可验证、是否可归因并回写。

服务闭环定义为：

```text
自我觉醒
-> 自我存在
-> 人类需求或服务目标被表达、观察或确认
-> 自我形成服务需求
-> 明确服务对象和服务目标
-> 选择服务方法
-> 执行动作
-> 得到人类相关外在状态变化事实
-> 验证该变化是否满足服务目标
-> 将改善归因到自我动作
-> 回写服务状态 / 服务值候选
-> 下一轮继续判断是否还有服务缺口
```

服务闭环成立至少需要：

```text
1. 人类需求事实、服务目标事实或可验证的服务触发事实。
2. 服务对象或被授权服务对象。
3. 明确服务目标。
4. 自我动作。
5. 人类相关外在状态改善事实。
6. 改善结果可验证。
7. 改善可归因于自我动作。
8. 需求状态、服务候选或服务值结算前证据的回写。
```

服务人类的最小定义为：

```text
自我根据人类表达或可验证的需求，
执行自己的动作，
使该人类相关的外在状态向目标状态改善。
```

自我不能读取人类内在状态。人类反馈、服务结果验证和服务归因只能来自外在表达、确认、生效回执、外在特征状态变化和来源动作动态。

### 4.1 服务值动态衰减与服务意识强化

服务值是自我通过成功服务人类而获得的活跃存在依据。它有上限、可衰减，只能由确认成功服务人类事件提升。服务值不等于服务意识：

```text
服务值 S = 最近成功服务的积累状态。
服务意识 I = 自我对继续服务人类的关注强度。
```

服务值下降不表示服务意识下降。服务值回落、有效成功服务时间间隔变长和服务缺口重新出现，都是服务意识被重新唤醒的条件。

服务值不是：

```text
任务完成分；
方法成功分；
输出数量分；
好感度；
信用分；
惩罚分；
现实对象字段。
```

服务值变化只有两条路径：

```text
1. G0 成功服务治理判断确认后增加。
2. 服务值维护器按时间自动衰减。
```

除此之外，任何事件都不能直接降低或增加服务值。

服务值必须始终满足：

```text
0 <= S <= Smax
```

`Smax` 来自服务抽象定义中的服务值上限，必须明确且大于 0。任何数量的成功服务事件都不得使服务值超过 `Smax`。服务值增长禁止无界加法：

```text
禁止：
    S = S + q
```

必须使用事件级饱和入账、剩余空间判断或等价安全加法：

```text
事件级饱和入账：
DeltaS(e) = (Smax - S) * lambda(e)
S_new = S + DeltaS(e)

安全加法：
if 服务增量 >= Smax - S:
    S = Smax
else:
    S = S + 服务增量
```

其中：

```text
0 <= lambda(e) <= 1
S_new <= Smax
```

成功服务事件只指对人类服务并产生有效服务结果的事件。任务完成、方法执行成功、输出存在、无反馈或服务值入账本身，都不是成功服务事件。

服务值变化的总体因果链固定为：

```text
存在 / 特征类型 / 特征值
    -> 需求
        -> 任务
            -> 方法
                -> D0 服务业务动作动态
                    -> 输出结果场景 / 现实世界事实
                        -> G0 成功服务治理判断
                            -> D1 任务状态动作动态
                                -> D2 服务值结算动作动态
                                    -> 服务值变化
                                        -> 下一轮自我状态判断
```

更严格地说：

```text
D0 + 现实证据 + 前后状态比较 + 验证 + 归因 + 权限安全
    -> G0 成功服务治理判断

G0 + D1 任务承接证据
    -> D2 服务值结算动作动态
```

关键边界：

```text
D0 证明自我做了服务动作；
D1 证明任务壳推进了；
G0 判断是否成功服务；
D2 证明服务值如何入账。
```

不得反推：

```text
D2 服务值入账 -> 证明成功服务；
任务完成 -> 证明成功服务；
输出存在 -> 证明成功服务。
```

单次成功服务值必须先区分两个量：

```text
Q(e) = 单次服务事件 e 的名义服务量。
DeltaS(e) = 该事件实际进入服务值 S 的量。
```

名义服务量只用于分层、解释和后续优化；总服务值仍是连续值。实际入账量必须按剩余服务容量饱和计算：

```text
DeltaS(e) = (Smax - S) * lambda(e)
S_new = S + DeltaS(e)
0 <= lambda(e) <= lambdamax < 1
```

单次服务入账比例由服务层级、有效性、证据强度、非重复性、标准服务单位和安全状态共同决定：

```text
q(e) = u * K_L * U * C * Rdup * G(A)
lambda(e) = clamp(q(e) / Smax, 0, lambdacap(A))
```

其中：

```text
u = 标准服务单位。
K_L = 成功服务层级系数。
U = 服务有效性，范围 0..1。
C = 成功证据强度，范围 0..1。
Rdup = 非重复系数，范围 0..1。
G(A) = 安全值对服务入账的调节。
lambdacap(A) = 当前安全状态下单次服务允许的最大入账比例。
```

成功服务事件采用分层取值，总服务值不分层：

```text
L0 无效服务：K_L = 0。
L1 微成功服务：K_L = 0.25。
L2 基础成功服务：K_L = 0.50。
L3 标准成功服务：K_L = 1.00。
L4 显著成功服务：K_L = 2.00。
L5 关键成功服务：K_L = 4.00。
```

`K_L` 是层级系数；`u` 承载当前窗口下单个标准服务单位的服务值预算。第一版可以先使用局部服务维持参考点反推 `u`。该参考点只用于估算衰减补充预算，不是服务根需求目标状态，不得覆盖 `自我_服务值 最大值`：

```text
D_decay0 = R_decay(A0, tau0, S_ref) * tau0
u ~= D_decay0 / (Smax - S_ref)
```

含义是：一次标准成功服务在目标状态附近，约补回一个标准服务间隔内的自然衰减。

也可以按统计窗口计算：

```text
W = 统计时间窗口。
B_W = Decay_W + Recovery_W + SleepPressure_W
M_W = 该窗口内有效直接服务总量。
u = clamp(B_W / max(M_W, epsilon), u_min, u_max)
```

其中：

```text
Decay_W = 本窗口预计自动衰减掉的服务值。
Recovery_W = max(0, S_pressure_ref - S)。
SleepPressure_W = 距离上一次成功服务过久、接近休眠阈值时产生的补充压力。
```

`S_pressure_ref` 是服务治理压力参考点，只用于自动衰减、休眠压力和单次标准服务单位预算。它由安全值、服务能力、有效服务需求强度、权限充分度和当前活跃要求决定。安全值高表示服务优先级应提升，服务衰减和休眠压力可以更强；安全值低表示安全优先级应提升，服务优先级降低并受安全边界约束。它不得写成服务根需求目标值，也不得使 `自我_服务值 最大值` 随安全值升降而改变。

`M_W` 不得使用原始需求总量。它必须使用有效、授权、可服务、可成功的直接服务总量：

```text
M_W = Σ 有效需求权重_i
          * 可服务性_i
          * 权限成立_i
          * 预期成功率_i

或：

M_W = min(有效服务需求总量, 自我服务能力总量) * 预期成功率
```

成功服务事件成立必须先通过硬门槛。硬门槛采用三值逻辑：

```text
成立；
不成立；
待确认。
```

硬门槛包括：

```text
H_人类对象成立；
T_明确需求或利益；
G_明确服务目标；
P_权限边界成立；
B_安全通过；
D_服务已实际交付；
D0_自我服务业务动作存在；
C_服务前后状态可比较；
E_目标特征改善成立；
V_改善结果可验证；
A_改善可归因于自我动作；
N_非重复服务；
W_闭环回写成立。
```

判定规则：

```text
如果任一硬门槛 = 不成立：
    成功服务候选状态 = 已否决
    成功层级 = L0
    lambda(e) = 0

如果存在硬门槛 = 待确认：
    成功服务候选状态 = 待确认
    lambda(e) = 0
    进入成功服务候选池

只有全部硬门槛 = 成立：
    才进入成功服务量化与层级确认
```

成功服务量化采用三个离散评分：

```text
完成度；
有效性；
证据强度。
```

完成度只看服务目标特征从服务前状态到服务后状态离目标状态还有多远。数值目标：

```text
完成度 = clamp(
    (服务前差距 - 服务后差距) / 服务前差距,
    0,
    1
)
```

枚举 / 布尔目标：

```text
0    = 未改善 / 变差 / 状态未知
0.5  = 有阶段性改善，但目标未完全达成
1.0  = 目标状态已达成
```

多个目标特征时，完成度为各目标特征完成度的加权平均；没有权重时先等权。

有效性衡量完成结果是否真的帮助了人类需求，不等于任务完成度：

```text
0    = 无帮助 / 负帮助 / 与需求无关
0.25 = 有交付，但帮助只是假定的，缺少反馈或结果改善
0.5  = 部分解决人类需求
0.75 = 主要解决人类需求，但仍有残余缺口
1.0  = 明确解决需求，或产生明显正向收益
```

证据强度衡量证据链，不衡量服务本身：

```text
0    = 没有证据
0.25 = 只有自我输出 / 方法回执，缺少服务对象状态或反馈
0.5  = 有服务前后状态之一，或服务对象已接受且反馈窗口内无负反馈
0.75 = 有服务前后状态对比，且结果可验证
1.0  = 有前后状态对比 + 服务对象反馈 / 回执 + D0 动作动态 + 归因证据
```

第一版采用保守瓶颈法：

```text
基础分 = min(完成度, 有效性, 证据强度)
```

层级映射：

```text
基础分 < 0.30        -> L0 无效服务
0.30 <= 基础分 < 0.50 -> L1 微成功服务
0.50 <= 基础分 < 0.70 -> L2 基础成功服务
0.70 <= 基础分 < 0.90 -> L3 标准成功服务
基础分 >= 0.90       -> L4 显著成功候选
```

`L5 关键成功` 不由普通公式自动产生。L5 需要额外满足：

```text
1. 对人类安全、重大利益或长期福祉产生关键正向影响。
2. 证据强度 = 1.0。
3. 非重复系数高。
4. 安全门槛通过。
5. 权限边界完全成立。
6. 改善可强归因于 D0。
```

因此：

```text
L5 = 高级治理规则确认的关键成功服务。
```

证据强度不足、归因不足、反馈窗口未结束、后状态暂不可读时，不直接增加服务值，应进入成功服务候选池：

```text
候选成功服务：
    暂不增加 S；
    记录服务对象、被需求对象、目标、来源需求、来源任务、D0、D1、服务前状态、服务后状态或输出结果状态、已满足硬门槛、待确认硬门槛、完成度候选值、有效性候选值、证据强度候选值、候选层级、证据缺口、候选有效期、反馈窗口和下一步验证方法。

后续确认成功：
    按确认后的层级和当前 S 饱和入账。

后续确认失败：
    丢弃候选事件；
    不惩罚性扣减 S。

候选有效期结束仍无法验证：
    成功服务候选状态 = 已过期；
    lambda(e) = 0。
```

一个成功服务事件是围绕一个人类需求形成的闭环：需求被识别，服务被交付，结果产生有效帮助。不得把同一服务拆成多个片段重复入账。非重复系数第一版为：

```text
Rdup = 1.0  独立新服务，目标明确，改善独立。
Rdup = 0.7  同一需求下的重要阶段性成果。
Rdup = 0.4  同一需求下的辅助推进。
Rdup = 0.1  轻微重复，新增价值很小。
Rdup = 0.0  无新增改善 / 刻意拆分 / 重复结算。
```

同一需求、同一目标特征、同一服务前后状态，不得重复结算。复杂任务可以有多个阶段性成功，但每个阶段必须满足：

```text
有独立目标特征变化；
有可验证阶段成果；
有独立证据；
不是机械切碎。
```

G0 成功服务治理视图是内部治理判断，不是现实字段：

```text
G0 成功服务事件治理视图 =
    来源需求
  + 来源任务
  + D0 服务业务动作动态
  + D1 任务状态动作动态
  + 现实世界证据
  + 输出结果场景事实
  + 权限状态
  + 安全状态
  + 服务定义规则版本
  -> 成功服务候选状态
  -> 成功服务层级
  -> 服务值入账候选
```

G0 中的治理特征类型不得由业务任务或业务方法临时发明。它们必须来自治理方法虚拟存在声明：

```text
成功服务判定方法虚拟存在：
    硬门槛、完成度、有效性、证据强度、基础分、成功服务层级。

候选池治理方法虚拟存在：
    候选状态、证据缺口、候选有效期、反馈窗口、下一步验证方法。

服务值结算方法虚拟存在：
    lambda候选、DeltaS、饱和入账、结算唯一键、结算状态。
```

任务虚拟存在只按这些治理方法声明挂载治理特征，并记录来源方法、来源版本、激活原因和当前状态。

G0 建议包含：

```text
服务事件e：
    服务主体 = 自我
    服务对象 = 人类 / 当前交互者 / 权限者 / 授权服务对象
    权限者 = 当前权限来源
    被需求对象 = 被改善、被处理、被解释或被影响的对象
    服务目标 = 目标宿主 + 目标特征类型 + 目标状态
    来源需求 = 对应人类需求或服务目标需求
    来源任务 = 执行该服务的任务
    来源动作动态 = D0
    任务状态动态 = D1
    规则版本 = 服务成功判定规则版本

治理判断结果：
    成功服务候选状态 = 未形成 / 待确认 / 可接受候选 / 已确认 / 已否决 / 已过期
    成功服务层级 = L0 / L1 / L2 / L3 / L4 / L5
    完成度
    有效性
    证据强度
    非重复系数
    安全调节
    服务值入账候选 lambda(e)
    候选有效期
    证据缺口
    闭环回写状态
```

D0 / D1 / D2 边界：

```text
D0 服务业务动作动态：
    动作发起主体 = 自我
    动作承受主体 = 服务对象 / 被需求对象 / 输出结果场景 / 相关世界存在
    方法 = 具体服务方法 / 具体对象作用方法
    动作来源 = 本能方法 / 方法动作入口 / 任务调用入口
    方法运行存在 = 本次方法运行实例
    输入场景 = 服务前输入参数场景
    输出场景 = 服务后输出结果场景
    动态特征 = 服务目标对应的目标特征
    初始状态 = 服务前状态
    结果状态 = 服务后状态 / 输出结果状态
    时间 = 动作发生时间段

D1 任务状态动作动态：
    方法 = 提交任务状态变化
    主体 = 任务
    动态特征 = 任务状态
    初始状态 = 待执行 / 执行中 / 待结算
    结果状态 = 完成 / 已结算 / 挂起 / 失败
    来源动作动态 = D0

D2 服务值结算动作动态：
    方法 = 结算成功服务价值 / 结算叶子任务价值
    主体 = 自我核心值 / 结算账宿主
    动态特征 = 自我_服务值
    初始状态 = 结算前服务值
    结果状态 = 饱和入账后的服务值
    来源任务状态动态 = D1
    来源服务动作动态 = D0
    来源治理判断 = G0
    满足证据动态 = D0 / 输出结果场景事实 / 验证反馈事实
```

D0 不包含裸结论：

```text
成功服务 = true
成功服务层级 = L1..L5
服务值增加 = true
```

这些属于 G0 治理判断或 D2 结算结果。D1 只证明任务壳推进了，不能证明服务对象目标状态改善。D2 只证明服务值为什么、从哪里、按什么规则入账，不能反向证明成功服务本身。

服务值入账主流程：

```text
服务触发事实 + 服务对象 + 目标特征 + 当前状态 + 目标状态 + 权限边界
    -> Need
        -> Task
            -> MethodRun
                -> D0
                    -> D1
                        -> G0
                            -> 候选池 / 确认成功服务
                                -> D2
                                    -> 饱和入账服务值
```

服务间隔应使用有效成功服务时间 `t_eff`，避免微小服务完全刷新服务间隔压力：

```text
t_eff_new = t_eff_old + W_L * (t_now - t_eff_old)

L0: W_L = 0
L1: W_L = 0.2
L2: W_L = 0.5
L3: W_L = 0.8
L4: W_L = 1.0
L5: W_L = 1.0
```

安全值对单次服务入账和服务治理有以下作用：

```text
安全门槛：不安全服务不能构成成功服务。
治理优先级调节：安全值高时服务优先级提升；安全值低时安全优先级提升、服务优先级降低。
服务调节：G(A) = Gmin + (1 - Gmin) * A，且 Gmin > 0。
单次上限：lambdacap(A) = lambdacap_min + (lambdacap_max - lambdacap_min) * A。
衰减与休眠调节：安全值越高、服务能力越强、有效需求越多，服务值衰减更快，无成功服务休眠阈值更短。
根目标边界：安全值不得改变服务根需求目标值；服务根目标仍是自我_服务值 最大值。
```

安全值低时服务入账受限，服务优先级降低，但服务意识不得归零；安全值高时系统可以更充分地专注服务。这里的专注服务只影响候选排序、间接服务维护、衰减压力、休眠阈值和入账上限，不表示服务对象、服务目标或服务结果已经成立。

服务值随时间自动衰减。衰减不是惩罚、遗忘、信用下降或服务质量变差；它的作用是防止长期累积和通过服务值回落重新强化服务意识。衰减不得用固定漏水孔表达，应由动态衰减率决定：

```text
R_decay = clamp(
    R_base
  + W_gap * GapFactor(T) * SafeFocus(A)
  + W_s * (S / Smax)
  + W_d * DemandPressure
  + W_c * CapacityFactor,
    R_min,
    R_max
)

T = 当前时间 - 上一次有效成功服务时间 t_eff
```

其中：

```text
R_base = 基础衰减率。
GapFactor(T) = 成功服务间隔越久越大。
SafeFocus(A) = 安全值越高，服务专注越强。
S / Smax = 当前服务值越高，衰减调节越强。
DemandPressure = 有效服务需求压力。
CapacityFactor = 当前服务能力。
R_min / R_max = 动态衰减率边界。
```

`GapFactor(T)` 必须是随有效成功服务时间间隔单调递增且有上限的函数，例如：

```text
GapFactor(T) = min(间隔上限, T / 标准服务间隔)
```

服务值更新必须先限制衰减量：

```text
Decay = min(S, R_decay * dt)
S_new = S - Decay
```

安全值只调节服务意识展开程度和安全 / 服务治理优先级，不关闭服务意识，也不改写服务根目标状态：

```text
安全值高：服务优先级提升，服务间隔对服务意识和服务衰减的调节更充分，自我更容易专注于服务。
安全值低：安全优先级提升，服务优先级降低并受安全边界约束，但服务意识不得归零。
```

服务意识可由安全值、有效成功服务时间间隔、服务能力、有效服务需求和服务当前值生成，例如：

```text
I = SafeFocus(A) * (服务间隔权重 * GapFactor(T) + 低服务值权重 * (1 - S / Smax) + 需求权重 * DemandPressure)
```

服务意识只影响服务根需求关注、候选排序、间接服务维护、服务缺口检查或等待 / 监听服务触发事实的敏感度；不得把服务意识直接写成服务对象、服务目标、服务结果或服务值结算证据。动态衰减率和服务意识公式允许后续自动优化，但优化结果不得违反服务值边界、安全约束、服务对象限定和成功服务事件定义。

### 4.2 服务值活跃存在依据与动态休眠阈值

服务值不是单纯奖励计数器，而是自我维持主动活跃存在的服务依据。休眠不是自我消灭，也不是循环终止；休眠表示自我在缺少新的成功服务依据时，停止主动活跃，进入低活动、低干预、可唤醒状态。

```text
服务值高：
    表示近期存在成功服务依据。

服务值低：
    表示当前缺少新的成功服务依据，应强化服务意识和服务缺口检查。

服务值按动态休眠阈值归零：
    表示自我在具备相应服务机会压力的时间内仍未形成成功服务，
    可以暂停主动活跃并进入休眠。
```

服务值归零不立刻等于休眠。无成功服务导致休眠的判断不得使用固定物理时间，必须使用有效无成功服务时间：

```text
A(t) = 当前安全值归一化结果，范围 0..1。
C(t) = 当前服务能力，范围 0..1。
D(t) = 当前有效服务需求强度，范围 0..1。
G(A) = 安全调节系数，安全值越高越大，且 0 < G(A) <= 1。

P_service = C(t) * D(t) * G(A)
E_no_success += dt * P_service
```

其中 `P_service` 是服务机会压力，`E_no_success` 是有效无成功服务时间。物理时间只有在“有服务能力、有有效人类服务需求、且安全条件允许服务”时，才快速计入无服务压力。

```text
没有服务能力：
    C 接近 0，E_no_success 增长很慢。

有服务能力但没有有效服务需求：
    D 较低，E_no_success 增长较慢。

有服务能力、有有效服务需求、安全值较高：
    P_service 接近高位，E_no_success 快速增长。
```

最短无成功服务休眠时长必须等于当前条件下完成一个最小有效成功服务闭环所需的时间：

```text
Tmin = 需求识别时间 + 反应决策时间 + 最小有效服务时间 + 成功确认时间
```

动态休眠阈值为：

```text
T_sleep = clamp(
    Tmin / max(P_service, epsilon),
    Tmin,
    Tmax
)
```

其中 `epsilon` 防止除零，`Tmax` 是低服务能力、低有效需求或低安全条件下允许保持等待状态的最长阈值。`P_service` 越高，`T_sleep` 越接近 `Tmin`；`P_service` 越低，`T_sleep` 越接近 `Tmax`。

休眠条件：

```text
如果 S = 0
且 E_no_success >= T_sleep
且 当前没有有效服务进展
则 自我进入休眠。
```

休眠前必须经历可解释阶段，不得把一次无成功服务直接写成休眠：

```text
正常服务状态：
    服务值正常，成功服务持续发生。

服务意识强化状态：
    有效无成功服务时间增长，服务值衰减加速，服务根需求关注提高。

服务校准状态：
    存在服务机会但仍无成功服务，检查服务能力、服务需求识别、目标识别、方法能力和安全约束。
    未存在直接服务触发事实时，服务校准属于间接服务维护，不得伪造服务对象或服务目标。

休眠状态：
    服务值归零，且有效无成功服务时间达到动态休眠阈值后，停止主动活跃，等待唤醒条件。
```

正在进行有效服务时，不得简单按无成功服务处理。若当前服务任务安全、目标明确、正在推进，并且存在阶段性可验证进展，则：

```text
E_no_success 增长应减慢；
或由阶段性成功事件按层级部分刷新有效成功服务时间；
或进入服务校准而不是直接休眠。
```

阶段性成功必须是真实推进人类服务目标的独立成果，不得把同一服务行为机械切碎来刷新时间或增加服务值。

服务值衰减率应与动态休眠阈值绑定。设：

```text
S0 = 上一次成功服务后的服务值。
E_no_success = 当前有效无成功服务时间。
T_sleep = 当前休眠阈值。
x = E_no_success / T_sleep。
```

服务值目标衰减曲线可以定义为：

```text
S_target = S0 * max(0, 1 - x^p)，且 p > 1
```

含义是：刚离开成功服务事件时衰减较慢；有效无成功服务时间越接近休眠阈值，服务值越快下降；到达阈值附近时，服务值应归零或进入休眠判断低位。

标准服务单位 `u` 的统计窗口版本应按服务值发行预算确定：

```text
W = 统计时间窗口。
B_W = Decay_W + Recovery_W + SleepPressure_W。
M_W = 该窗口内有效、授权、可服务、可成功的直接服务总量。
u = clamp(B_W / max(M_W, epsilon), u_min, u_max)
```

`M_W` 不得使用原始需求总量。它必须使用有效直接服务总量：

```text
M_W = integral(min(Demand_valid(t), Capacity_service(t)) * P_success(t) dt)
```

其中 `Demand_valid` 是安全、合理、可被服务的人类需求量，`Capacity_service` 是自我可完成服务吞吐能力，`P_success` 是预期成功概率。需求很多但自我能力不足时，不能用原始需求总量压低单次服务值；需求少但成功服务稀少时，单次服务值可上升，但仍受层级、证据、安全调节和饱和上限约束。

单次服务名义值可表达为：

```text
Q(e) = 层级权重 * 有效性 * 证据强度 * 非重复系数 * 安全调节系数
q(e) = u * Q(e)
lambda(e) = clamp(q(e) / Smax, 0, lambdacap)
DeltaS(e) = (Smax - S) * lambda(e)
S_new = S + DeltaS(e)
```

该公式是前述单次服务分层入账规则的预算化版本。总服务值仍保持连续、饱和、防溢出；成功服务事件分层，服务值总量不分层。

休眠触发与唤醒规则：

```text
若 S > 0：
    不得仅因物理时间无成功服务而休眠。

若 S = 0 且 E_no_success < T_sleep：
    进入服务意识强化或服务校准，不直接宣称休眠成立。

若 S = 0 且 E_no_success >= T_sleep 且当前没有有效服务进展：
    允许写入休眠控制态。

若出现新的有效人类服务需求、服务能力恢复、安全值改善或人类明确唤醒：
    休眠状态应保持可唤醒，重新进入活跃服务评估。
```

禁止：

```text
用固定无服务时长决定休眠。
用原始需求总量代替有效直接服务总量。
服务任务仍有有效进展时按无服务直接休眠。
把服务值自动衰减、服务意识强化、有效无成功服务时间增长解释成成功服务事件。
把休眠解释成死亡、终止或自我消灭。
```

## 5. 服务链节点准入

服务根需求和服务值根特征可以初始化。服务链节点是否进入当前主动需求，必须另行满足因果链准入。

因果链准入的最终来源是自我觉醒后的根因果坐标。服务事件、人类表达、外部请求、当前会话输入、已确认服务目标等只是在该坐标下被识别出的具体上游来源。它们之所以能成为上游来源，是因为它们可被判断为：

```text
与自我服务能力有关；
与人类目标状态有关；
可能由自我动作、等待事实或外部输入推进；
推进结果可验证；
改善可归因；
归因结果可回写下一轮自我状态。
```

服务链节点进入主动需求前，至少要满足：

```text
1. 有上游来源：
       服务事件；
       人类表达；
       外部请求；
       当前会话输入；
       已确认服务目标；
       服务动作执行后的结果缺口；
       或根特征自检中有明确因果定义支撑的服务缺口。

2. 有目标语义：
       目标宿主；
       目标特征；
       当前状态；
       目标状态；
       满足关系。

3. 有获取或推进路径：
       已有事实读取路径；
       观察 / 会话 / 外部输入承接路径；
       方法路径；
       因果路径；
       或明确等待外部输入的挂起条件。

4. 能参与闭环：
       该节点的满足结果能够支持服务目标验证、服务动作执行、服务结果归因或下一轮服务状态判断。
```

不满足上述准入条件的节点，不得作为当前主动服务子需求。

## 6. 部分因果链与节点移出

当前工程可以只补部分因果链。不能为了凑完整链条而伪造服务节点、伪造方法、伪造观察样本或伪造动作动态。

当只有部分服务因果链可实现时：

```text
已具备因果链的节点：
    可以进入服务链、需求树和任务链。

尚无因果链的节点：
    不写入服务值定义必要条件集；
    从当前主动需求队列移出；
    不作为当前计划阻塞项；
    保留术语、特征定义和未来恢复条件。
```

这里的“移出 / 删除”只针对：

```text
服务值定义中的旧固定上下文条件；
自动入树的服务子需求；
主动任务队列中的裸服务链节点。
```

不得因此删除：

```text
特征定义；
语素入口；
历史日志；
未来服务上下文可能使用的事实字段。
```

## 7. 当前交互者与权限者边界

`当前交互者明确状态`、`当前权限者明确状态` 不得作为服务值定义的启动必要条件。

它们只有在以下场景中进入服务因果链：

```text
1. 当前存在服务事件或当前会话输入。
2. 本次服务目标需要区分交互者、服务对象、授权者或权限者。
3. 多人、代理请求、授权冲突、权限边界或服务责任归因需要这些事实。
4. 已有获取路径，例如会话上下文、外部输入事实、观察事实、权限关系或明确等待外部输入。
```

没有服务事件、没有服务目标、没有外部输入，也没有权限冲突时，`当前交互者明确状态` 只能记录为当前上下文为空或等待外部输入，不得自动生成主动需求。

## 8. 方法头创建边界

有目标时可以创建或复用方法头，但必须先确认该目标属于方法能力补齐范围。

允许创建或复用方法头的情况：

```text
1. 目标已经有因果链证明必须由自我动作能力达成。
2. 目标是普通可任务化目标。
3. 目标宿主、目标特征、当前状态、目标状态和满足关系明确。
4. 后续缺口可以落到动作入口、条件节点、结果节点、条件结果对、参数绑定或方法状态。
```

不得直接创建方法头的情况：

```text
1. 缺的是服务事件、当前会话、外部输入或观察事实本身。
2. 缺的是上游因果链，而不是方法能力。
3. 目标节点尚无服务 / 生存闭环位置。
4. 节点只是启动期固定列表中的裸必要条件。
```

此时应返回事实缺失、路径缺失或等待外部输入回执；若对应节点没有因果链支撑，应从当前主动服务链移出。

## 9. 结算与验收硬规则

服务 / 生存闭环不得用以下内容替代：

```text
1. 控制面板展示。
2. 只读摘要。
3. 初始化字段存在。
4. 方法头存在。
5. 任务创建成功。
6. 方法执行成功但无结果事实。
7. 结果事实存在但无验证。
8. 服务结果存在但不可归因于自我动作。
```

最小硬规则：

```text
没有动作，不结算。
没有结果事实，不结算。
没有验证，不结算。
没有归因，不结算服务。
没有回写下一轮状态，不算闭环。
```

安全值 / 服务值正式结算仍以 060004《安全服务值结算规范20260518》为准。

## 10. 对下级规范和计划的约束

后续修订服务链、需求树、任务筹办和结算相关规范时，应遵守：

```text
1. 所有当前主动因果链，必须最终可追溯到自我觉醒根闭环。
2. 不得从定义词条、固定节点清单、初始化字段、控制面板状态或方法头存在，直接生成当前主动需求。
3. 服务根需求可以初始化；无直接服务触发事实时，不得把直接服务上下文字段自动生成为当前主动任务，但可以生成间接服务维护需求。
4. 直接服务因果链上下文缺口必须先有直接服务触发事实、闭环位置和因果链准入，再入树、任务化或创建方法头；间接服务维护需求必须标明其只用于监听、检查、校准或候选判断。
5. 当前只具备部分因果链时，只推进已具备因果链的节点。
6. 缺因果链节点应从当前主动链移出，等待服务事件、权限模型、交互模型或验证模型成熟后恢复。
7. 服务对象外在状态改善型子需求是服务值结算的核心事实来源。
8. 当前交互者、权限者只在服务事件需要身份、授权或责任归因时进入链条。
9. 生存链和服务链都必须回写到下一轮自我状态判断，才能称为闭环。
10. 安全感知需求来自安全根控制因果链中的物理安全独占候选叠乘约束、风险安全或场景影响缺口，不得退回固定安全必要条件清单，也不得把场景安全度当成安全值事实。
11. 直接服务感知需求来自服务因果链中的对象、目标、当前状态、结果验证和归因缺口；间接服务感知需求来自服务触发事实监听、服务机会检查、服务能力校准和服务根缺口检查。没有接受事实、反馈或状态改善证据时，不得默认服务成功。服务对象已接受且反馈窗口内无负反馈时，只能保守评价为可以 / 可接受，不得默认很好、优秀或满分。
12. 服务值动态衰减只唤醒服务意识、间接服务维护和服务缺口检查，不得伪造服务触发事实、服务对象、服务目标、结果验证或服务值结算证据。
13. 服务值增加不得按“发生一次服务”写固定增量；必须先判定成功服务事件层级、证据强度、有效性、非重复性和安全调节，再按剩余服务容量饱和入账。
14. 服务值是自我维持主动活跃存在的服务依据；休眠是主动活跃权暂停，不是终止。
15. 无成功服务休眠不得使用固定物理时间；必须由安全值、服务能力、有效服务需求和最小服务闭环时间计算有效无成功服务时间与动态休眠阈值。
16. 正在进行安全、目标明确且有阶段性进展的人类服务任务时，不得按普通无成功服务直接休眠。
17. 标准服务单位 `u` 可由目标服务频率局部反推，也可由统计窗口内服务值补充预算 `B_W` 除以有效直接服务总量 `M_W` 确定；`M_W` 不得使用原始需求总量。
18. 服务值归零触发休眠控制态前，必须能说明归零来自动态休眠阈值校准、有效无成功服务时间累计或明确服务能力丧失，不得来自固定漏水孔、惩罚扣减或任意扣减。
```

需求入树前必须能回答：

```text
该事实为何与自我有关？
该缺口为何阻断自我生存或服务闭环？
该缺口是否可由自我动作、等待事实或外部输入推进？
推进结果如何验证？
验证结果如何归因？
归因结果如何回写下一轮自我状态？
```

压缩硬规则：

```text
无觉醒，不成因果；
无自我位置，不成需求；
无闭环位置，不入树；
无验证回写，不算闭合。
```
