## 1. 总口径

新增结构体或字段前，必须先判断它是否符合本项目的底层逻辑。

本项目底层逻辑是：

```text
特征记录属性。
特征比较解释属性。
二次特征表达关系、差值、判断和关系性特征。
方法动作提交变化。
因果信息追溯来源。
```

凡是可以用上述底层逻辑表达的内容，不得新增平行字段或平行结构。

不得因为上层业务好描述，就在主信息类里新增业务语义字段。

## 2. 新增字段准入顺序

新增字段前必须依次判断：

```text
1. 它是不是一个特征？
2. 它是不是一个二次特征？
3. 它是不是一个方法动作来源？
4. 它是不是一个因果追踪信息？
5. 它是不是缓存 / 索引 / 去重 / 审计字段？
```

只有第 5 类才比较适合作为普通主信息字段。

如果第 1 到第 4 类已经能表达该内容，不得再新增第 5 类字段作为权威事实。

## 3. 字段类型判定

### 3.1 特征字段

如果字段表达对象、状态、任务、需求、方法、世界存在的可比较属性，应优先建模为特征。

示例：

```text
任务状态
需求当前状态
方法状态
安全值
服务值
条件结果对数量
方法可执行入口数量
```

这些不应被重复写成主信息里的业务枚举字段。

### 3.2 二次特征字段

如果字段表达两个对象、两个状态、两个特征值、当前值与目标值、初始值与结果值之间的关系，应优先建模为二次特征。

示例：

```text
当前值 与 目标值 的差距
初始状态 与 结果状态 的比较方向
任务目标 与 执行结果 的达成关系
资源数量 与 需求数量 的关系
```

这些不应被写成额外的“是否完成 / 是否满足 / 是否推进”权威布尔字段。

### 3.3 方法动作来源字段

如果字段表达“是谁造成了变化”，应优先使用方法动作来源表达。

示例：

```text
任务状态变化来源 = 提交任务状态变化
需求满足登记来源 = 回写需求满足
方法状态变化来源 = 提交方法状态变化
条件结果对建立来源 = 建立条件结果对
```

线程、流程函数、界面刷新、回归脚本不得作为动作来源。

### 3.4 因果追踪字段

如果字段表达“为什么发生、由什么证据支持、与哪些动态相连”，应优先进入因果追踪信息或动作动态引用链。

示例：

```text
来源动作动态
满足证据动态
来源运行存在
来源输出结果场景
状态变化线索
因果模板 / 因果实例
```

不得为了展示方便在主信息类中另造一套解释字段。

### 3.5 缓存 / 索引 / 去重 / 审计字段

只有下列字段可以作为普通主信息字段优先考虑：

```text
缓存字段：由权威事实推导，可丢弃、可重算。
索引字段：用于快速查找，不改变事实语义。
去重字段：用于防重复写入、防重复结算、防重复入树。
审计字段：用于追踪生成机制、迁移来源、补账来源。
```

这类字段必须注明：

```text
是否权威。
由哪些权威字段推导。
是否允许作为业务判断依据。
不一致时以谁为准。
```

## 4. 禁止项

禁止新增下列字段作为主信息权威字段：

```text
1. 业务语义标签字段。
2. 可由特征类型 + 特征值比较推导出的判断字段。
3. 可由来源动作 + 动态特征 + 初始状态 + 结果状态推导出的分类字段。
4. 可由二次特征表达的关系字段。
5. 可由动作动态链追溯的原因字段。
6. 只为日志、UI、说明文字服务的语义字段。
```

如果确实需要这类信息，应使用：

```text
推导函数
只读投影
非权威缓存
显示层格式化
日志文本
```

不得写成数据层权威事实。

## 5. 动态节点字段边界

动态节点的核心语义是：

```text
某个主体的某个特征，从初始状态变化到结果状态，
并记录该变化来自哪个动作、输入场景、输出场景和时间段。
```

动态节点不应变成业务分类容器。

### 5.1 动态本体字段

动态本体应只记录：

```text
初始状态
结果状态
动态主体
动态特征
时间
```

这些字段表达“发生了什么状态变化”。

### 5.2 来源追踪字段

动态可以保留来源追踪字段：

```text
来源类型
来源动作
来源动作相位
来源输入场景
来源输出场景
动态路径签名
```

这些字段表达“这次变化从哪里来”。

其中：

```text
来源类型只能表示生成机制。
来源类型不得表示业务含义。
```

允许的来源类型语义应类似：

```text
观察生成
方法执行生成
推断生成
人工生成
系统补账生成
```

不应写成：

```text
任务状态提交
筹办回执同步
执行回执同步
需求满足回写
安全结算
服务结算
```

这些业务含义应由来源动作、动态特征、状态变化和二次特征推导。

### 5.3 动态业务语义类型

动态业务语义类型不适合作为动态节点主信息类的权威字段。

它容易重复：

```text
来源动作
动态特征
初始状态 / 结果状态
二次特征关系
因果追踪信息
```

若需要业务语义，应使用推导函数：

```cpp
动态语义判定结果 判定动态语义(
    const 动态节点主信息类& 动态,
    const 特征比较策略表& 比较策略表);
```

或使用只读投影 / UI 显示文本。

不得让业务语义标签成为第二套事实账。

### 5.4 来源动作名、来源执行成功、来源错误码

来源动作名、来源执行成功、来源错误码如果保留，只能作为非权威快照或调试缓存。

权威信息应来自：

```text
来源动作
来源方法运行存在
来源输入场景
来源输出场景
动作动态链
```

若缓存字段与权威来源冲突，以权威来源为准。

## 6. 业务语义推导规则

业务语义应通过底层事实推导，而不是直接存储。

示例：

```text
任务状态变化
= 动态主体 是任务虚拟存在
+ 动态特征 是任务状态特征
+ 来源动作 是 提交任务状态变化

筹办回执同步
= 来源动作 是 同步筹办回执到任务
+ 动态特征 属于筹办回执相关特征

执行回执同步
= 来源动作 是 同步执行回执到任务
+ 动态特征 属于执行回执相关特征

需求满足回写
= 来源动作 是 回写需求满足
+ 动态主体 是需求治理账 / 需求节点
+ 动态特征 是需求满足登记、有效截止或结算账相关特征
```

这类推导可以进入：

```text
诊断函数
控制面板显示
日志格式化
回归断言辅助
```

不得进入主信息权威字段。

## 7. 新增结构体准入规则

新增结构体前必须判断：

```text
1. 是否只是已有特征的组合？
2. 是否只是已有二次特征的组合？
3. 是否只是动作动态引用链的另一种包装？
4. 是否只是因果投影的只读结果？
5. 是否只是为了某个回归或 UI 临时好看？
```

若答案为是，应优先使用：

```text
复合抽象特征
二次特征
只读投影结构
诊断结果结构
局部运行期临时结构
```

而不是新增持久主信息结构。

## 8. 存量字段处理

存量字段如果与本规范冲突，不要求立即删除，但必须按下列方式处理：

```text
1. 标记其权威性。
2. 明确它是权威字段、非权威缓存、显示字段还是迁移字段。
3. 新代码不得继续扩大其权威用法。
4. 后续计划应逐步迁移到特征、二次特征、动作动态或因果追踪链。
```

尤其是：

```text
动态业务语义类型：
    应迁移为推导结果或显示层字段。

来源类型：
    可保留为来源审计字段，但不得表达业务分类。

来源执行成功 / 来源错误码：
    可暂存为非权威快照；权威结果应回查方法运行存在和输出结果场景。
```

## 9. 最小审查清单

任何新增字段或结构体提交前，必须能回答：

```text
1. 这个信息是否可比较？
   是：优先建模为特征。

2. 这个信息是否表达两个值之间的关系？
   是：优先建模为二次特征。

3. 这个信息是否表达事实变化来源？
   是：优先使用来源动作和动作动态链。

4. 这个信息是否表达原因、证据或归因？
   是：优先进入因果追踪信息。

5. 这个信息是否只是便于查找、显示、去重或审计？
   是：可以是普通字段，但必须非业务权威。
```

如果无法说明上述归属，不得新增。

## 10. 与其他规范的关系

本规范是一级系统建模约束。

它约束所有主信息类、动态节点、需求节点、任务节点、方法节点、因果节点、抽象特征和详细设计。

与下列规范共同生效：

```text
004 特征值三态比较底层逻辑规范
011 特征类规范
011001 抽象特征规范
001 方法动作动态硬规则规范
060 因果补完流程规范
060005 状态转换因果树与目标投影层级规范
```

若下级规范允许新增业务语义字段，但该字段可由特征、二次特征、方法动作或因果追踪推导，应按本规范收束。

## 11. 一句话定稿

```text
主信息类只存底层事实和必要索引；
业务语义从特征、二次特征、方法动作和因果链中推导，
不得为了上层好描述而新增第二套事实字段。
```
