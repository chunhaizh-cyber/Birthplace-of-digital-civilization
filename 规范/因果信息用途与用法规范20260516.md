## 1. 总口径

因果信息不再只用于补完方法。因果信息是自我治理层的解释、预测、反推、审查、结算与学习更新基础。

因果信息最高分类固定为两类：

```text
状态变化因果：
    来源于状态迁移动态。
    证明 A -> B 这种状态迁移存在。
    用于变化线索、学习线索、观察线索和证据补齐线索。
    不得直接作为可执行方法候选。

动作致变因果：
    来源于动作致变动态。
    证明某动作信息在特定前置状态下可以造成 A -> B。
    用于任务筹办、候选方法、练习、执行验证和结算归因。
    必须有动作来源、状态端点和证据动态。
```

其中：

```text
状态变化因果：
    是因果信息的一类，但不是可执行完整因果模板。
    当它尚未稳定或尚未验证时，也称状态变化线索。

动作致变因果：
    是可执行完整因果模板的一类。
    只有主动动作致变因果可以直接服务任务筹办的动作 / 方法候选。

证据动态样本：
    一次观察 / 执行 / 推断形成的动态证据，不是因果主体。
```

动作致变因果 / 可执行完整因果模板的标准形式：

```text
在条件状态 C 下，执行动作信息 A，会导致结果状态 R。
```

即：

```text
C + A -> R
```

其中 `A` 是由动态信息归纳出的动作信息，不是方法 ID、流程名或自由文本动作摘要。方法只作为动作信息的生成、识别或确认来源；任务筹办可以根据主动动作致变因果反查可执行方法，但不得把“方法 M”直接当作因果动作字段。

当动作未知时，只建立状态变化因果 / 状态变化线索：

```text
C -> R，待补动作。
```

后续若发现动作，再补成动作致变因果 / 可执行完整因果模板。

### 1.0.1 双账用途边界

状态迁移账和动作致变账是同一次变化的两个用途层，不是重复事实：

```text
状态迁移账回答：
    发生了什么变化？

动作致变账回答：
    谁能造成这个变化？
```

用途分工固定为：

| 账本 | 主要用途 | 消费方 |
| --- | --- | --- |
| 状态迁移动态 / 状态变化因果 | 证明状态真的变了；发现变化模式；生成线索 | 扫描、观察、因果归纳、学习、复验 |
| 动作致变动态 / 动作致变因果 | 证明某动作信息能造成该变化；用于选择方法 | 任务筹办、方法候选、练习、执行验证、结算归因 |

主动动作致变因果可直接用于筹办方法；状态变化因果只能作为线索，不能直接当方法。被动动作致变因果有动作语义，但不可被任务筹办召回为普通可调用方法。

内部治理因果消费边界：

```text
内部治理动态可以因来源动作明确而直接生成内部治理因果样本；
但任务筹办消费时仍只能把已满足条件、已通过稳定性要求的主动动作致变因果作为方法候选；
单次内部治理因果样本只能作为学习、补条件、复验或稳定度更新材料。
```

任务筹办面对目标状态时，查询顺序固定为：

```text
1. 查询目标状态动作致变因果分支：
       是否有动作能让该特征从当前状态变到目标状态。

2. 若无动作致变因果，查询目标状态变化因果 / 状态变化线索分支：
       是否至少存在这种状态变化模式。

3. 生成缺口：
       有状态变化因果但无动作致变因果 -> 生成学习 / 练习需求。
       连状态变化因果都没有 -> 生成观察 / 尝试 / 因果补完需求。
```

学习层使用规则：

```text
1. 只有状态迁移账、没有动作致变账：
       生成学习 / 练习需求，寻找可尝试动作。

2. 有动作致变账但缺条件：
       补条件结果对，记录成功 / 失败样本，收敛适用条件。

3. 动作执行了但目标状态迁移没有出现：
       生成动作尝试动态、失败动态或缺证据回执；
       降低动作致变因果稳定度；
       派生练习、参数补齐或条件补齐需求；
       不生成正向动作致变因果。
```

建议的查询接口契约：

```cpp
查询主果变化因果族(目标主体, 目标特征, 当前状态, 目标状态)
查询目标状态动作致变因果(目标主体, 目标特征, 当前状态, 目标状态)
查询目标状态变化因果(目标主体, 目标特征, 当前状态, 目标状态)
查询有状态变化但无动作致变的因果()
查询因果分支样本集(主果变化锚点, 分支句柄)
查询候选条件项交集(主果变化锚点, 分支句柄, 交集类型)
查询因果反例样本(主果变化锚点, 条件项 / 动作候选)
验证动作结果是否出现状态迁移(动作动态句柄, 目标状态迁移)
查询同源变化证据组(动态节点句柄 / 因果节点句柄)
```

这些接口是因果消费契约，不表示当前代码已经完整实现。实现时必须使用项目结构中的存在、特征、状态、动态、因果节点、主果变化锚点、因果样本、因果分支和同源变化证据组句柄，不得用自由文本 ID、日志或临时 JSON 承载业务判断。

凡同一次特征变化同时生成状态迁移动态、动作致变动态、状态变化因果和动作致变因果，必须绑定同一个同源变化证据组。结算、需求满足和账务值变化必须按同源变化证据组去重；因果稳定度可以分别更新，但不得重复入账。

因果族和因果分支只改变查询粒度，不放宽消费边界：

```text
状态变化因果分支：
    可解释变化、生成学习 / 观察 / 证据补齐需求。
    不得直接生成可执行方法候选。

动作致变因果分支：
    只有主动动作子类在匹配当前条件后，才能作为任务筹办候选方法依据。

条件伴随分支：
    只能生成补条件、补来源、补动作或反例验证需求。
    不得直接作为动作能力。
```

### 1.1 因果树挂载位置

因果树不挂在任务树、需求树或方法树下面，也不作为并行于世界树的旁路账本。

权威口径：

```text
因果树挂在世界树的根链上。
```

也就是说：

```text
世界树根链：
    承载状态节点、动态节点、因果模板、证据动态样本和状态变化因果 / 状态变化线索的全局状态转换因果树。

需求树：
    引用因果解释或因果需求候选，用于决定要改变什么。

任务树：
    引用因果证据和可结算路径，用于判断任务完成后能否回流结算。

方法树：
    引用因果模板和证据动态样本，用于补条件、补动作、补结果和更新稳定度。
```

因此，因果树的结构归属是：

```text
世界层事实解释结构。
```

它不是：

```text
任务私有因果树
需求私有因果树
方法私有因果树
安全值旁路索引
```

因果树本体存储所有状态转换信息，而不是只存安全因果。安全、服务、学习、自维护等只是从状态转换因果树中按目标语义和来源需求方向生成的只读投影视图。

```text
世界状态转换因果树：
    挂在世界树根链；
    存储所有状态转换、动作动态、因果模板、证据动态样本和状态变化因果 / 状态变化线索。

安全目标投影树：
    从世界状态转换因果树中，按可映射到安全目标 / 安全结算的目标特征生成。

服务目标投影树：
    从世界状态转换因果树中，按可映射到服务目标 / 服务结算的目标特征生成。

学习 / 方法 / 自维护投影树：
    从世界状态转换因果树中，按学习收益、方法改善、自维护目标等语义生成。
```

安全值变化状态只是账务状态转换投影之一，不是因果树总根。它说明系统如何把一次已验收的安全目标改善入账，不说明世界事实为什么变安全。

安全目标投影、服务目标投影、学习收益投影、自维护投影等，都是从世界树根链上的状态转换因果信息按目标语义和来源需求方向投影出来的只读视图。第一版工程实现可以先返回普通结构体投影，但语义上必须保留：

```text
节点来源 = 世界树根链上的状态 / 动态 / 因果模板 / 证据动态样本；
边来源 = 世界树根链上的动作动态引用、来源低层动态引用或因果模板；
    任务 / 需求 / 方法只能引用这些世界树因果节点，不得复制成另一套权威因果账。
```

### 1.2 遗传因果信息组

遗传信息的主体不是裸动作动态，而是带来源动态证据的因果信息组。

标准来源链：

```text
动作动态 / 被动动作动态 / 观察动态
    -> 状态变化因果 / 状态变化线索或动作致变因果 / 可执行完整因果模板
    -> 证据动态样本
    -> 初始因果模板 / 后天证据增强后的因果信息组
```

方法能力与初始因果模板的分工如下：

```text
主动动作：
    能力结构从本能方法 / 方法系统取得，包括本能方法、方法头、条件节点、结果能力和条件结果对。
    本能方法的因果信息不进入出生期初始因果模板组，只能通过学习及实际使用生成。
    主动动作动态只作为运行证据、验收证据和稳定度样本。

被动动作：
    出生期初始因果模板组承载的是被动因模板、自动果模板、动态转因果规则、幂等键和后处理 / 结算 / 提交链触发规则。
    被动动作动态只作为来源证据和实例样本。
```

因此：

```text
自我主动能做什么，主要从方法系统获取。
自我被动知道什么因会自动带来什么果，必须从初始因果模板或后天证据增强后的因果信息组获取。
```

初始因果模板的验收不看名称是否叫“遗传”，而看是否满足：

```text
1. 因果信息可读。
2. 因 / 条件 / 果 可解析为状态、特征或二次特征；不得把方法能力伪装成出生期初始因果模板。
3. 来源动态证据可追溯，或明确标记为出生期初始假设。
4. 被动动作模板不会被反推为可调用方法。
5. 若存在本能方法因果模板，必须由学习或实际使用生成，不得登记为出生期初始因果模板。
6. 后天证据可以强化、削弱、分化或覆盖该初始因果模板。
```

### 1.3 因果主信息与解释层边界

因果主信息只存事实骨架和基础计数，解释结论由查询层、二次特征解释器或投影层临时推导。

```text
因果作用类型：
    不作为因果主信息字段。
    只能由主果比较模板及其二次特征比较对象、比较量符号在解释层临时命名。
    生成、消除、增强、减弱、抑制、转换等词不进入因果主信息，
    也不得作为底层因果匹配、任务判断或结算依据。

因果确定性：
    不作为因果主信息枚举。
    用观察次数、条件命中次数、因出现次数、果出现次数、成立次数、失败次数表达。

置信度 / 稳定度 / 成功率 / 基线率 / 提升率：
    都是派生解释值，不写入因果主信息事实字段。

时间窗口：
    属于匹配策略和查询参数，不写入因果主信息。

失败样本：
    不写入因果主信息，只保留失败次数和最近失败时间。
```

若本文后续出现“因果置信度”“置信分”“稳定度”“成功率”等说法，均指由基础计数和查询参数计算出来的解释结果，不表示因果主信息中存在对应持久字段。

## 2. 七类用途

两类因果在七类用途中的消费边界固定如下：

| 用途 | 状态变化因果 | 动作致变因果 | 是否允许生成方法候选 | 是否允许结算 |
| --- | --- | --- | --- | --- |
| 解释状态变化 | 可用 | 可用 | 否 | 否 |
| 预测动作后果 | 不可单独使用 | 必须使用 | 否，只做执行前评估 | 否 |
| 反推可用动作 | 只能做线索 | 主动动作致变因果可直接候选 | 是，仅限主动动作致变因果 | 否 |
| 生成需求候选 | 可用 | 可用 | 否，只生成需求候选 | 否 |
| 执行前审查 | 可辅助 | 必须使用 | 否，审查既有候选 | 否 |
| 执行后验收 | 可证明结果变化 | 证明归因 | 否 | 只输出验收建议 |
| 结算 | 不能单独结算 | 与状态结果同源后可作为归因证据 | 否 | 需满足双钥匙和副作用审查 |

### 2.1 解释状态变化

输入：

```text
一个结果状态或特征变化。
```

输出：

```text
可能原因链。
```

无动作解释形式：

```text
结果状态 R
<- 状态迁移 S
<- 条件状态 C / 上游状态 U
<- 来源未知 / 外部事件 / 观察事实
```

有动作解释形式：

```text
结果状态 R
<- 动作 A
<- 条件状态 C
<- 上游原因 U
```

用途：

```text
回答“为什么会这样”。
```

### 2.1.1 被动动作因果桥

被动动作因果桥属于动作致变因果的被动子类。它不是新的动作来源，也不是状态迁移账 / 动作致变账之外的第三套账，而是由标准动作动态被动抽象出的承上启下关系。

被动的含义是：

```text
只要被动因正式出现，并满足该被动规则，
对应被动果就自动出现。
```

这里的自动出现由生命周期提交链、后处理链、结算链或对应领域提交链完成，不由普通任务筹办选择，也不由自我把 `被动动作` 当成可调用动作来执行。

输入：

```text
一条动作语义为 被动动作 的标准动作动态。
```

该动态必须能回解：

```text
动态主体；
动态特征；
初始状态；
结果状态；
来源低层动态；
输入 / 输出事实场景或等价状态事实。
```

输出：

```text
上游事实为什么导致本轮状态变化；
后续若需要同类结果，需要哪些上游事实、条件状态、任务状态或证据材料。
```

形式：

```text
上游事实 U
-> 被动因 I
-> 自动出现的被动果 R
-> 被动动作动态 P
-> 二次特征 / 目标投影
```

用途：

```text
知道为什么；
知道需要什么；
为需求候选、结算审查和安全 / 服务目标投影提供材料。
```

边界：

```text
被动动作不得被反推成可调用动作候选。
被动动作致变因果只用于解释、投影需求、检查提交链 / 后处理链 / 结算链缺口。
因果反推读到 被动动作 时，只能生成上游事实需求、条件需求或证据补齐需求。
被动因已具备但被动果缺失时，应生成被动提交链 / 后处理链 / 结算链缺口，而不是生成“调用被动动作”的普通任务。
```

### 2.2 预测动作后果

输入：

```text
当前条件状态 + 候选动作。
```

输出：

```text
可能结果状态
派生置信分
风险
副作用
```

形式：

```text
当前状态 C + 候选动作 A
-> 预测结果 R1 / R2 / R3
```

用途：

```text
执行前评估，不让任务只看“能不能做”，还要看“做了会发生什么”。
```

### 2.3 反推可用动作

输入：

```text
目标状态。
```

输出：

```text
能够导致该目标状态的动作 / 方法候选。
```

形式：

```text
目标结果 R
<- 哪些动作 A 能导致 R？
<- 这些动作需要哪些条件 C？
```

用途：

```text
任务筹办
候选方法选择
缺口生成
```

### 2.4 生成需求候选

输入：

```text
不良状态
风险状态
未满足目标
```

输出：

```text
可干预因果节点对应的需求候选。
```

示例：

```text
物理不安全事件 P
<- 直接原因 A
<- 上游原因 B
<- 长期原因 C

投影为：
处理 P、控制 A、确认 B、预防 C。
```

用途：

```text
从因果解释链投影到需求候选。
```

边界：

```text
因果信息只能生成需求候选。
正式需求入树必须由自我线程调用需求域方法完成。
```

2026-05-23 补充：

```text
因果链不是任务生成器。

因果链的作用是解释：
    为什么某个目标状态没有达到；
    哪个前置事实、方法能力、验证证据、权限条件或安全条件阻断了目标达成；
    哪个缺口可以被翻译成原子需求候选。

因果链生成需求候选必须有事实起点，例如：
    需求未满足；
    任务执行失败；
    任务结果未达标；
    方法缺动作 / 缺入口 / 缺条件结果对；
    安全或服务状态低于目标；
    观察到状态变化但归因证据不完整。

候选需求必须能归约为：
    需求主体；
    被需求存在；
    目标特征；
    当前状态；
    目标状态；
    来源因果；
    来源任务 / 来源方法 / 来源动作动态。

因果链不得直接生成任务。
任务只能由正式需求被任务管理链承接后创建。

诊断摘要、等待原因、说明文本、日志字符串只能辅助人工排错，
不得作为因果语义、需求目标、需求去重、任务状态、价值结算或归因判断依据。
```

### 2.5 执行前因果审查

输入：

```text
候选方法 / 候选动作。
```

输出：

```text
是否允许执行
预期收益
预期风险
硬边界触发情况
```

审查内容：

```text
动作 A 是否可能导致：
    物理安全下降
    服务对象受损
    任务状态异常
    需求目标被反向破坏
```

用途：

```text
安全门控
服务有效性过滤
避免坏动作
```

### 2.6 执行后因果验收

输入：

```text
动作动态
输出结果场景
来源任务
来源需求
```

输出：

```text
动作是否真的导致了目标结果。
```

形式：

```text
预测：C + A -> R
实际：C + A -> R'

若 R' 满足 R：
    成立次数 +1

若 R' 不满足 R：
    失败次数 +1

若出现副作用：
    补充副作用因果
```

用途：

```text
任务完成判断
需求满足证据
方法可靠性更新
```

### 2.7 更新因果模板稳定度

输入：

```text
一次执行或观察产生的证据动态样本。
```

输出：

```text
模板派生置信分
派生稳定度
成立次数
失败次数
```

用途：

```text
让因果知识成长，避免一次观察就成为铁律。
```

## 3. 内部循环位置

推荐链路：

```text
动态 / 状态变化 / 方法运行结果
-> 因果沉淀
-> 因果解释
-> 因果需求候选
-> 需求树更新指令
-> 任务筹办
-> 方法 / 动作选择
-> 执行前因果审查
-> 执行
-> 执行后因果验收
-> 因果模板稳定度更新
-> 需求满足 / 价值结算
-> 下一轮压力重判
```

硬边界：

```text
1. 因果类不直接写任务状态。
2. 因果类不直接写需求满足。
3. 因果类不直接写安全 / 服务根值。
4. 因果类不直接创建正式任务。
5. 因果类只提供解释、预测、反推、审查、验收和证据。
```

## 4. 与需求树的关系

因果解释链不等于需求树。

```text
因果解释链：
    解释为什么发生。

需求树：
    决定要改变什么。
```

示例：

```text
因果链：
    C -> B -> A -> P

需求投影：
    避免 P
    ├── 处理 A
    ├── 确认 / 修复 B
    └── 预防 C
```

规则：

```text
1. 一个因果节点可以生成多个需求候选。
2. 一个需求也可以同时处理多个因果节点。
3. 因果需求投影只生成候选，不直接入树。
4. 正式入树由自我线程按需求树规范裁决。
```

## 5. 与方法树的关系

因果信息在学习中的具体口径见：

```text
规范/因果信息在学习中的作用规范20260516.md
```

过去因果信息主要用于补完方法：

```text
缺条件结果对
-> 通过执行结果补条件结果对
-> 方法变得可用
```

现在扩展为：

```text
因果反推目标动作：
    帮助选择方法。

因果预测动作后果：
    帮助判断方法风险。

因果验收实际结果：
    帮助更新方法稳定度。

因果失败计数：
    帮助派生学习 / 修复需求。
```

方法不是因果信息唯一服务对象。因果信息同时服务需求、任务、方法、安全、服务和结算。

## 6. 与安全的关系

本节的深层需求投影细则见：

```text
规范/生存深层需求投影规范20260516.md
```

安全因果不应强绑为安全特征树。正确关系：

```text
安全特征：
    描述当前安全状态。

安全因果：
    解释安全状态为什么变化。

安全需求：
    根据因果节点生成行动目标。
```

安全因果距离层级由到物理不安全事件的反向因果距离决定：

```text
P：物理不安全事件，0 层。
A：直接原因，1 层。
B：导致 A 的原因，2 层。
C：导致 B 的原因，3 层。
```

安全因果距离层级只用于解释不安全事件的上游原因距离、需求投影和优先级衰减，不直接等同安全特征子节点，也不得直接作为安全结算贡献层级使用。

硬规则：

```text
安全因果距离层级：
    回答“某个原因距离物理不安全事件有多远”。

安全结算贡献层级：
    回答“某个任务结果对安全 / 服务核心值最多能贡献多少额度”。

二者不得直接互换。
结算前必须通过：
    目标特征实际变化
    任务贡献角色
    因果证据强度
重新判定安全 / 服务结算贡献层级。
```

### 6.1 自检观测因果

自检主要产生观测因果，不直接产生物理修复因果。

```text
物理因果：
    动作真实改变物理状态。
    例如：降低负载 -> 温度下降。

观测因果：
    动作改变自我对某个状态的认知。
    例如：执行自检 -> 硬件状态已知。

治理因果：
    动作改变任务、需求、方法或治理账状态。
    例如：回写需求满足 -> 需求满足登记已形成。
```

安全自检的典型因果模板是：

```text
安全状态未知 + 执行自检 -> 安全状态已知
方法状态未知 + 执行方法自检 -> 方法维护状态已知
执行自检 -> 生成异常报告
```

这些模板说明“自检让状态更清楚”，不说明“自检直接修复了物理安全”。因此：

```text
自检正常：
    可以降低安全不确定性、提高安全观测完整度、刷新风险估计。

自检异常：
    可以暴露风险、生成应急安全需求、触发原因解释。

自检本身：
    不直接结算为物理安全值增加。
```

因果系统在安全自检链路中的位置是：

```text
自检动态 / 自检输出结果场景
    -> 因果沉淀
        -> 安全状态变化因果 / 状态变化线索或观测动作致变因果模板
            -> 安全特征刷新
                -> 安全需求候选
```

安全特征刷新可以包含：

```text
物理安全不确定性；
安全观测完整度；
宕机风险；
损坏风险；
运行稳定性；
当前物理异常状态；
方法维护状态。
```

其中方法维护状态用于判断自我处理安全任务的能力基础，不得被误读成物理安全已经被直接提高。

自检发现的问题一律属于安全问题。它们可能是直接物理安全问题，也可能是方法、运行账、证据链或治理能力上的安全支撑问题。

```text
自检发现问题：
    形成安全需求候选或安全风险线索。

解决该问题：
    可以通过需求满足和叶子任务价值结算增加安全值。
```

因果解释上应保持两段关系：

```text
执行自检 -> 发现 / 澄清安全问题
解决问题 -> 安全值或安全评估提高
```

不得把第一段误写成：

```text
执行自检 -> 安全值提高
```

也不得丢掉第二段：

```text
解决自检发现的问题 -> 安全收益
```

## 7. 与结算的关系

结算时不应只看“任务完成”。

结算必须同时具备双钥匙和同源去重：

```text
1. 状态迁移账：
       目标特征确实发生目标方向变化。

2. 动作致变账：
       该变化可归因于自我动作 / 治理动作 / 允许的被动提交链。

3. 同源变化证据组：
       状态迁移账与动作致变账指向同一次变化。

4. 副作用审查：
       反向副作用已识别、计入或确认不存在。
```

具体检查项：

```text
1. 来源需求目标是什么。
2. 执行动作是什么。
3. 预测结果是什么。
4. 实际结果是什么。
5. 实际结果是否满足目标。
6. 是否出现反向副作用。
7. 该因果模板是否应增加成立次数或失败次数。
```

真实安全 / 服务结算只来自目标特征真实变化和同源动作归因同时成立。因果信息提供证据链、归因、派生证据强度、同源变化证据组和副作用审查，不直接写入安全 / 服务核心值。

结算方法必须读取因果验收结果，至少包括：

```text
验收结论：
    成立 / 部分成立 / 不成立 / 反向成立 / 证据不足。

因果证据类型：
    直接执行证据 / 观察证据 / 推断证据 / 外部声明证据。

因果置信分：
    范围 [0, DEN]，由基础计数和证据类型临时计算，不作为因果主信息字段。

副作用列表：
    每个副作用必须绑定目标特征、实际变化值、严重度、是否已处理。

竞争原因：
    是否存在其他动作或环境状态更可能导致该结果。

可结算建议：
    可结算 / 仅候选 / 待补证据 / 禁止结算。
```

其中：

```text
因果验收负责证明“动作是否导致目标特征变化”；
结算方法负责判断“该证明是否足够入账，以及入账多少”。
只有动作记录而没有目标方向状态迁移，禁止结算。
只有结果变化而没有动作致变归因，禁止结算。
状态迁移账和动作致变账不同源，禁止结算。
```

## 9. 最小落地顺序

### P1. 因果沉淀

```text
动态 -> 状态变化因果 / 状态变化线索 / 动作致变因果 / 证据动态样本。
```

### P2. 因果预测

```text
条件状态 + 候选动作 -> 预测结果。
```

### P3. 因果反推

```text
目标结果 -> 候选动作 / 方法。
```

### P4. 因果需求投影

```text
风险 / 不良结果 -> 原因链 -> 需求候选。
```

### P5. 执行前因果审查

```text
候选动作 -> 风险 / 副作用 / 是否允许。
```

### P6. 执行后验收与稳定度更新

```text
实际结果 -> 成立 / 失败 / 副作用 -> 更新模板。
```

### P7. 结算接入

```text
需求满足、叶子任务价值结算、安全 / 服务回流，引用因果证据链。
```

## 10. 最终口径

因果信息的用途不是“给方法补条件结果对”这么窄。它应成为自我内部循环的解释与预测层：

```text
解释状态变化；
预测动作后果；
反推可用动作；
投影需求候选；
审查执行风险；
验收执行结果；
把每次成功或失败回写为因果模板的稳定度变化。
```

一句话：

```text
因果信息不直接替自我行动，但它告诉自我为什么、会怎样、该找什么、能不能做、做完算不算数。
```
