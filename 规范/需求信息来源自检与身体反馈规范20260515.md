安全 / 服务不是硬编码目标链，而是自我存在上的根特征。

## 1. 总原则

自检和身体反馈都是需求信息来源，不是正式需求入树者。

```text
自检程序可以生成：
    需求候选信息
    差距信息
    需求草案
    自检报告

身体反馈可以生成：
    关注特征实时值
    反馈来源
    反馈时间

正式需求节点入树：
    只能由自我线程按需求树规则裁决；
    若需要生成动作动态，动作来源必须是需求域方法。
```

因此，禁止：

```text
自检线程直接写正式需求节点；
自检线程直接创建任务；
身体反馈直接构造完整需求；
反馈来源绕过自我线程刷新需求树；
把报告型候选伪装成已入树需求。
```

一句话：

```text
自检负责主动找差距，身体负责被动报数值，自我线程负责把这些信息变成需求树和任务推进。
```

## 2. 自检：主动差距发现

自检程序的职责是主动比较实时特征与预设正常值。

```text
读取目标宿主的实时特征值；
读取预设正常值 / 正常区间 / 正常状态；
比较差距；
偏离正常范围时生成需求候选信息；
报送自我线程。
```

自检生成的是候选信息，不是正式需求节点。

根特征自检的“预设正常值 / 正常区间 / 正常状态”不得来自硬编码 C++ 函数表，而必须来自世界树抽象特征树：

```text
读取抽象根特征定义；
读取自我根特征实例；
比较目标状态与当前值；
检查必要条件集；
生成缺口报告。
```

若读取对象是安全 / 服务根特征，具体规则以 011003 为准。

最小字段：

```text
来源类型 = 自检
反馈主体 = 自检程序 / 自检子存在
目标宿主 = 被检查的存在
目标特征类型 = 被检查的特征
最初值 / 最初状态 = 本次自检首次发现差距时的状态快照
当前值 / 当前状态 = 实时观测值
目标值 / 目标状态 / 正常区间 = 预设正常值
满足关系 = 等于 / 大于 / 小于 / 区间内
差距程度 = 当前值与正常值的偏差
证据时间 = 观测时间
派生归因 = 自检发现
```

示例：

```text
自检发现：
    方法M.条件结果对数量 = 0

正常值：
    方法M.条件结果对数量 >= 1

候选信息：
    目标宿主 = 方法M
    目标特征类型 = 条件结果对数量
    最初状态 = 0
    当前状态 = 0
    目标状态 = >= 1
    来源 = 自检
```

自我线程收到后再决定：

```text
记录为报告；
等待休眠期评估；
转成正式需求；
合并到已有同目标需求；
拒绝入树并记录异常。
```

正式需求入树的去重身份为：

```text
同一父需求
同一目标宿主
同一目标特征类型
满足关系 / 方向掩码重叠
```

若自检候选与同一父需求下已有活跃子需求目标相同，只能复用 / 合并该需求节点，刷新当前状态、统计和归因信息；不得因为最初状态、观测摘要、来源报告或派生归因不同而新增第二个需求节点。

## 3. 身体反馈：被动特征上报

身体反馈只反馈关注特征实时值。

```text
反馈主体
目标宿主
特征类型
特征值
时间戳
置信度 / 来源
```

身体反馈不负责提供：

```text
目标值；
任务建议；
需求结构；
方法建议；
修复策略。
```

若反馈未显式携带目标宿主，默认：

```text
目标宿主 = 反馈来源子存在
```

自我线程接收后：

```text
读取抽象特征定义中的正常值 / 目标值；
计算差距；
刷新安全 / 服务缺口压力；
必要时生成或刷新对应根需求或必要条件子需求；
必要时发起任务。
```

## 4. 两条输入流的区别

| 来源 | 性质 | 产物 | 是否直接入树 |
| --- | --- | --- | --- |
| 自检 | 主动 | 差距候选 / 需求候选信息 / 自检报告 | 否，由自我线程裁决 |
| 身体反馈 | 被动 | 关注特征实时值 | 否，由自我线程计算差距后裁决 |

```text
自检：主动比较“实时值 vs 正常值”，给出差距候选。
身体反馈：被动上报“某特征当前值”，由自我线程比较差距。
```

## 5. 原子目标完整性

自检和身体反馈都必须能确定：

```text
目标宿主.目标特征类型 = 当前值
```

如果只有：

```text
特征类型 = 安全值
当前值 = 30
```

但不知道是谁的安全值，则不能生成可执行需求信息，只能记录为异常报告。

完整候选至少应能补齐：

```text
目标宿主 / 被需求存在
目标特征类型
最初状态
当前状态
目标状态或正常区间
满足关系
来源归因
```

其中：

```text
最初状态：
    是候选生成时第一次被自检记录下来的状态快照。
    它用于后续判断差距是否仍有效、是否已经自然消失、是否需要合并或刷新。

当前状态：
    是自我线程处理候选时可重新观测或刷新后的状态。

目标状态：
    是正常值、正常区间或维护目标。
```

如果最初状态缺失，自检候选仍可作为普通报告保留，但不能作为完整需求候选信息进入正式入树闸门。

## 5.1 方法自检目标

方法类自检的目标特征类型应统一收束为：

```text
方法状态
```

不再优先派生一组平行目标特征类型，例如：

```text
方法成熟度阶段；
方法动作状态；
方法运行账完整性；
方法条件结果对状态；
方法可执行入口数量。
```

这些细分项只作为 `方法状态` 的判定证据、缺口证据或显示解释，不作为需求树首选目标特征类型。

方法类自检的维护目标不是“最低可用”这一单点，而是让方法状态沿统一状态集推进。

第一版 `方法状态` 只收束为以下状态值：

```text
方法状态 = 结构完整
方法状态 = 有真实动作入口
方法状态 = 有条件结果对
方法状态 = 可用
方法状态 = 好用
```

不得把以下缺口词写成方法状态值：

```text
只有方法头；
缺真实动作入口；
缺条件结果对；
方法不可用；
运行账不完整。
```

这些只能作为证据、缺口说明或诊断摘要。

自检可以检查出物理结构错误，但不得为此新增任务系统不识别的中间目标类型。

```text
不得新增或使用：
    缺失结构类型值；
    缺失动作类型值；
    缺失条件结果类型值；
    其他只表达物理错误类别的平行需求目标。

这类信息只能作为：
    方法状态判定证据；
    缺口证据；
    诊断摘要；
    日志显示；
    人工排错线索。
```

反馈到需求树时必须收束为正式目标特征，例如：

```text
方法状态 = 结构完整；
方法状态 = 有真实动作入口；
方法状态 = 有条件结果对；
方法状态 = 可用；
方法状态 = 好用。
```

```text
任务筹办口径：
    方法状态 = 可用
    表示该方法具备最低可筹办 / 可执行前提。

自检维护口径：
    方法状态 = 好用
    表示该方法在可用基础上具备更稳定、更完整、更适合自动召回和默认执行的质量。
```

`方法状态 = 可用` 的第一版判定条件为：

```text
条件结果对数量 > 0
```

`方法状态 = 好用` 的第一版判定条件为：

```text
方法最近连续成功次数 > 3
```

方法虚拟存在上可以保留以下三个方法特征作为自检证据和显示解释：

```text
方法运行次数；
方法成功次数；
方法最近连续成功次数。
```

其中 `方法运行次数`、`方法成功次数` 不作为第一版“好用”的硬判定条件，只作为自检证据、运行账参考和后续扩展依据。阈值属于自检标准，不是新的需求目标特征。自检总目标固定为 `方法状态 = 好用`，自检候选不得因为当前缺条件结果对而把目标降级成 `方法状态 = 可用`。缺条件结果对、条件结果对数量、连续成功次数等未满足项只写入证据；第一次承接该自检需求时应由 `自我_练习` 处理。练习运行时若发现目标方法缺条件结果对，再由练习输出结构化缺口，派生 `方法状态 = 可用` 需求并交给 `自我_尝试学习` 承接。

因此，方法自检候选应优先表达为：

```text
目标宿主 = 方法虚拟存在
目标特征类型 = 方法状态
最初状态 = 自检首次发现时已确认的最高方法状态
当前状态 = 当前已确认的最高方法状态
目标状态 = 结构完整 / 有真实动作入口 / 有条件结果对 / 可用 / 好用 中的一个
满足关系 = 达到或超过目标状态
证据 = 只有头节点、方法动作缺失、条件节点数、结果节点数、条件结果对缺失、方法运行次数不足、方法成功次数不足、方法最近连续成功次数不足、最近执行结果等
```

方法状态 `可用` 仍由任务筹办和学习需求链用于最低结构前提；自检维护总目标必须表达为 `方法状态 = 好用`，不得把成熟度、运行账、条件结果对等细分证据重新拆成一组平行需求目标，也不得由自检直接生成 `方法状态 = 可用` 的分段目标。`方法状态 = 可用` 只能作为练习执行时发现前置缺口后的派生需求目标，由 `自我_尝试学习` 承接；可用前置补齐后，原好用目标继续由 `自我_练习` 推进。

方法自检可以检查方法状态，但这里的“检查”是观测和维护，不是替任务筹办直接提交方法状态变化。

第一版方法自检至少可以观察：

```text
方法状态；
方法动作状态；
方法可执行入口数量；
条件结果对数量 / 状态；
最近运行账；
方法运行次数；
方法成功次数；
方法最近连续成功次数。
```

自检发现方法状态低于预设维护目标时，只能生成：

```text
方法维护候选信息；
方法质量差距信息；
方法安全 / 可维护性报告；
必要时生成“方法状态达到可用 / 好用”的正式需求候选。
```

它不得直接把方法状态写成：

```text
可用；
好用；
稳定；
运行账完整。
```

### 5.1.1 代码缺陷型自检报告

部分自检项不是世界目标缺口，也不是学习需求，而是内部实现或一致性错误暴露。

第一版至少包括：

```text
方法运行账完整性异常；
方法虚拟存在完整性异常；
可用方法数量镜像不一致；
状态清理阻塞。
```

这些项目不得直接入树，不得生成正式需求节点，不得创建任务。

处理规则：

```text
1. 自检线程生成报告型候选；
2. 记录错误日志；
3. 弹窗提示开发者；
4. 自我线程可记录待处理报告；
5. 后续由代码修复或专门维护逻辑处理。
```

这类报告的目标是暴露工程缺陷，便于修改代码；不能把内部一致性错误伪装成普通需求生长。

除代码缺陷型自检项外，自检发现的问题不再无条件统一归入安全问题。

分类规则：

```text
方法质量 / 方法状态 / 运行账 / 证据缺失：
    影响自我处理任务、学习、应急和后续安全行动的可靠性，归入安全信号。

服务根特征必要条件缺失：
    例如当前服务对象未知、服务目标未知、结果验证条件缺失、因果归因条件缺失，归入服务根需求的子需求候选。

抽象定义缺失：
    归入世界模型维护报告或维护需求。

自我根特征实例缺失：
    归入自我结构维护报告或维护需求。
```

方法不可用、无真实动作入口、无条件结果对、稳定度不足等问题，仍属于安全根需求可接收的安全信号，因为它们会降低自我后续处理任务和风险的可靠性。

若自检发现的是最低可用性缺口，例如方法不可用、无真实动作入口、无条件结果对，则该信息可以作为任务筹办 / 学习链的证据来源；正式学习需求仍必须由自我线程按需求树和学习需求规则入树。

自检线程不得因为同一方法已经存在学习需求、方法补齐需求或学习任务而抑制缺口候选提交。

```text
自检职责：
    按标准观测；
    形成缺口信息 / 需求候选；
    发送给自我线程。

不得在自检线程侧执行：
    同方法学习需求去重；
    同方法学习任务去重；
    因已有任务而跳过报告。
```

同一方法同时只允许存在一个活跃学习 / 方法补齐任务的约束，应在正式需求任务化或任务创建入口执行。也就是说，需求信息可以持续提交和入树；真正创建任务时，若同一来源方法已经存在未终结的学习 / 方法补齐任务，则本次任务创建请求应被过滤或等待复用，不应反向阻断自检报告。

这些问题被解决后，可以通过叶子任务价值结算增加安全值。这里增加安全值的原因不是“自检动作完成”，而是“自检发现的安全问题已经被解决，并且有需求满足证据和结算证据”。

## 5.2 自检与安全不确定性

自检不直接提高物理安全。自检首先改变的是自我对安全状态的认知：

```text
安全状态未知
    + 执行自检
        -> 安全状态更清楚 / 不确定性下降 / 风险被发现
```

因此，自检正常不等于物理安全值直接增加。它最多说明：

```text
当前观测范围内未发现异常；
物理安全不确定性下降；
安全观测完整度提高；
相关风险可以被重新估计。
```

如果原安全评估因为未知而被压低，自检正常可以通过“安全不确定性下降”使安全评估回升；如果自检发现异常，则安全值可能下降，并触发应急安全需求、原因确认需求或风险控制需求。

安全自检候选信息应优先表达为：

```text
目标宿主 = 自我 / 被检查子存在 / 被检查方法 / 被检查资源
目标特征类型 = 安全不确定性 / 安全观测完整度 / 当前异常状态 / 宕机风险 / 损坏风险 / 运行稳定性
最初状态 = 自检首次记录的安全观测状态
当前状态 = 当前安全观测状态
目标状态 = 不确定性降低 / 观测完整 / 无异常 / 风险低于阈值
满足关系 = 达到或低于阈值 / 区间内 / 无异常
```

其中方法状态自检属于安全观测的一部分：方法质量、方法状态、入口、条件结果对和运行账会影响自我能否可靠处理后续安全任务，但它本身仍是观测和维护信息，不能被解释成物理安全已经被直接修复。

安全自检发现的问题按安全问题处理。区别只在于问题所属层级不同：

```text
物理异常：
    直接影响物理安全。

方法质量 / 方法状态异常：
    影响自我处理任务、学习、应急和后续安全行动的可靠性。

运行账 / 证据缺失：
    增加安全不确定性，使自我无法可靠判断风险。
```

因此，解决这些自检问题都可以形成安全收益；但安全收益必须在问题解决后，通过需求满足与叶子任务价值结算链路入账，不能在自检报告生成时提前入账。

## 6. 入树边界

自检候选和身体反馈进入自我线程后，必须走需求树统一闸门：

```text
目标宿主有效；
目标特征类型有效；
当前状态或观测值有效；
目标状态 / 正常区间有效；
满足关系有效；
父需求或挂接策略明确；
派生归因完整；
同父同目标先查重 / 合并。
```

不满足闸门时：

```text
保留为报告；
记录日志；
不得兜底创建正式需求节点。
```

## 7. 自检需求挂接策略

自检 / 主动报送信息产生的需求候选，必须先由自我线程按缺口类型和根特征归属裁决父需求。

第一版挂接规则：

```text
安全根特征缺口或安全观测缺口：
    挂载到安全根需求下。

服务根特征缺口或服务必要条件缺口：
    挂载到服务根需求下。

抽象定义缺失：
    进入世界模型维护报告或维护需求。

自我特征实例缺失：
    进入自我结构维护报告或维护需求。

代码缺陷型自检报告：
    记录日志 / 弹窗 / 待处理报告，不入普通需求树。
```

这里挂载的是：

```text
自我线程正式裁决入树后的子需求。
```

不是：

```text
自检程序直接写入的需求；
身体反馈直接构造的需求；
子存在绕过自我线程创建的需求。
```

第一版流程：

```text
自检 / 主动报送 / 身体反馈
    -> 形成需求候选或特征差距信息
        -> 报送自我线程
            -> 自我线程检查入树闸门
                -> 按缺口类型和根特征归属选择父需求
                    -> 由需求域方法执行入树 / 合并 / 刷新
```

正式自检子需求至少必须具备：

```text
父需求 = 按缺口类型选定的安全根需求 / 服务根需求 / 维护类父需求
来源 = 自检 / 主动报送 / 身体反馈 / 子存在反馈
目标宿主 = 承载该特征的存在
目标特征类型 = 需要恢复到正常范围的特征
当前状态 / 当前值 = 实时观测值
目标状态 / 正常值 / 正常区间 = 预设正常值
满足关系 = 等于 / 大于 / 小于 / 区间内
派生归因 = 来源报告 / 子存在 / 特征反馈
```

第一版安全子需求类型可以包括：

```text
确认安全状态；
降低安全不确定性；
提高安全观测完整度；
确认方法维护状态；
修复或补齐安全相关方法质量；
处理已发现物理异常；
确认异常原因；
控制已确认风险；
预防重复风险。
```

第一版服务子需求类型可以包括：

```text
明确当前人类服务对象；
明确当前交互者；
明确当前权限者；
明确当前服务目标；
明确服务对象当前状态；
形成服务结果验证条件；
形成服务结果归因条件。
```

这样做的目的只是保证安全 / 服务根特征缺口信号不丢失。安全根需求只承接安全信号；服务根需求只承接服务信号；二者不得互相兜底。后续再根据以下维度整理、合并或重挂：

```text
目标宿主；
目标特征类型；
来源；
缺口类型；
是否阻塞当前父任务；
可任务化程度；
任务结果和结算回流。
```

如果安全问题暂时无法进一步分类，或暂时找不到明确父任务，不得因此阻塞正式入树或任务化。第一版默认：

```text
需求层：
    未分类安全问题 / 无父任务安全问题挂载到安全根需求下。

任务层：
    未分类安全任务 / 无父任务安全任务挂载到安全根需求对应的根承接任务 / 安全根任务下。
```

该规则只解决“挂到哪里”的问题，不降低原子目标闸门。未分类安全需求仍必须具备：

```text
目标宿主；
目标特征类型；
当前状态；
目标状态 / 正常区间；
满足关系；
来源归因。
```

因此：

```text
分类缺失：
    不阻塞安全需求入树 / 任务化。

父任务缺失：
    不阻塞安全需求入树 / 任务化。
    由任务管理线程按安全根需求承接关系创建或复用安全根任务。

原子目标缺失：
    仍然阻塞正式入树，只能保留为报告。
```

即使按安全根 / 服务根承接，也不得生成模糊需求。同一父需求下仍必须按：

```text
目标宿主
目标特征类型
满足关系 / 方向掩码
```

先查重 / 合并，派生归因不得作为身份键。

权重第一版不继承安全 / 服务根需求压力，也不按缺口严重度折算成额度：

```text
安全子需求活动权重 = 1
服务子需求活动权重 = 1
```

权重只用于表示该安全需求参与调度，不等于真实安全 / 服务结算值。安全需求的真实结算仍必须走叶子任务完成后的结算链；`I64_MAX` 不得进入真实服务结算。

安全自检完成后的结算对象应优先是：

```text
安全不确定性下降；
安全观测完整度提高；
方法维护状态被确认；
风险被发现并进入需求树。
```

不得把“自检完成”直接结算为：

```text
物理安全值增加；
真实服务值增加。
```

但自检发现的问题被解决后，应允许结算安全值：

```text
自检发现安全问题
    -> 正式安全子需求入树
        -> 子需求任务化
            -> 叶子任务解决该问题
                -> 回写需求满足
                    -> 结算叶子任务价值
                        -> 安全值增加
```

换句话说：

```text
自检发现问题不加安全值；
解决自检发现的问题会增加安全值。
```

## 8. 与动作动态的关系

自检报告和身体反馈本身不是方法动作动态来源。

若根特征自检需要进入动作动态和因果账本，必须由明确方法表达，例如：

```text
方法 = 自检自我根特征
动作结果 = 缺口事实已知 / 自我根特征状态已知
```

线程仍然不是动作来源；报告投递也不是动作来源。

正式入树、合并、需求满足登记等事实若需要动作动态，必须由需求域方法完成，例如：

```text
派生需求入树；
回写需求满足；
登记任务发起意图。
```

线程只能调度和报送，不是动作来源。

## 9. 最终口径

```text
自检是主动差距发现机制。
普通自检根据实时特征值和预设正常值生成需求候选信息；自我根特征自检必须读取世界树抽象特征定义和自我特征实例后生成缺口报告。自检程序不得直接写需求树或创建任务。

身体反馈是被动特征上报机制。
自我的子存在只反馈需要关注的特征类型和值，自我线程根据这些反馈值和自身正常值 / 目标值计算差距，并决定是否刷新需求、生成子需求或发起任务。

自检和身体反馈都只是需求信息来源。
正式需求入树、权重刷新、任务发起和满足登记，仍由自我线程通过对应需求域方法完成。

自检 / 主动报送形成的需求候选，第一版在通过自我线程入树裁决后按缺口类型挂到安全根需求、服务根需求或维护类父需求下；后续再根据目标宿主、特征类型、来源、缺口类型和任务结果归纳整理。
```
