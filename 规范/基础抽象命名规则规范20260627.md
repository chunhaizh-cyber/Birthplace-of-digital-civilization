## 0. 定位

本规范定义场景、存在、特征、变化四类基础信息的最高抽象命名规则。

这些词不是普通中文标签，也不是某个实例节点的显示名。它们是四类基础信息沿对应数据类型向上抽象到不能再抽象时得到的根抽象名。

本规范只确定抽象命名和匹配口径，不新增结构体，不新增枚举，不用文本字段承载机器逻辑。工程实现仍必须按 007 使用项目通用数据结构闭环。

## 1. 四个根抽象名

四类基础信息的最高抽象固定为：

```text
场景类信息最高抽象 = 场景
存在类信息最高抽象 = 存在
特征类信息最高抽象 = 特征
动态类信息最高抽象 = 变化
```

含义固定为：

```text
场景：
    所有场景类信息的根抽象名。

存在：
    所有存在类信息的根抽象名。

特征：
    所有特征类信息的根抽象名。

变化：
    所有动态类信息的根抽象名。
```

示例：

```text
某个房间场景、当前观察场景、自我内部世界
    -> 向上抽象到最高层 = 场景

杯子、人、任务虚拟存在、方法执行实例、观察候选
    -> 向上抽象到最高层 = 存在

位置、颜色、支撑状态、任务状态、归属状态
    -> 向上抽象到最高层 = 特征

位置变化、支撑断开、任务筹办状态变化、方法执行状态变化、走、跳、拿起
    -> 向上抽象到最高层 = 变化
```

## 2. 根名与最高抽象结果合一

当某类信息抽象到不能再抽象时，其最高抽象结果的名称，就是该数据类型本身的根名。

规则固定为：

```text
根名 = 类型最高抽象名。
```

因此：

```text
场景不是某个具体场景的名字；
场景是所有场景类信息的根抽象。

存在不是某个具体物体的名字；
存在是所有存在类信息的根抽象。

特征不是某个具体属性的名字；
特征是所有特征类信息的根抽象。

变化不是某个具体动作标签；
变化是所有动态类信息抽象链的根。
```

禁止把这些根名当作普通文本标签、动作标签、日志词或兜底字符串参与机器判断。

## 3. 动态抽象以变化为根

动态信息向上抽象时，最高层结果固定为：

```text
变化
```

动态抽象链的基本方向为：

```text
实例动态
    -> 某存在某特征变化
    -> 某类存在某类特征变化
    -> 某类存在某类特征某种变化关系
    -> 某类存在的一组特征变化组合
    -> 复杂动态
    -> 变化
```

示例一：

```text
人A左脚支撑状态：支撑 -> 摆动
    -> 人形存在的支撑状态变化
    -> 存在的关系 / 支撑类特征变化
    -> 存在的特征变化
    -> 变化
```

示例二：

```text
任务T.筹办状态：筹办中 -> 筹办完成_可执行
    -> 任务虚拟存在的治理状态变化
    -> 治理虚拟存在的状态变化
    -> 存在的特征变化
    -> 变化
```

动态节点主信息类是工程承载结构；变化是动态信息抽象到最高层后的概念名。不得用“变化”替代动态节点，也不得把动态节点主信息类改名为变化来获得抽象语义。

## 4. 抽象动态必须由四根共同定位

一个有用的抽象动态不能只写成：

```text
变化
```

只停在变化只能作为最高兜底，不能区分走、跳、滑动、被拖动、任务筹办状态变化、方法执行状态变化等不同动态。

抽象动态必须至少考虑四条根抽象链：

```text
场景抽象：
    这种变化发生在哪类场景中。

存在抽象：
    哪类存在发生了变化。

特征抽象：
    哪类特征发生了变化。

变化抽象：
    前后状态之间发生了哪类变化关系。
```

抽象动态的标准形式为：

```text
某类场景中，
某类存在的
某类特征
从某类初始状态
到某类结果状态
发生某类变化。
```

展开到工程判断时，抽象动态应由以下锚点共同定位：

```text
抽象动态 =
    场景抽象
  + 存在抽象
  + 特征抽象
  + 变化抽象
  + 初始状态抽象
  + 结果状态抽象
  + 时间关系抽象
  + 低层动态结构
```

最高兜底形式只允许是：

```text
变化
```

## 5. 四个根抽象的作用边界

四个根抽象在动态抽象中的作用不同：

```text
场景：
    限定变化发生的世界、场域或事实容器。

存在：
    限定谁发生变化。

特征：
    限定哪个方面发生变化。

变化：
    限定前后状态之间的变化关系。
```

实例最小动态固定表达为：

```text
场景 S 中
存在 E 的
特征 F
从状态值 V0@t0
变化到状态值 V1@t1
```

抽象最小动态固定表达为：

```text
某类场景中
某类存在的
某类特征
发生某类变化
```

再上层可以抽象为：

```text
场景中，存在的特征发生变化。
```

最高层可以继续收束为：

```text
变化。
```

## 6. 特征抽象按特征收束

特征信息本身也必须沿特征链向上抽象，最高层收束为：

```text
特征
```

基本链路为：

```text
具体特征值
    -> 具体特征
    -> 抽象特征
    -> 特征
```

示例：

```text
杯子E.位置 = P1
    -> 位置特征
    -> 空间特征
    -> 特征
```

动态抽象中的初始状态抽象、结果状态抽象和变化关系抽象，必须依赖：

```text
特征值 -> 特征值域 -> 抽象特征 -> 特征
```

不得用自由文本签名、日志文案、黑盒编号或未挂接项目结构的字符串替代特征抽象链。

## 7. 场景必须作为抽象维度

同一类变化在不同场景类型中的意义可能不同。动态抽象匹配不得只看存在、特征和变化，还必须判断实例动态所在场景能否归入抽象动态要求的场景抽象。

示例：

```text
杯子位置变化
```

在现实场景中可以表示：

```text
杯子被移动。
```

在观察证据场景中可以表示：

```text
观察候选中心变化。
```

在自我内部世界中可以表示：

```text
任务虚拟存在状态变化。
```

因此，抽象动态查找必须纳入：

```text
实例动态所在场景
    能否归入
抽象动态要求的场景抽象
```

## 8. 抽象动态覆盖实例动态的匹配规则

抽象动态覆盖实例动态时，按四根抽象链判断：

```text
1. 场景链匹配
    实例所在场景 -> 抽象场景 -> 场景

2. 存在链匹配
    实例动态主体 -> 主体概念 -> 存在

3. 特征链匹配
    实例动态特征 -> 抽象特征 -> 特征

4. 变化链匹配
    实例状态变化关系 -> 抽象变化关系 -> 变化
```

最小动态匹配示例：

```text
实例：
    场景S 中，杯子E.位置 P1 -> P2

可被抽象覆盖为：
    现实场景中，可移动物体的位置变化

再上层：
    场景中，存在的特征变化

最高层：
    变化
```

复杂动态匹配示例：

```text
实例复杂动态：
    人E在现实场景中走

抽象：
    现实场景 / 可支撑场景
    人形存在
    支撑关系 + 位置 + 姿态特征
    周期性组合变化

最高层：
    变化
```

兼容性来自各链路可以继续上抽到根名；区分性来自抽象过程中保留足够中间层锚点。不得为了召回方便，一开始就把动态抽象收缩成单独的“变化”。

## 9. 对现有数据结构的要求

本规范不要求新增结构体。

需要明确四类根抽象节点：

```text
根场景抽象节点：
    名称 = 场景
    类型 = 场景

根存在抽象节点：
    名称 = 存在
    类型 = 存在

根特征抽象节点：
    名称 = 特征
    类型 = 特征

根动态 / 变化抽象节点：
    名称 = 变化
    类型 = 动态 / 变化
```

各抽象链最高节点固定为：

```text
场景概念链最高节点 = 场景
存在概念链最高节点 = 存在
特征概念链最高节点 = 特征
动态抽象链最高节点 = 变化
```

不得把“变化”新增为与动态节点并列的平行业务结构；不得把“变化”塞成仅供字符串匹配的枚举；不得用签名或文本字段替代四根抽象链。

## 10. 一句话口径

```text
场景、存在、特征、变化，不只是词；
它们是四类数据类型抽象链的根。

动态抽象最高到“变化”，
但有效动态抽象必须在“变化”之下保留足够锚点，
才能既兼容实例，又区分实例。
```
