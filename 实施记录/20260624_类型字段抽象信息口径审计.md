# 20260624 类型字段抽象信息口径审计

## 0. 结论摘要

本次按以下口径审计源码中的 `类型` 字段：

```text
抽象信息节点必须唯一。
抽象信息名称必须唯一。
实例名称可以为空。
实例类型应指向抽象信息入口。
自然语言输出实例时再由类型名 + 场景 / 归属 / 位置等结构定语生成可读称谓。
```

当前项目已经具备实现该口径的基础结构，但仍存在两类需要收束的边界：

```text
1. `const 语素入口节点类* 类型 / 特征类型 / 目标特征类型` 已能作为抽象信息入口。
2. `语素入口主信息类::对应基础信息` 已能把入口绑定到真正的基础信息节点。
3. `存在类::取或创建子存在_按类型` 已支持名称为空、只按类型创建实例。
4. 但 `存在主信息::类型` 与 `概念模板 / 概念集` 还不是同一套强同步事实。
5. 大量 `枚举_*类型` 是协议 / 结构分派枚举，不应强行变成抽象信息节点。
6. 剩余 `std::string *类型*` 多数是 SQL / 控制面板 / 日志投影，必须继续保持非权威。
```

## 1. 已确认的类型字段分层

### 1.1 抽象信息入口型

承载形式：

```cpp
const 语素入口节点类* 类型;
const 语素入口节点类* 特征类型;
const 语素入口节点类* 目标特征类型;
```

代表代码：

```text
基础信息主信息类.h::主信息基类::名称 / 类型
任务主信息类.h::任务主信息类::类型
存在类.cpp::读取存在类型 / 写入类型
世界树类.cpp::取或创建子存在_按类型
任务模块.筹办.ixx / 任务模块.执行.ixx 中大量特征类型入口
```

判断：

```text
这类字段可以承接“类型 = 抽象信息入口”的口径。
完整条件不是指针非空，而是该语素入口能通过 `语素入口主信息类::对应基础信息` 回到基础信息节点。
```

### 1.2 抽象信息桥接型

承载形式：

```cpp
枚举_信息入口类型 信息入口类型;
枚举_主信息类型 对应基础信息类型;
可解析引用<基础信息节点类> 对应基础信息;
```

代表代码：

```text
语素主信息类.h::结构_信息入口定义
语素主信息类.h::信息入口定义表
语素类.cpp::确保语素入口对应基础信息
语素类.cpp::添加对应基础信息
基础信息类.cpp::确保语素入口模板
```

判断：

```text
这是“词面 / 语素入口 -> 抽象信息节点”的核心桥。
如果类型字段用于机器语义判断，必须能走到这一层。
如果只是 `添加信息入口词(...)` 后未确保对应基础信息，只能算入口标签，不算抽象信息结构完整。
```

### 1.3 主信息结构分派型

承载形式：

```cpp
枚举_主信息类型 主信息类型;
枚举_信息入口类型 信息入口类型;
枚举_信息存储树 存储树;
```

判断：

```text
这些不是“苹果 / 水果”意义上的抽象信息类型。
它们是代码结构和路由分派类型，应保留为枚举。
不能把它们简化成普通抽象信息节点，否则会混淆“节点本体是什么结构”和“实例归属于哪个抽象概念”。
```

### 1.4 业务协议枚举型

承载形式：

```cpp
枚举_任务管理派生需求类型
枚举_任务管理因果路径生成类型
枚举_外设观察报告类型
枚举_动作句柄类型
枚举_世界类型
枚举_因果锚点类型
枚举_二次特征来源类型
枚举_二次特征基准类型
```

判断：

```text
这些是协议、状态机、分支路由或值域枚举。
可以保留。
如果这些枚举结果需要进入项目事实闭环，应投影成特征值 / I64 / 抽象特征指针组合，而不是改成自由文本。
当前已有若干结构使用 `类型抽象特征指针 + 类型值` 的方式，方向正确。
```

### 1.5 文本投影型

承载形式：

```cpp
std::string 类型文本;
std::string 类型主键;
std::string 最近工作项类型;
std::string 目标特征类型ID;
std::string 展开类型;
std::string 事实类型;
std::string 缺口类型;
```

代表范围：

```text
世界树 SQL 投影
控制面板树和 WebView 展开
任务管理界面线程快照
外设观察等待项 / 观察约束 ID 快照
自我线程治理快照 / 根闭环信息位摘要
```

判断：

```text
这类字段不得作为机器判断权威。
主键 / ID / 文本是投影、显示、日志或跨线程快照材料。
若某字段进入路由、去重、任务推进、结算或因果匹配，应改为语素入口指针、基础信息节点引用、枚举或特征值。
```

## 2. 当前结构完整性判断

### 2.1 已完整或基本完整

```text
语素入口唯一性：
    `添加信息入口词(词节点, 信息入口类型)` 会复用同一词节点下同一信息入口类型。

入口到基础信息：
    `确保语素入口对应基础信息` 会按入口类型推导主信息类型，调用 `基础信息类::确保语素入口模板` 创建或查找节点，再回写 `对应基础信息`。

基础信息模板创建：
    存在、抽象特征、特征、状态、动态、二次特征、因果、语言记录都有模板创建分支。

实例名称可为空：
    `存在类::取或创建子存在_按类型` 在未命中时调用 `创建存在_按名称类型(父节点, nullptr, 类型)`。

核心概念绑定：
    `世界树类::绑定核心概念语素` 已把“存在 / 实物存在 / 虚拟存在 / 自我 / 需求 / 任务 / 方法”等核心入口绑定到概念存在节点。
```

### 2.2 不完整或需要明确规则的部分

```text
存在实例的 `类型` 与 `概念集` 尚未强同步：
    `创建存在_按名称类型` 只写 `名称 / 类型`。
    `创建存在实例` 只写 `名称` 并填 `概念集`，类型仍可为空。
    这导致“类型=苹果”和“概念集含苹果概念”在当前代码中可能是两套事实。

语素入口不一定已经对应基础信息：
    很多代码调用 `添加信息入口词(...)` 只取得入口指针。
    如果该入口只用于显示或字段类型标识，可以接受。
    如果该入口用于抽象信息判断，则还必须确保 `对应基础信息` 有效。

抽象特征结构要求比普通类型入口更严格：
    `抽象特征主信息类::校验结构` 要求名称和类型非空，叶子特征必须有值域。
    因此“特征类型入口存在”不等于“抽象特征结构完整”。

任务类型字段语义需要后续收束：
    `任务主信息类::类型` 当前注释为“任务类型词，用于任务分类判断”。
    按新口径，它应明确是“任务抽象概念入口”还是普通显示分类入口。
    如果参与任务分类机器判断，应确保对应 `任务概念入口` 或任务相关基础信息结构完整。
```

## 3. 是否可以简化

可以简化，但不应一刀切删除所有 `类型` 字段。建议收束为四类：

```text
1. 抽象信息入口：
   `const 语素入口节点类* 类型`
   用于存在、特征、动态、状态、任务等语义对象的抽象归属。

2. 结构分派枚举：
   `枚举_主信息类型 / 枚举_信息入口类型 / 枚举_信息存储树`
   用于决定主信息结构、入口路由和存储树。

3. 协议状态枚举：
   `枚举_*类型`
   用于线程消息、任务治理、外设报告、动作句柄等有限状态或协议分支。

4. 非权威文本投影：
   `std::string *类型*`
   只用于 SQL、控制面板、日志、主键快照和自然语言输出材料。
```

### 3.0 修订后的审计判定方式

本轮新增口径后，审计 `类型` 字段、抽象特征和复合特征时，先按以下顺序判定，不直接按名称长短或是否能自然语言拆分来决定结构：

```text
1. 先判定对象层级：
   抽象信息 / 实例 / 特征类型 / 特征值 / 协议枚举 / 文本投影。

2. 若是实例：
   `类型` 指向唯一抽象信息入口。
   `名称` 可以为空。
   自然语言称谓由类型名 + 定语生成。

3. 若是叶子特征：
   必须有特征值或明确值域。
   值域可以是离散集合，也可以是连续区间。
   值域中的多个可取值表达 OR。

4. 若是复合特征：
   子链只保存这个复合特征必需同时具备的子特征槽位。
   子链表达 AND。
   每个子特征槽位仍是完整抽象特征节点。
   复合特征不得循环嵌套，组成链最多 3 层。

5. 若是可变长度、连续结构或整体数据：
   优先作为特征值，不拆成子特征链。
   例如轮廓、点序列、路径、像素掩码、点云、体素块、VecI / VecIU64 等。

6. 若存在跨槽位组合约束：
   用低级校验函数、二次特征或专门方法表达。
   不把“任选 N 个 / 不重复 / 可选 / 排斥 / 权重”塞进复合特征子链。

7. 需求 AND / OR：
   只作为需求生命周期专用逻辑参考。
   不直接复用为抽象特征子链语义。
```

审计时的核心问题改为：

```text
这个名字表达的是一个抽象信息节点，还是一个实例事实？
这个字段保存的是类型入口，还是值？
这个可描述部分是固定槽位，还是可变长度数据？
如果是固定槽位，是否属于复合特征子链的 AND？
如果是可选候选，是否应进入槽位值域的 OR？
如果是整体 vector / mask / 点集，是否应保留为特征值？
```

### 3.1 抽象概念的分类链和根链关系

所有抽象概念都应作为独一无二的抽象信息节点存在。某个抽象概念可以挂到另一个抽象概念下作为子节点，但这只表示分类链上的父子关系，不表示该节点失去自身的抽象概念身份。

当前口径：

```text
1. 每个抽象概念节点本身都是抽象信息根链上的一员。
2. 抽象概念可以同时出现在某条分类链中，作为其它抽象概念的子节点。
3. 父子关系只表达“更上级分类 / 更下级分类”，不把子概念压缩成父概念的属性字段。
4. 实例的 `类型` 应指向最贴近当前语义需要的抽象概念节点。
5. 上级分类用于归类、召回、继承默认结构或自然语言组织，不替代实例自身类型。
6. 分类层级可根据需要调整；调整的是父子关系，不应制造同名抽象节点或让同一名称指向多个节点。
7. 新增抽象概念时，应先定位所属分类根链，再把新概念挂入该分类根链，不应先创建孤立概念再靠文本说明补关系。
8. 分类根链本身可以挂在更上级世界树或信息树节点下；根链入口负责承接该分类下的新增概念。
```

例如：

```text
世界树
    抽象存在根
        水果
            苹果

抽象存在根
    在世界树上是一个抽象存在分类根节点。
    它的子链就是抽象存在的根链。

抽象概念 = 苹果
    可以是 `水果` 的子节点。
    也仍然是抽象信息根链上的唯一节点 `苹果`。

实例 = 某个苹果
    类型 = 苹果
    名称 = 可为空
    自然语言输出 = 这个苹果 / 桌上的苹果 / 某某的苹果
```

这意味着类型简化时不能只把下级概念并入上级概念名称，也不能因为一个概念是其它概念的子节点，就取消它自己的类型入口。
新增概念的第一步也不是生成一个无归属入口，而是先按 `抽象存在 / 抽象特征 / 状态 / 动态 / 方法 / 需求` 等分类找到对应根链，再在该根链下建立唯一节点。

### 3.2 坐标类特征的层级简化方向

坐标类长名称不应简单把 `存在_场景绝对坐标X` 改成全局裸 `X轴`。更新后的方向也不再把 `二维坐标` 的子链直接写成 `X轴 / Y轴`，而是把 `二维坐标 / 三维坐标` 审计为固定槽位型复合特征，把 `X轴 / Y轴 / Z轴 / 1轴 / 2轴` 审计为槽位值域中的可选轴值。

抽象特征概念根链示例：

```text
抽象特征根
    坐标系
    二维坐标
    三维坐标
    X轴
    Y轴
    Z轴
    场景坐标系
    像素坐标系
    场景绝对坐标系
    场景相对坐标系
```

复合特征槽位关系示例：

```text
坐标系
    子特征引用 -> 二维坐标
    子特征引用 -> 三维坐标

二维坐标
    子特征槽位 -> 第一轴
    子特征槽位 -> 第二轴

三维坐标
    子特征槽位 -> 第一轴
    子特征槽位 -> 第二轴
    子特征槽位 -> 第三轴

第一轴 / 第二轴 / 第三轴
    值域 -> 坐标轴集合{X轴, Y轴, Z轴, 1轴, 2轴, ...}

场景坐标系
    子特征引用 -> 场景绝对坐标系
    子特征引用 -> 场景相对坐标系
    子特征引用 -> 二维坐标 / 三维坐标

像素坐标系
    子特征引用 -> 二维坐标
```

当前建议口径：

```text
1. `坐标系` 是坐标类复合抽象特征的上级概念。
2. `二维坐标 / 三维坐标 / 坐标轴 / X轴 / Y轴 / Z轴 / 第一轴 / 第二轴 / 第三轴` 都先进入抽象特征根链，成为唯一抽象特征概念。
3. `二维坐标` 的直接子链只保留 `第一轴 / 第二轴` 两个必需槽位。
4. `三维坐标` 的直接子链只保留 `第一轴 / 第二轴 / 第三轴` 三个必需槽位。
5. `X轴 / Y轴 / Z轴 / 1轴 / 2轴` 是轴槽位的值域候选，不作为 `二维坐标 / 三维坐标` 的直接组成子特征。
6. `二维坐标 / 三维坐标` 作为坐标系的子特征时，由 `坐标系 / 场景坐标系 / 像素坐标系` 等复合特征关系引用。
7. `场景 / 像素` 在坐标口径下表示坐标来源或参照域，不等同于普通场景实例或像素实例。
8. `绝对 / 相对` 是坐标系限定层，应形成 `场景绝对坐标系 / 场景相对坐标系` 等抽象特征节点或复合限定关系。
9. `X轴` 不能脱离坐标轴值域或具体坐标系语境作为全局裸机器语义；它可以是抽象特征根链上的唯一轴概念，也可以作为多个轴槽位的候选值。
10. `存在` 由宿主节点表达，不应长期写进特征名。
11. 层级不是一次定死的结构，可根据后续需要调整；不变的是每个抽象特征概念唯一、名称唯一、先入根链、再建立父子 / 子特征引用关系。
```

旧名 `存在_场景绝对坐标X` 的目标表达应收束为：

```text
宿主 = 存在实例
坐标系 = 场景绝对坐标系
维度结构 = 三维坐标
轴槽位 = 第一轴 / 第二轴 / 第三轴
轴槽位值域 = 坐标轴集合
具体轴值 = X轴 / Y轴 / Z轴 之一
结构关系 = 场景绝对坐标系 引用 三维坐标；三维坐标 引用 第一轴 / 第二轴 / 第三轴
```

像素坐标可对应：

```text
宿主 = 图像 / 观察帧 / 像素簇 / ROI 等实例
坐标系 = 像素坐标系
维度结构 = 二维坐标
轴槽位 = 第一轴 / 第二轴
轴槽位值域 = 坐标轴集合
常见具体轴值 = X轴 / Y轴
结构关系 = 像素坐标系 引用 二维坐标；二维坐标 引用 第一轴 / 第二轴
```

因此简化方向不是缩短字符串本身，而是把长字符串中的宿主、坐标系、维度结构和维度子特征拆成结构化抽象特征节点与引用关系。自然语言输出时再组合为“某存在的场景绝对三维坐标 X 轴值”等可读称谓。

### 3.3 坐标轴约束的低级实现口径

`坐标轴数量 = 2` 不再作为二维坐标的必要显式子特征优先写入。二维坐标有 `第一轴 / 第二轴` 两个槽位时，轴数量可由结构推导。当前仍不引入通用 `OR / AND` 语义解析器，而是走固定槽位、值域和低级校验函数：

```text
1. 先建立抽象特征根链：
   坐标轴
       X轴
       Y轴
       Z轴
       1轴
       2轴
       ...

2. 在二维坐标或三维坐标定义下写固定槽位：
   二维坐标.第一轴
   二维坐标.第二轴
   三维坐标.第一轴
   三维坐标.第二轴
   三维坐标.第三轴

3. 每个轴槽位写值域：
   第一轴.值域 = 坐标轴集合
   第二轴.值域 = 坐标轴集合
   第三轴.值域 = 坐标轴集合

4. 低级校验只做明确检查：
   槽位数量符合二维 / 三维定义
   每个槽位值都属于 `坐标轴` 值域
   同一坐标定义内轴槽位值不重复
```

这里的“未赋值”只表示抽象定义没有限定具体轴，不让代码自动理解为可以直接任选。若后续确实需要自动选择轴，应作为一个明确方法执行：读取 `坐标轴` 子链、按确定规则选择 N 个、写回具体轴集合，并留下方法动作动态或运行证据；不把这一步藏在抽象特征匹配里。

### 3.4 轮廓、路径、点集等可变结构的审计口径

轮廓这类对象不应因为自然语言上能拆成很多点，就被审计为复合特征子链。它更适合作为一个特征类型，其值由整体结构承载：

```text
特征类型 = 轮廓
特征值 = VecI / VecIU64 / 点序列 / 掩码句柄 / 外部材料句柄
```

不建议表达为：

```text
轮廓
    点1
    点2
    点3
    ...
```

因为点数量可变，且点序列是值结构，不是稳定的抽象特征槽位。若需要判断轮廓性质，应派生为二次特征或低级计算结果：

```text
轮廓点数量
轮廓是否闭合
轮廓面积
轮廓外接矩形
轮廓中心点
轮廓相似度
```

因此后续审计遇到数组、vector、点云、路径、掩码、体素链等结构时，默认先判定为“整体特征值 + 解释视图”，只有固定槽位、数量稳定、语义稳定的组成项才进入复合特征子链。
