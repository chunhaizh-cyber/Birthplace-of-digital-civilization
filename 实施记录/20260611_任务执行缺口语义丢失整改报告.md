# 任务执行与本能方法缺口语义丢失整改报告

生成时间：2026-06-11

## 1. 结论

本次问题的根因不是 `6150` 或外设观察流程需要在任务执行层补一个等待分支，而是：

```text
方法动作内部已经产生了“当前方法条件不满足”的结构化事实，
但通用执行桥只把“方法执行情况 != 执行成功”折叠成普通执行失败码，
导致任务执行普通函数和工作线程回执层拿不到“方法前置/输入/供料缺口”的通用语义。
```

因此，整改不能在 `任务筹办`、`任务执行` 或工作线程执行推进里识别 `6150`、外设方法 ID、外设特征名，也不能在这两个普通函数中直接返回裸 `失败` / `执行失败` / `筹办失败` 之类的终止判断。本能方法也同样不能“返回错误码了事”：错误码只能作为兼容索引或显示码，不能替代运行存在 / 输出结果场景里的特征化事实。正确方向是补齐通用语义链：

```text
本能方法运行存在 / 方法运行存在 / 输出结果场景
-> 特征化缺口 / 特征化异常 / 特征化等待事实
-> 通用执行缺口类型
-> 通用运行结果码或运行结果分类
-> 任务执行推进回执
-> 任务状态建议 / 等待 / 派生需求 / 重筹办
```

`6150 提交_当前观察范围可观测单位存在对应事实` 只是暴露该缺口的自然样本，不应成为任务执行层的特殊分支。

## 2. 规范边界

依据：

```text
规范/规范目录.md
规范/任务筹办与执行边界规范20260512.md
规范/任务筹办按方法能力查找到就绪因果链规范20260513.md
计划/计划索引.md
```

必须保持的边界：

```text
1. 任务筹办 / 任务执行是任务管理生命周期普通函数，不进入方法树，不作为本能方法。
2. 任务筹办找路径、找方法、找条件，但不得按安全、服务、观察、外设等领域词硬编码前置目标。
3. 任务执行负责调用当前方法、取得输出结果场景和运行存在、形成过程回执，不直接写任务状态。
4. 任务状态变化仍必须走任务域被动状态动作 `提交任务状态变化`。
5. 方法前置条件、输入参数、外部供料等待等缺口必须由方法条件、条件结果对、输入包、运行存在或供料等待元信息表达。
6. 任务筹办 / 任务执行内部不得出现无闭环的裸判断；所有不能继续推进的信息都必须先被整理为特征信息、缺口类型、目标主体、当前状态、目标状态、来源方法、输入 / 输出场景引用等结构化回执事实。
7. 裸 `失败` 只能作为下游提交入口或显示层根据完整特征化事实作出的阶段判断；不得成为任务筹办 / 任务执行普通函数直接吐出的根语义。
8. 本能方法返回前必须写出可机器读取的运行存在特征：方法执行情况、失败原因或执行缺口类型、输入参数场景、输出结果场景、目标宿主、目标特征类型、当前状态 / 目标状态或异常类型。不得只返回 `本能动作错误_*`。
9. 本能动作错误码是兼容索引，不是闭环事实；缺动作入口、输入参数不满足、动作异常、方法首节点缺失等都必须落成特征化缺口或异常事实。
```

## 3. 代码证据链

### 3.1 任务执行只认少数缺条件运行码

`任务模块.执行.ixx` 中 `任务结果缺条件_最小_v0()` 只把两个运行码识别为缺条件：

```text
本能方法结果_任务缺条件需自我线程
本能动作错误_输入参数不满足
```

随后 `私有_按方法运行结果推导任务状态_最小_v0()` 只在上述缺条件码命中时建议 `等待中`；否则成功建议 `待重筹办`，失败建议 `失败`。

这说明任务执行普通函数没有能力从 `失败原因=执行缺口_当前方法条件不满足` 自行推导等待或前置缺口。

更严格地说，这段逻辑已经违反“所有信息先特征化再返回”的闭环要求：

```text
方法运行结果未被解析成：
    缺口类型
    缺口目标主体
    缺口当前状态
    缺口目标状态
    是否可等待
    是否需派生需求
    是否需重筹办

就直接返回：
    枚举_任务状态::失败
```

这不是可闭环回执，而是裸终止判断。

### 3.2 运行结果码折叠丢失失败原因语义

`本能动作管理类.ixx` 的 `本能动作运行结果值()` 读取顺序为：

```text
1. 读取 本能动作运行结果码；
2. 读取运行存在自身 I64 值；
3. 读取 方法执行情况；
4. 方法执行情况 == 执行成功 -> 0；
5. 其他方法执行情况 -> 本能动作错误_执行失败。
```

该函数没有读取 `失败原因`，也没有读取 `执行缺口类型`。所以当方法输出运行存在只写了：

```text
方法执行情况 = 执行失败
失败原因 = 执行缺口_当前方法条件不满足
```

上层得到的仍是普通：

```text
本能动作错误_执行失败
```

### 3.3 6150 已经写出条件不足事实，但没有把缺口语义升格为运行结果

`自我动作实现.外设模块.ixx` 中 `提交_当前观察范围可观测单位存在对应事实` 的逻辑已经计算：

```text
可写对应事实 = false
提交状态 = 条件不足
失败原因 = 执行缺口_当前方法条件不满足
方法执行情况 = 执行失败
```

并把提交状态、映射缺口、来源报告质量、目标实际结果状态等写入运行存在 / 输出结果场景 / 目标宿主。

但返回路径最终是 `输出运行虚拟存在(...)`。该输出运行存在不会统一写入 `本能动作运行结果码`，也没有把 `失败原因` 翻译成任务执行可识别的缺条件码。因此任务执行层读取时仍退化为普通失败。

### 3.4 工作线程已有外设特判，证明这是补丁方向

`任务模块.管理工作线程.ixx` 当前存在这些领域特判：

```text
私有_需求特征是外设观察供料等待特征_工作线程
私有_方法是外设观察供料等待本能_工作线程
私有_执行输出是外设观察供料等待缺口_工作线程
执行失败回执外设观察供料等待
```

它们通过“外设方法 ID + 外设特征名”把普通失败回执改成等待。这违反“任务筹办 / 执行都是通用逻辑”的边界，也说明真正缺失的是通用缺口语义，而不是外设等待分支。

### 3.5 筹办函数也存在“上报失败”语义外露

`任务模块.筹办.ixx` 中当前存在类似口径：

```text
学习本能真实单步入口缺口上报失败，等待入口提交链修复
已有真实单步本能入口缺口上报失败，等待入口提交链修复
方法状态可用性缺口生成失败
```

这些位置虽然大多仍会写 `等待中` 或结构缺口，但报告整改时必须继续收紧：筹办函数不能把“缺口生成失败 / 上报失败”作为返回根语义。它必须返回一个可闭环的特征化回执，例如：

```text
缺口特征类型 = 方法可执行入口数量 / 条件结果对数量 / 方法状态
缺口当前状态 = 缺失 / 未就绪 / 未提交
缺口目标状态 = 已存在 / 已就绪 / 已提交
处理建议 = 等待提交入口 / 重筹办 / 派生需求
闭环承接入口 = 提交_生成缺口子需求 / 提交任务状态变化 / 方法结构补齐提交入口
```

说明文本只能是日志 / 显示辅助，不能作为机器闭环判断字段。

### 3.6 本能动作管理层仍有错误码直返路径

`本能动作管理类.ixx` 当前定义了多类错误码：

```text
本能动作错误_未注册
本能动作错误_执行失败
本能动作错误_动作异常
本能动作错误_动作未知异常
本能动作错误_方法首节点缺失
本能动作错误_方法节点类型错误
本能动作错误_缺动作入口
本能动作错误_动作入口不归本类执行
本能动作错误_输入参数不满足
```

并在准备检查中多处直接走：

```text
return 设置结果(本能动作错误_输入参数不满足)
return 设置结果(本能动作错误_缺动作入口)
return 设置结果(本能动作错误_方法首节点缺失)
```

这些路径创建了带 `本能动作运行结果码` 的运行结果，但如果没有同步写出：

```text
执行缺口类型
失败原因
缺口目标主体
缺口当前状态
缺口目标状态
输入参数场景
输出结果场景
建议承接入口
```

上层仍只能读取一个错误码，无法判断是等待、补参数、补动作入口、补条件结果对、重筹办，还是登记真实异常。

因此，本能动作管理层也要从“错误码返回器”改为“特征化运行结果生成器”。错误码可以继续写入 `本能动作运行结果码`，但必须附带完整的特征化缺口 / 异常事实。

## 4. 根因判定

根因分三层：

```text
第一层：方法输出层
    失败原因已经写入，但缺少统一的“执行缺口类型”或运行结果码写入规则。

第二层：运行结果解释层
    本能动作运行结果值() 不读取失败原因 / 执行缺口类型，把非成功统一折叠为普通执行失败。

第三层：任务回执层
    任务执行普通函数和工作线程只能看到普通失败，只好靠外设特判把失败改回等待。

第四层：闭环承接层
    筹办 / 执行普通函数中仍存在裸失败或失败说明口径；
    这些口径没有强制携带“目标主体、目标特征、当前状态、目标状态、来源方法、承接入口”，
    因而不是完整闭环。

第五层：本能方法入口层
    本能动作管理层仍允许用 `本能动作错误_*` 作为主要返回；
    错误码缺少特征化上下文，不能独立支撑后续等待、补齐、派生需求或异常登记。
```

最终表现：

```text
方法内部知道“还缺输入材料 / 当前方法条件不满足”，
任务执行层却只知道“动作执行失败”。
```

更完整的根因表述是：

```text
任务筹办 / 任务执行还没有被约束为“特征化回执生产器”。
它们仍允许把过程断点压缩成枚举失败、文本失败或建议失败状态。
这样一来，上层无法稳定判断该等待、重筹办、派生需求、补方法结构，还是登记真实执行故障。

本能方法同样还没有被约束为“特征化运行结果生产器”。
它们仍允许把准备失败、输入缺口、动作入口缺口或动作异常压缩成错误码。
这样会把本能方法内部已经知道的缺口语义丢给上层猜。
```

## 5. 整改原则

```text
1. 不在任务筹办 / 任务执行中识别 6150。
2. 不在任务筹办 / 任务执行中识别外设特征名、外设方法 ID 或 D455。
3. 不把供料等待字段升级成任务层领域规则。
4. 不把条件不足伪装成成功。
5. 不把真实缺口直接生成为普通阻塞子需求；是否派生需求必须看通用缺口类型和提交入口要求。
6. 不新增说明性摘要字段作为机器判定依据。
7. 机器判定字段使用离散语义键、运行码、指针特征或已有特征，不依赖人类文本。
8. 任务筹办 / 任务执行返回前必须完成特征化：任何异常、缺口、不可执行、等待、重筹办、派生需求建议，都必须有可机器读取的特征类型 / 当前状态 / 目标状态 / 来源方法 / 输入输出场景引用。
9. 任务筹办 / 任务执行不得直接返回裸 `失败`；需要表达失败时，应返回“特征化缺口或异常事实 + 建议由哪个提交入口处理”。
10. `动作执行失败` 只能用于已经有完整方法运行存在、输出结果场景、失败原因、动作动态或错误日志证据的真实执行故障；不能用于输入缺口、条件缺口、等待供料、结构未闭合或回执生成不完整。
11. 本能方法不得只返回错误码；所有 `本能动作错误_*` 必须能映射到特征化运行结果事实。
12. 本能方法准备检查失败、动作入口缺失、输入参数不满足、动作异常，必须分别写出通用缺口类型或异常类型，供任务执行和工作线程读取。
```

## 6. 整改方案

### P0 撤出任务层外设特判

目标：

```text
任务模块.管理工作线程.ixx 不再用外设方法 ID + 外设特征名判断执行失败是否改为等待。
```

处理：

```text
1. 删除或停用 `私有_方法是外设观察供料等待本能_工作线程`。
2. 删除或停用 `私有_需求特征是外设观察供料等待特征_工作线程`。
3. 删除执行失败回执中的 `外设观察供料等待` 专用分支。
4. 保留外设等待项本身，但它只能由“方法供料要求 / 等待项元信息”维护，不进入任务执行回执的领域判断。
```

### P1 建立通用方法运行结果语义分类和特征化回执包

目标：

```text
把“运行结果码、方法执行情况、执行缺口类型、失败原因”统一翻译成通用分类；
同时要求分类结果必须携带特征化回执包，不能只返回枚举失败。
```

建议新增或收束为一个通用 helper：

```text
方法运行结果分类 = {
    成功,
    输入参数不满足,
    方法前置条件未满足,
    可等待供料缺口,
    需要自我线程补齐,
    普通执行失败,
    未知
}
```

该 helper 必须是方法层 / 执行桥通用逻辑，不属于任务筹办或外设模块。它的输出不能只有分类枚举，还应包含：

```text
缺口特征类型
缺口当前状态
缺口目标状态
缺口目标主体
来源方法
输入参数场景
输出结果场景
当前方法运行存在
是否存在等待承接证据
是否允许派生需求
建议承接入口
```

读取优先级建议：

```text
1. 显式 本能动作运行结果码；
2. 显式 执行缺口类型；
3. 显式 失败原因 中可稳定映射的离散语义键；
4. 方法执行情况；
5. 未知。
```

其中：

```text
失败原因 = 执行缺口_当前方法条件不满足
```

应映射为：

```text
方法前置条件未满足
```

并可在旧运行码兼容层折算为：

```text
本能动作错误_输入参数不满足
```

或新增更准确的通用运行码：

```text
本能动作错误_方法前置条件不满足
```

若新增运行码，必须同步调整 `任务结果缺条件_最小_v0()`，不能只改单个外设方法。

### P2 方法输出统一写执行缺口类型

目标：

```text
方法动作 / 本能方法内部只负责把真实运行事实写清楚，不负责决定任务状态。
```

通用写入规则：

```text
当方法动作判定不是执行失败故障，而是当前方法输入、前置条件、供料、目标材料暂不满足时：
    方法执行情况 = 执行失败
    失败原因 = 对应离散失败原因
    执行缺口类型 = 对应通用缺口类型

当本能动作管理层发现未注册、缺入口、方法首节点缺失、输入参数不满足或动作异常时：
    本能动作运行结果码 = 兼容错误码
    方法执行情况 = 执行失败 或 准备未满足
    失败原因 / 异常类型 = 对应离散语义键
    执行缺口类型 = 可补齐缺口或不可恢复异常
    输入 / 输出场景引用 = 尽量写入
```

对 `失败原因 = 执行缺口_当前方法条件不满足` 的现有方法，应统一补写：

```text
执行缺口类型 = 执行缺口_当前方法条件不满足
```

优先改通用写入 helper：

```text
写入双目相机通用结果(...)
写入本能方法自身环境失败(...)
通用方法输出结果写入 helper
本能动作运行结果创建 helper
```

不要逐个在 `6150`、`6145`、`扫描`、`跟踪` 方法里散落补丁。

尤其要改造：

```text
创建本能动作运行结果实例_按码(...)
本能动作管理类::检查方法运行准备(...)
本能动作管理类::执行功能函数(...)
```

这些入口不应只创建“错误码运行结果”，而应创建“错误码 + 特征化缺口 / 异常事实”的运行存在。

### P3 任务执行只读通用特征化回执

目标：

```text
任务执行普通函数仍然只做通用映射；
不得直接把未知 / 非成功压成裸失败。
```

建议规则：

```text
方法运行结果分类 == 成功：
    记账结果 = 成功
    建议任务状态 = 待重筹办

方法运行结果分类 in {输入参数不满足, 方法前置条件未满足, 可等待供料缺口, 需要自我线程补齐}：
    记账结果 = 未定义或待承接，按现有状态机最小兼容选择
    建议任务状态 = 等待中 或 待重筹办
    推进状况 = 方法前置条件未满足
    必须携带特征化缺口回执

方法运行结果分类 == 普通执行失败：
    只有在方法运行存在 / 输出结果场景 / 失败原因 / 错误日志或动作动态证据闭合时，才允许转入失败建议
    否则仍返回特征化异常回执，交由上层提交入口处理
    推进状况 = 动作执行失败
```

关键是任务执行只读“通用分类”，不读外设口径。

需要整改的直接点：

```text
`私有_按方法运行结果推导任务状态_最小_v0()` 不能在缺少特征化解析结果时 `return 枚举_任务状态::失败`。
`执行任务()` 不能仅凭 `本能动作运行成功(...) == false` 把记账结果置为失败。
```

应替换为：

```text
方法运行结果 -> 通用特征化回执包 -> 建议状态 / 记账结果 / 推进状况
```

### P4 工作线程按通用缺口生成回执

目标：

```text
工作线程执行推进回执不再从外设方法/特征判断等待。
```

建议映射：

```text
执行缺口类型 = 当前方法条件不满足：
    回执.状况 = 方法前置条件未满足
    回执.缺口特征类型 = 通用缺口类型或方法条件缺口特征
    回执.需要创建或复用子需求 = false，除非方法输出明确给出派生需求特征 / 当前状态 / 目标状态
    回执.建议任务状态 = 等待中 或 待重筹办，依据是否存在等待项/供料元信息

存在等待承接证据：
    保留等待，等待外部供料或下一轮真实输入

不存在等待承接证据，但存在可任务化缺口：
    按通用派生需求入口构造派生需求消息

既无等待证据，也无可派生缺口：
    先归为特征化异常回执；
    只有错误证据闭合后，才归为普通动作执行失败
```

“等待承接证据”应来自通用等待项 / 方法供料要求 / 当前工作项元信息，而不是外设特征名。

### P5 保持界面线程供料适配边界

界面线程当前按“当前方法结果能力 / 方法供料要求”创建外设等待项的方向可以保留，但必须表述为：

```text
方法供料适配
```

不能表述为：

```text
任务执行认识外设方法
```

也就是说，外设只作为方法供料口径配置存在。任务执行看到的仍是通用“当前方法条件不满足 / 可等待供料缺口”。

### P6 筹办函数改为闭环特征化返回

目标：

```text
任务筹办普通函数的每个早退分支，都必须返回闭环特征化回执。
```

最低字段：

```text
推进状况
建议任务状态
建议任务阶段
当前任务
对应需求
当前方法
候选方法集
缺口特征类型
缺口目标主体
缺口当前状态
缺口目标状态
需要自我线程
需要创建或复用子需求
父任务需要重筹办
承接入口 / 获取途径
```

整改点：

```text
凡是当前写“缺口上报失败 / 生成失败 / 执行失败”的分支，
必须改为“缺口回执构造不完整”或“提交入口待承接”的特征化状态，
并补齐可继续处理的目标特征和承接入口。
```

说明：

```text
文本 `说明` / `摘要` 可以保留给日志，
但机器判断必须读上述特征化字段。
```

### P7 本能方法返回改为闭环特征化运行结果

目标：

```text
本能方法和本能动作管理层返回的运行结果，必须是可闭环运行存在。
```

最低字段：

```text
本能动作运行结果码
方法执行情况
失败原因 / 异常类型
执行缺口类型
当前方法
方法虚拟存在
输入参数场景
输出结果场景
目标宿主
目标特征类型
当前状态
目标状态
动作动态或异常日志引用
建议承接入口
```

错误码使用规则：

```text
错误码只用于兼容旧读取路径、排序、快速判断或显示。
错误码不得是唯一机器事实。
任何读取错误码的上层逻辑，都必须能进一步读取运行存在特征化事实。
```

映射建议：

```text
本能动作错误_输入参数不满足
    -> 执行缺口类型=输入参数不满足 / 当前方法条件不满足

本能动作错误_缺动作入口
    -> 执行缺口类型=方法缺可执行入口

本能动作错误_方法首节点缺失 / 方法节点类型错误
    -> 异常类型=方法结构异常，需错误日志和弹错

本能动作错误_动作异常 / 动作未知异常
    -> 异常类型=动作运行异常，需错误日志和异常证据

本能动作错误_执行失败
    -> 仅在已写清真实执行失败原因、动作动态或异常日志后使用
```
