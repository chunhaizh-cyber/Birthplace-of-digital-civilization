## 2. 用户对当前流程的解读

当前图不是单纯的需求生成流程，而是完整闭环：

```text
需求前材料发现
    -> 目标归一
    -> 入树裁决
    -> 任务化推进
    -> 结果验证
    -> 满足回写
    -> 父链 / 根状态重判
```

### 2.1 模块 1：来源发现

模块 1 是“需求前材料发现”，不是正式需求生成。

来源包括：

```text
根特征缺口
自检 / 主动报送
身体反馈 / 观察反馈
任务筹办缺口
执行缺口
子需求完成后的父目标回查信号
```

输出包括：

```text
候选
报告
草案
回查信号
```

禁止误读为：

```text
已经生成正式需求。
```

### 2.2 模块 2：目标归一与消息规范化

模块 2 是翻译层，不是裁判层。

核心作用：

```text
乱七八糟的缺口材料
    -> 统一的入树请求材料
```

现有正确点：

```text
1. 自检 / 反馈候选先识别是否为代码缺陷型报告。
2. 非代码缺陷型材料再检查原子目标完整性。
3. 筹办 / 执行派生草案构造成 结构_任务管理派生需求消息。
4. 消息需补主键槽、同步语义槽、生成幂等键。
5. 外设内部材料字段和仅参数诊断需要过滤。
```

### 2.3 模块 3：自我线程入树裁决

模块 3 是正式需求边界，应视为“海关”。

正式需求只能在这里盖章进入统一需求树。

现有正确点：

```text
1. 新增原子需求指令进入 需求类::执行更新指令。
2. 派生需求消息先由自我线程接收。
3. 派生需求消息经 私有_确保派生需求节点 进入入树闸门。
4. 闸门检查父需求、来源因果 / 动态、当前状态、目标状态、目标特征、目标主体。
5. 闸门处理外设内部材料字段、父子目标自复制等问题。
6. 通过后才复用、合并或新增需求节点。
```

### 2.4 模块 4：任务化与任务推进

模块 4 不是“需求生成”，而是“需求兑现”。

但它会产生新的派生需求材料，所以会反向参与需求生成。

关键链路：

```text
正式需求节点
    -> 服务优先 / 安全优先需求列表
    -> 当前主需求候选
    -> 可任务化叶子需求
    -> 创建或复用任务头 / 任务虚拟存在
    -> 任务管理工作线程筹办
    -> 路径筹办 / 临时因果视图
    -> 方法筹办 / 候选方法选择 / 条件参数入口检查
    -> 方法执行
    -> 若目标未达成，形成执行缺失回执或派生需求草案
    -> 回到模块 2
```

### 2.5 模块 5：满足回写与父链重判

模块 5 是闭环锁扣。

关键边界：

```text
子需求完成不等于父需求满足，必须回查父目标特征。
```

否则系统会误把子任务完成当作需求树真实闭合。

## 3. 主要优点记录

```text
1. 正式需求入口唯一。
2. 任务管理侧不越权。
3. 候选、缺口、报告、派生消息被分层处理。
4. 子需求完成不直接推导父需求满足。
5. 闭环方向清楚，执行失败、筹办缺口、证据不足会回到模块 1 或模块 2。
```

## 5. 建议修订后的核心流程

后续可将最终口径压缩为：

```text
1. 来源发现
   读取根状态、自检、身体反馈、观察反馈、筹办缺口、执行缺口、父目标回查信号。
   输出：需求前材料。

2. 目标归一
   将需求前材料翻译成原子目标或派生需求消息。
   检查父域、目标宿主、目标特征、当前状态、目标状态、满足关系。
   通过三态比较确认确有差距。
   输出：入树请求。

3. 自我裁决入树
   自我线程校验来源、权限、父需求、因果 / 动态、目标主体和幂等键。
   复用、合并或新增需求。
   只有通过 需求类::执行更新指令 后才形成正式需求节点。

4. 任务化推进
   只对普通可任务化叶子需求创建 / 复用任务。
   筹办查因果、补参数、选方法。
   缺口生成派生需求消息，并挂起来源任务等待闭合。
   就绪后执行方法，输出结果场景、运行存在、动作动态。

5. 结果验证
   区分内部治理事实与外设观察事实。
   检查证据来源、时间、新鲜度、版本、可归因性。
   可信后才进入需求满足判断。

6. 满足回写
   来源需求满足后退出活动集。
   满足不等于父满足，必须回查父目标特征。
   满足不等于价值结算，结算必须过安全 / 服务硬闸门。

7. 父链和根状态重判
   父目标未达成则父任务重筹办。
   父目标达成则继续向上回查。
   最后刷新根状态、主需求和调度摘要。
```

## 7. 拒绝回执治理闭环补充

本节记录用户对“拒绝回执不能只记录日志”的补充口径。

### 7.1 核心原则

```text
拒绝普通需求化
    ≠ 不处理

拒绝入树
    = 进入“拒绝回执治理闭环”
```

新增原则：

```text
任何拒绝回执都必须有后续处理状态。
拒绝不是终态，闭合处理才是终态。
```

因此：

```text
可以拒绝入普通需求树；
不可以拒绝后无处理。
```

拒绝回执应从：

```text
拒绝原因
```

升级为：

```text
拒绝原因 + 后续处理策略 + 处理结果
```

### 7.2 拒绝回执的定义

建议定义：

```text
需求入树拒绝回执 =
    某个需求前材料未能进入普通需求树时，
    自我线程生成的治理事件。
```

职责：

```text
1. 说明为什么不能普通需求化。
2. 决定由谁处理。
3. 决定是否可以自动修复。
4. 决定是否重提入树。
5. 决定是否合并 / 冷却 / 隔离 / 转学习 / 转诊断。
6. 最终形成闭合状态。
```

### 7.3 建议新增模块 3.5

当前 v0.2 结构：

```text
模块 3：自我线程入树裁决
    -> 正式需求节点
    -> 拒绝 / 暂存结果
```

建议改为：

```text
模块 3：自我线程入树裁决
    -> 正式需求节点
    -> 需求入树拒绝回执

模块 3.5：拒绝回执治理处理
    -> 修复后重提
    -> 合并既有需求
    -> 转来源任务内部处理
    -> 转学习 / 观察 / 验证缺口
    -> 转代码诊断 / 禁用路径
    -> 冷却闭合
    -> 人类介入 / 开发处理
```

接口 C 建议从：

```text
正式需求节点
或
拒绝 / 暂存结果
```

改为：

```text
正式需求节点
或
已进入治理闭环的拒绝回执
```

```cpp
    I64 冷却截止时刻 = 0;
    int 已重试次数 = 0;
    int 最大重试次数 = 3;

    I64 生成时需求树版本 = 0;
    I64 生成时来源任务版本 = 0;
    I64 处理完成版本 = 0;
};
```

重点新增字段：

```text
后续处理类型
处理状态
关联既有需求ID
关联既有任务ID
关联诊断项ID
已重试次数
最大重试次数
```

### 7.5 拒绝原因处理表

| 拒绝原因 | 能否忽略 | 后续处理方案 | 闭合标准 |
| --- | --- | --- | --- |
| 字段缺失 | 否 | 若可从来源任务 / 来源需求 / 动态补齐，则自动补槽后重提；否则退回来源模块补槽，来源任务挂起 | 补齐后重提成功，或来源模块确认无法补齐并转诊断 |
| 父需求非法 | 否 | 尝试重新判定父域；能归入安全 / 服务 / 学习 / 内部治理父域则重提；不能则转代码诊断 | 找到合法父需求，或隔离生成路径 |
| 父为结构根 | 否 | 禁止直接挂结构根；根据目标特征映射到安全根 / 服务根 / 方法补全父域 | 改挂合法父域后重提，或生成父域判定缺口 |
| 目标主体不可判定 | 否 | 外部事实转观察 / 识别缺口；内部事实转读取虚拟存在 / 任务状态；都不可判定则退回来源模块 | 主体明确，或来源路径被隔离 |
| 目标特征缺失 | 否 | 若是消息漏填则补槽；若抽象特征不存在则转特征定义 / 方法补全 / 学习缺口 | 目标特征明确，或转诊断 |
| 当前状态缺失 | 否 | 外部现实状态缺失则生成观察验证；内部治理状态缺失则读取任务 / 方法虚拟存在；材料缺失则退回来源 | 当前状态获得，或确认不可观测 |
| 目标状态缺失 | 否 | 回到定义展开 / 临时因果视图，重新构造目标状态；不能构造则转规则缺陷诊断 | 目标状态明确，或规则缺陷入账 |
| 来源因果不可解析 | 否 | 重建临时因果视图；若因果缺失则转学习缺口；若引用损坏则转数据修复 | 因果可解析，或学习任务入树 |
| 来源动态不可解析 | 否 | 读取动作动态 / 结果场景；若动态缺失，来源任务不得结算，转执行记录修复 | 动态可解析，或任务结果作废 |
| 外设内部材料字段 | 否 | 不进入普通需求树；转外设材料仓库 / 方法内部数据处理 / 观察结果包修复 | 材料字段被内部处理，或来源任务降级 |
| 参数诊断不需求化 | 否 | 不生成普通需求；转参数绑定重试 / 参数映射学习 / 方法筹办重跑 | 参数闭合，或方法候选降权 |
| 父子目标自复制 | 否 | 取消该派生草案；来源任务重筹办；若重复出现，隔离该生成规则 | 自复制链断开 |
| 同批重复 | 可以不新增 | 合并到同批既有候选 / 需求，补证据计数 | 已合并，不再重复派生 |
| 近期重复 | 可以不新增 | 进入冷却；绑定既有未闭合需求 / 任务；增加重复压力计数 | 冷却关闭或既有需求闭合 |
| 代码缺陷型报告 | 否 | 不进普通需求树；生成开发诊断项，禁用相关路径或降级运行，必要时通知人类 | 诊断项建立，路径已隔离或等待修复 |

补充边界：

```text
同批重复 / 近期重复不是忽略，而是不新增需求。
必须合并证据、绑定既有节点或进入冷却闭合。
```

### 7.6 代码缺陷型报告闭环

代码缺陷型报告通常不应进入普通需求树，因为普通需求树是运行期目标治理，不是源码修复系统。

但“待处理”不能停在文本层，应转为：

```text
代码缺陷型报告
    -> 生成开发诊断项
    -> 禁用或降级相关生成路径
    -> 阻止同类错误继续派生
    -> 通知权限者 / 开发者
    -> 若系统具备自修改能力，再转代码修复任务
```

运行期闭合标准：

```text
1. 错误路径不继续污染需求树。
2. 来源任务知道自己失败原因。
3. 系统不会无限重试。
4. 人类或开发者能看到明确诊断项。
5. 修复后有复验入口。
```

### 7.7 不进入普通需求树的合法闭合

#### 外设内部材料字段

处理方向：

```text
转外设材料处理
或
转方法内部材料依赖
或
挂到观察结果包
```

闭合标准：

```text
来源任务拿到材料句柄
或
来源任务确认材料不可用并生成观察质量缺口
```

#### 参数诊断

处理方向：

```text
参数绑定重试
参数映射学习
方法候选降权
任务重筹办
```

闭合标准：

```text
参数绑定成功
或
候选方法被判定不可用
或
转学习任务
```

#### 重复项

处理方向：

```text
合并证据
增加重复计数
绑定既有需求 / 任务
更新最后出现时间
```

闭合标准：

```text
重复材料已经归并到既有对象
```

### 7.8 拒绝回执处理流程

建议流程：

```text
入树请求失败
    ↓
生成 需求入树拒绝回执
    ↓
按拒绝原因选择处理策略
    ↓
是否可自动处理？
    ├─ 是：
    │   ├─ 补槽 / 合并 / 重定向 / 冷却 / 转学习 / 转观察
    │   └─ 验证处理结果
    │       ├─ 成功：关闭回执
    │       └─ 失败：增加重试次数或升级
    │
    └─ 否：
        ├─ 生成诊断项
        ├─ 隔离来源路径
        ├─ 挂起来源任务
        └─ 请求人类 / 开发者处理

所有分支最终必须写入：
    回执处理状态
    处理结果
    关联对象
    是否允许再次派生
```

伪代码草案：

```cpp
void 处理需求入树拒绝回执(结构_需求入树拒绝回执& r) {
    auto 策略 = 根据拒绝原因选择策略(r.拒绝原因);

    r.后续处理类型 = 策略.处理类型;
    r.是否可自动处理 = 策略.可自动处理;
    r.是否可重试 = 策略.可重试;

    switch (策略.处理类型) {
    case 自动补槽后重提:
        if (尝试补齐字段(r)) {
            r.处理状态 = 已补槽重提;
            重提入树请求(r);
        } else {
            升级为来源模块补槽或诊断(r);
        }
        break;

    case 合并到既有需求:
        合并证据到既有需求(r);
        r.处理状态 = 已合并;
        break;

    case 转观察验证缺口:
        生成观察验证材料(r);
        r.处理状态 = 已转观察验证;
        break;

    case 转学习缺口:
        生成学习缺口材料(r);
        r.处理状态 = 已转学习;
        break;

    case 转方法内部处理:
        绑定到来源任务或方法虚拟存在(r);
        r.处理状态 = 已转来源任务内部处理;
        break;

    case 转代码诊断:
        建立开发诊断项(r);
        禁用或降级来源路径(r);
        r.处理状态 = 已转代码诊断;
        break;

    case 冷却后关闭:
        绑定既有对象并设置冷却(r);
        r.处理状态 = 已冷却关闭;
        break;

    default:
        r.处理状态 = 处理失败;
        break;
    }

    写入拒绝回执账本(r);
}
```

### 7.9 来源任务必须接收拒绝回执

规则建议：

```text
派生需求消息被拒绝后：
    来源任务不得继续按原路径重复筹办；
    必须根据拒绝回执进入对应状态。
```

来源任务状态候选：

```text
等待派生需求入树
派生需求被拒绝_等待补槽
派生需求被拒绝_已合并既有
派生需求被拒绝_转学习
派生需求被拒绝_转观察验证
派生需求被拒绝_来源路径隔离
派生需求被拒绝_需重筹办
```

### 7.10 可写入规范的最终规则候选

```text
拒绝回执闭环规则：

1. 入树拒绝不是终态。
2. 任意入树拒绝必须生成结构_需求入树拒绝回执。
3. 拒绝回执必须进入拒绝回执治理处理器。
4. 拒绝回执必须形成以下终态之一：
   - 已补槽重提
   - 已合并既有需求 / 任务
   - 已转来源任务内部处理
   - 已转观察验证缺口
   - 已转学习缺口
   - 已转代码诊断
   - 已隔离来源路径
   - 已冷却关闭
   - 已请求人类 / 开发者处理
5. 禁止静默忽略。
6. 禁止仅记录日志但不改变任何治理状态。
7. 禁止将代码缺陷、外设内部材料字段、参数诊断强行普通需求化。
8. 来源任务必须接收派生需求入树成功或拒绝回执，并据此挂起、重筹办、降权、转学习或终止路径。
```

### 7.11 补充后的最终判断

```text
拒绝入树可以，但拒绝治理不可以。
```

分类处理方向：

```text
普通目标缺口
    -> 进入普通需求树

学习 / 方法缺口
    -> 进入学习或方法补全路径

观察 / 证据缺口
    -> 进入观察验证路径

参数 / 外设材料缺口
    -> 回到来源任务或方法内部处理

重复项
    -> 合并 / 冷却

代码缺陷
    -> 诊断 / 隔离 / 通知 / 等待修复
```

一句话口径：

```text
系统可以说“这不是一个普通需求”，但必须继续说清楚：
它转给谁、怎么处理、什么时候关闭、失败后如何升级。
```
