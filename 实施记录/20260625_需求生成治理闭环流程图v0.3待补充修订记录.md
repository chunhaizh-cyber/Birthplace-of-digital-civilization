## 2. 用户对当前流程的解读

当前图不是单纯的需求生成流程，而是完整闭环：

```text
需求前材料发现
    -> 目标归一
    -> 入树裁决
    -> 任务化推进
    -> 结果验证
    -> 满足回写
    -> 父链 / 根状态重判
```

### 2.1 模块 1：来源发现

模块 1 是“需求前材料发现”，不是正式需求生成。

来源包括：

```text
根特征缺口
自检 / 主动报送
身体反馈 / 观察反馈
任务筹办缺口
执行缺口
子需求完成后的父目标回查信号
```

输出包括：

```text
候选
报告
草案
回查信号
```

禁止误读为：

```text
已经生成正式需求。
```

### 2.2 模块 2：目标归一与消息规范化

模块 2 是翻译层，不是裁判层。

核心作用：

```text
乱七八糟的缺口材料
    -> 统一的入树请求材料
```

现有正确点：

```text
1. 自检 / 反馈候选先识别是否为代码缺陷型报告。
2. 非代码缺陷型材料再检查原子目标完整性。
3. 筹办 / 执行派生草案构造成 结构_任务管理派生需求消息。
4. 消息需补主键槽、同步语义槽、生成幂等键。
5. 外设内部材料字段和仅参数诊断需要过滤。
```

### 2.3 模块 3：自我线程入树裁决

模块 3 是正式需求边界，应视为“海关”。

正式需求只能在这里盖章进入统一需求树。

现有正确点：

```text
1. 新增原子需求指令进入 需求类::执行更新指令。
2. 派生需求消息先由自我线程接收。
3. 派生需求消息经 私有_确保派生需求节点 进入入树闸门。
4. 闸门检查父需求、来源因果 / 动态、当前状态、目标状态、目标特征、目标主体。
5. 闸门处理外设内部材料字段、父子目标自复制等问题。
6. 通过后才复用、合并或新增需求节点。
```

### 2.4 模块 4：任务化与任务推进

模块 4 不是“需求生成”，而是“需求兑现”。

但它会产生新的派生需求材料，所以会反向参与需求生成。

关键链路：

```text
正式需求节点
    -> 服务优先 / 安全优先需求列表
    -> 当前主需求候选
    -> 可任务化叶子需求
    -> 创建或复用任务头 / 任务虚拟存在
    -> 任务管理工作线程筹办
    -> 路径筹办 / 临时因果视图
    -> 方法筹办 / 候选方法选择 / 条件参数入口检查
    -> 方法执行
    -> 若目标未达成，形成执行缺失回执或派生需求草案
    -> 回到模块 2
```

### 2.5 模块 5：满足回写与父链重判

模块 5 是闭环锁扣。

关键边界：

```text
子需求完成不等于父需求满足，必须回查父目标特征。
```

否则系统会误把子任务完成当作需求树真实闭合。

## 3. 主要优点记录

```text
1. 正式需求入口唯一。
2. 任务管理侧不越权。
3. 候选、缺口、报告、派生消息被分层处理。
4. 子需求完成不直接推导父需求满足。
5. 闭环方向清楚，执行失败、筹办缺口、证据不足会回到模块 1 或模块 2。
```


### 4.3 模块 2 / 模块 3 增加统一拒绝回执

建议定义：

```text

    来源材料ID

    拒绝阶段
    拒绝原因类型
    是否可重试
```

拒绝原因候选：

```text

代码缺陷型报告
```

用途：

```text
让下一轮扫描知道缺口是暂时不能入树、永远不能入树，还是补证据后可重试。
```

### 4.5 模块 5 拆出“结果事实验证”

在“来源需求满足？”前增加：

```text

```

分支建议：


目标：



## 5. 建议修订后的核心流程

后续可将最终口径压缩为：

```text
1. 来源发现
   读取根状态、自检、身体反馈、观察反馈、筹办缺口、执行缺口、父目标回查信号。
   输出：需求前材料。

2. 目标归一
   将需求前材料翻译成原子目标或派生需求消息。
   检查父域、目标宿主、目标特征、当前状态、目标状态、满足关系。
   通过三态比较确认确有差距。
   输出：入树请求。

3. 自我裁决入树
   自我线程校验来源、权限、父需求、因果 / 动态、目标主体和幂等键。
   复用、合并或新增需求。
   只有通过 需求类::执行更新指令 后才形成正式需求节点。

4. 任务化推进
   只对普通可任务化叶子需求创建 / 复用任务。
   筹办查因果、补参数、选方法。
   缺口生成派生需求消息，并挂起来源任务等待闭合。
   就绪后执行方法，输出结果场景、运行存在、动作动态。

5. 结果验证
   区分内部治理事实与外设观察事实。
   检查证据来源、时间、新鲜度、版本、可归因性。
   可信后才进入需求满足判断。

6. 满足回写
   来源需求满足后退出活动集。
   满足不等于父满足，必须回查父目标特征。
   满足不等于价值结算，结算必须过安全 / 服务硬闸门。

7. 父链和根状态重判
   父目标未达成则父任务重筹办。
   父目标达成则继续向上回查。
   最后刷新根状态、主需求和调度摘要。
```
