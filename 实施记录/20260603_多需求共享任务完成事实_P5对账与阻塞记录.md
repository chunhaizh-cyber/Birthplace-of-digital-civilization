# 多需求共享任务完成事实 P5 对账与阻塞记录

日期：2026-06-03

对应计划：

```text
计划/20260603_被动动作因果桥与结算动态统一结构修订计划_v0.1.md
P5 多需求共享任务完成事实结算
```

## 1. 修正后的口径

本轮按以下口径继续检查：

```text
1. 任务有对应的需求结点。
2. 需求列表负责把同类 / 同目标需求材料汇总，并保留需求树结点引用。
3. 当一个任务完成时，先完成该任务自身结算。
4. 自身结算内部包含自身对应需求、父任务缺口满足程度判断、父需求 / 父任务链收束。
5. 自身结算完成后，才通过需求列表找到同目标或同需求语义的其它需求树结点。
6. 横向候选之间按任务权重高者优先。
7. 对每个候选需求结点，回到它自己的对应任务或任务列表，按“需求 + 其父链 / 父缺口处理”作为独立结算单元判断是否可被本次完成事实被动收束。
```

因此，P5 的问题不是“任务没有需求归属”，也不是“需求列表没有需求树结点”。

## 2. 当前已有代码材料

需求列表项保存需求树结点：

```text
自我线程模块.ixx
结构_需求列表项

需求节点指针
需求节点主键
节点安全权重
节点服务权重
类型安全权重汇总
类型服务权重汇总
```

需求列表构建会把需求树结点写入列表项：

```text
自我线程模块.impl.cpp
私有_从需求树构建需求列表(...)

列表项.需求节点指针 = reinterpret_cast<std::uintptr_t>(节点)
列表项.需求节点主键 = 节点->获取主键()
```

需求列表的汇总权重已经是排序 / 优先级用途：

```text
类型安全权重汇总
类型服务权重汇总
```

正式结算不得把这两个汇总字段当成结算预算。

需求类已有同目标重叠判断材料：

```text
需求类.h
生成需求目标键_已加锁(...)
需求目标重叠_已加锁(...)
查找直接子需求_按目标重叠_已加锁(...)
```

子需求权重刷新已按新口径：

```text
OR关系：
    每个活跃子需求继承父需求权重。

AND关系：
    活跃子需求平分父需求权重。
```

## 3. 当前已存在的近似收束链

代码里已有一个收束已完成叶需求的扫描：

```text
自我线程模块.impl.cpp
私有_收束已完成叶需求_线程侧(...)
```

它会扫描需求树叶子需求，找到该需求自己的对应任务或任务列表中已完成 / 已结算的任务，然后调用：

```text
私有_处理任务满足反馈_线程侧(...)
```

这说明当前系统已经承认：

```text
需求树结点 -> 对应任务 / 任务列表 -> 完成任务 -> 需求收束
```

但这条链只处理“该需求自己的任务已经完成”的情况。

## 4. P5 仍缺的自动桥

P5 要处理的是另一种情况：

```text
任务 A 完成
-> 完成 A 自身结算（自身对应需求 + 父缺口满足程度 + 父需求 / 父任务链收束）
-> A 的实际结果同时满足需求 B / C
-> B / C 各自有对应任务 B_task / C_task
-> B_task / C_task 应该被被动收束
```

当前结果消息主链仍只处理任务自己的来源需求：

```text
自我线程模块.impl.cpp
私有_按成功结果满足来源需求并唤醒父任务_任务管理新链(...)

auto* 来源需求 = 私有_任务来源需求_线程侧(任务头);
...
私有_处理任务满足反馈_线程侧(..., 任务头, ...)
```

缺少的桥是：

```text
任务 A 的来源需求结点
-> A 自身结算内部完成 D1 / D2 判断、父缺口满足程度判断、父需求 / 父任务链收束
-> 需求列表中同目标 / 同需求语义的其它需求树结点
-> 横向候选按任务权重高者优先
-> 这些需求结点各自的对应任务
-> 判断这些对应任务是否可由 A 的完成事实被动完成 / 已结算
-> 对每个横向候选分别按“需求 + 其父链 / 父缺口处理”走回写需求满足 D1 和结算 D2
```

## 5. 当前真正阻塞点

P5 不能直接实现为“枚举候选需求后循环调用结算”，因为结算被动因已经按 P3 固定为：

```text
任务虚拟存在.任务状态 = 已结算
```

对于任务 A 自己，这个被动因已经由结算前提交链补齐。

但对于候选需求 B / C 的对应任务，当前没有自动代码证明：

```text
任务 A 完成
-> B_task / C_task 被动进入 完成
-> B_task / C_task 被动进入 已结算
-> 生成各自任务状态动作动态
-> 再生成各自 D2 结算动态
```

也就是说，需求列表能找到候选需求结点和对应任务；真正缺的是：

```text
同目标任务被动完成 / 已结算提交桥
```

按照被动动作检查口径：

```text
只要被动因出现，被动果必须自动出现；
检查方式必须看代码里是否存在因到果的自动执行路径。
```

这条桥当前还没有完整代码路径。

## 6. 下一步建议

先补 P5a：

```text
P5a 同目标需求候选扫描与被动完成桥
```

最小内容：

```text
1. 以完成任务 A 的来源需求为锚点，先进入 A 自身结算。
2. A 自身结算内部完成 D1 / D2 判断、父缺口满足程度判断、父需求 / 父任务链收束。
3. 如果被满足缺口相对完成前没有变化，则自身结算不进入核心安全 / 服务值结算。
4. 自身结算完成后，从服务 / 安全需求列表中收集同目标需求结点。
5. 对每个候选需求结点，解析它自己的对应任务和任务列表。
6. 横向候选任务按任务权重高者优先。
7. 如果候选任务已经完成 / 已结算，则按“需求 + 其父链 / 父缺口处理”进入既有结算链。
8. 如果候选任务未完成，但 A 的 actual 结果可满足候选需求目标，则通过任务状态提交链把候选任务被动推进到完成。
9. 完成状态动作动态生成后，再进入已结算提交和 D2 结算。
10. OR 路径仍必须先检查或提交 OR 组结算令牌；未取令牌不得进入核心安全 / 服务值结算。
```

然后再补 P5b：

```text
P5b 多候选需求逐路径结算
```

验收：

```text
同一任务完成事实可以解释多个需求；
每条需求路径使用自己的需求结点和对应任务；
需求列表汇总权重只用于优先级；
正式结算预算来自各需求结点权重和任务承接权重固化；
横向结算按任务权重高者优先；
横向候选各自仍以“需求 + 其父链 / 父缺口处理”为独立结算单元；
OR 路径未取得令牌时不结算核心安全 / 服务值。
```
