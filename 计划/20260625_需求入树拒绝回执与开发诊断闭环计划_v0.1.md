## 1. 目标

把需求入树拒绝从“日志 / 弹错 / 暂存”升级为结构化闭环：

```text
入树请求
    -> 自我线程裁决
    -> 成功：正式需求节点
    -> 拒绝：结构化拒绝回执
    -> 按闭环类型处理
    -> 来源任务接收结果并停止原路径重复派生
```

同时把代码缺陷型拒绝单独拆出：

```text
代码缺陷型拒绝
    -> 开发诊断项
    -> 来源路径隔离
    -> 来源任务实现缺陷阻断回执
    -> 日志 / 弹窗 / 报错 / 通知开发者
    -> 代码修正 + 编译 + 回归
    -> 关闭诊断项
```

## 2. 不解决什么

```text
1. 本计划不把代码缺陷普通需求化。
2. 本计划不把任务筹办 / 任务执行恢复成本能方法。
3. 本计划不新增文本字段参与机器判断。
4. 本计划不宣称当前代码已经实现拒绝回执闭环或开发诊断闭环。
5. 本计划不改变 P13b 当前主动执行顺序；只有用户明确切入或该缺口阻塞当前需求类切片时才执行。
```

### P1：拒绝原因与策略表设计

目标：

```text
1. 在需求类或对应治理协议中定义拒绝原因、拒绝闭环类型、处理状态。
2. 建立“拒绝原因 -> 处理策略”的结构化映射。
3. 保证新增拒绝原因必须同时补处理方案。
4. 区分规范缺口、可治理拒绝和代码缺陷，不把无处理方案的拒绝原因一律打成开发诊断。
5. 处理器必须检查拒绝回执是否进入合法终态。
```

验收：

```text
1. 枚举值都有策略映射。
2. 没有只返回文本或只写日志的拒绝路径。
3. Debug x64 构建通过。
```

### P2：拒绝回执结构和账本

目标：

```text
1. 增加结构化拒绝回执。
2. 回执携带来源材料、来源任务、来源需求、来源方法、幂等键、版本号、闭环类型、处理状态。
3. 拒绝回执能被来源任务读取。
4. 拒绝回执账本只记录状态和证据；主动转派由拒绝回执治理处理器执行。
```

验收：

```text
1. 入树拒绝路径生成回执。
2. 回执能绑定来源任务或关联既有对象。
3. 同批重复和近期重复能合并 / 冷却，不新增需求。
```

### P3：开发诊断闭环

目标：

```text
1. 代码缺陷型拒绝生成开发诊断项。
2. 来源任务收到实现缺陷阻断回执。
3. 来源路径被阻断、降级或隔离。
4. 关闭诊断项必须要求代码修正、编译和回归证据。
5. 运行期处理只做到诊断、隔离、报告和阻断；开发期修复验证负责关闭诊断项。
```

验收：

```text
1. 空指针、非法枚举、结构损坏、状态机非法跳转等不能普通需求化。
2. 同一路径不重复污染需求树。
3. Debug x64 构建通过。
4. 真实运行日志能看到诊断项建立、路径隔离和来源任务阻断。
```

### P4：来源任务等待和重筹办承接

目标：

```text
1. 来源任务在派生需求上报后进入等待入树结果状态。
2. 入树成功时等待派生需求完成。
3. 可治理拒绝时按回执补槽、转学习、转观察或重筹办。
4. 开发诊断拒绝时进入实现缺陷阻断。
5. 派生需求满足后，来源任务必须恢复并重新筹办；派生需求失败或被拒绝时按回执重筹办或停止路径。
```

验收：

```text
1. 不再出现同一任务同一路径重复生成同一派生需求消息。
2. 来源任务状态变化有结构化证据。
3. 真实运行日志能复核状态推进。
```

### P5：结果验证、结算闸门和父链重判联动

目标：

```text
1. 结果事实可信性验证先于需求满足判断。
2. 价值结算硬闸门先于安全 / 服务值入账，最低条件包括叶子需求、目标真实满足、结果可验证、动作可归因、未重复入账、属于安全 / 服务可结算域。
3. 子需求满足后必须回查父目标特征。
```

验收：

```text
1. 证据不足不被写成需求满足。
2. 任务完成不直接触发价值结算。
3. 父目标未达成时能触发父任务重筹办。
```
