## 1. 本计划解决什么

本计划目标是把需求树生成和内部治理闭环收束为一条可实现、可验收的主链：

```text
根特征缺口
-> 根需求活动
-> 根任务承接
-> 任务筹办读取目标变化因果
-> 被动因果向上游追溯
-> 命中主动动作致变因果
-> 生成真正可任务化目标
-> 安全 / 服务到扫描的因果链生成正式扫描需求
-> 任务执行产生动作动态 / 状态变化动态
-> 因果信息生成或增强
-> 任务完成后结算
-> 安全 / 服务账务变化
-> 下一轮根特征状态判断
```

核心收口：

```text
需求不是看到一个字段就生成。
需求是在明确缺口以后才生成。
缺口必须有目标宿主、目标特征、当前状态、目标状态、来源因果或来源定义、权限 / 验证要求。
被动因果只能提供证据、来源和上游追溯线索。
主动动作致变因果才能承接真正可任务化目标。
内部治理结构缺陷不得包装成普通需求。
```

### 1.1 完整性 / 可执行性复核结论

本计划的方向完整，已经覆盖：

```text
根特征缺口来源；
根需求与根任务承接；
被动因果闭环；
主动 / 被动动态信息盘点；
因果需求提取；
主动因果承接；
需求树生成入口收束；
任务筹办消费因果视图；
安全 / 服务治理主轴；
服务触发事实准入；
安全 / 服务到扫描需求硬判据；
任务结算回到下一轮根状态判断。
```

但原计划的执行粒度仍偏宽，直接执行会有三类风险：

```text
1. P1 同时处理根目标读取和根任务承接策略，容易把定义修正与任务初始化混成一个大改。
2. P2 / P3 同时涉及动态、因果、任务筹办和学习链，若不先做现状对账，容易新增重复函数或绕过已有结构。
3. “补本能方法”容易被误解为补内部治理方法；实际应优先补普通函数和提交入口，只有真实对象作用或方法状态改变才考虑本能方法。
```

因此本计划修改为：

```text
先只读对账；
再按根目标、根任务、被动因果、动态信息盘点、因果需求、主动因果承接、需求入口、任务筹办、治理主轴、服务准入、扫描需求硬判据、结算回写逐段闭合；
每段必须有进入条件、退出证据和止损条件；
没有项目结构证据时不得宣称闭环。
```

### 1.2 执行约束与切片原则

```text
1. P0 只读，不改代码；P0 必须产出现状差距表后，才允许进入 P1。
2. 每个执行切片只允许修一个主问题；若暴露第二个独立问题，先把第一个问题收束为断点或待办。
3. 新增函数前必须先查 `说明书/函数功能说明文档.md` 和现有类接口；能复用普通函数时不新增本能方法。
4. 安全 / 服务治理优先级裁决不是严格意义的内部治理本能方法；学习 / 方法状态改变类才是严格内部治理本能方法候选。
5. 日志、SQL 投影、控制面板和调试输出只能作为证据读取面，不能承载机器逻辑或业务状态。
6. 任何“已闭环”判断必须给出：输入入口、核心处理、项目结构承载、输出 / 状态变化、调用路径、真实验证。
7. 计划执行过程中不得恢复“任务筹办 / 任务执行作为本能方法”的旧口径。
8. 默认禁止新增持久业务结构体；需要新结构体时必须先证明已有存在 / 场景 / 特征 / 特征值 / 状态 / 动态 / 二次特征 / 因果 / 需求 / 方法 / 基础信息节点无法承载。
9. 新建布尔型综合状态特征前必须展开子特征集合、各子特征值域、判定规则、写入方、来源动态和验证方式；未展开不得入树、入因果、入任务筹办或入结算。
10. 代码改动前先判断改动规模；若改动较大，优先用同名 + 版本号的新函数构建替代实现，验证确认后再替换旧函数，避免在旧函数内大段重写导致回滚困难。
```

## 2. 简化需求树生成规则

### 2.1 需求树生成入口只保留四类

```text
入口 A：根特征缺口
    自我_安全值 / 自我_服务值 当前状态低于最大值目标。
    只激活安全根需求 / 服务根需求和根任务承接。
    不直接生成固定安全清单或直接服务任务。

入口 B：任务筹办缺口
    任务筹办为了让当前任务可执行而发现缺口。
    原则上只允许四类：缺方法、缺条件、方法缺动作、方法缺条件结果对。
    参数不可配、证据不足、服务触发事实缺失等必须归并到条件 / 证据条件缺口，不另造泛化需求类型。

入口 C：执行期真实变化缺口
    只允许条件突然变化、输入材料过期、输出结果不满足目标、副作用约束触发等运行期事实。
    如果执行期才发现目标语义缺失、协议缺入口、方法结构字段缺失、任务状态账无法写回，应按逻辑错误或开发诊断处理。

入口 D：可验证外部 / 人类服务触发事实
    当前会话输入、人类表达、外部请求、服务目标事实、反馈事实等点亮直接服务因果链。
    只在触发事实存在且闭环信息位确认缺口阻断行动、验证、归因或回写时，生成直接服务子需求。
```

自检不单独作为第五类普通入口。自检只负责发现根特征缺口、事实缺口、因果缺口或代码缺陷型拒绝；入树前必须翻译到上述入口之一或进入开发诊断闭环。

### 2.2 被动因果不能直接生普通需求

被动因果包括：

```text
观察动态导致的状态变化因果；
提交入口导致的状态变化因果；
任务状态动作动态；
任务完成后结算动态；
服务值自动衰减动态；
外部事实变化动态。
```

它们只能说明：

```text
发生了什么变化；
变化由哪个提交 / 观察 / 结算 / 外部事件留下证据；
上游来源动态或来源因果是什么；
还缺哪些条件、证据、动作入口或方法结构。
```

它们不得直接成为：

```text
普通可执行方法候选；
主动动作来源；
普通可任务化需求来源；
安全 / 服务值结算前证据的充分条件。
```

### 2.3 主动因果是可任务化承接点

主动动作致变因果至少需要：

```text
动作主体；
被作用目标；
目标特征；
动作前状态；
动作后状态；
方法 / 动作入口；
D0 方法动作动态或可验证的动作运行证据；
同源变化证据组；
副作用约束和验证方式。
```

关键生成口径：

```text
主动因果由本能方法执行产生的主动动态信息承接。
内部治理普通函数只能读取、分类、复核、标记或回执，不生成主动因果。
被动因果由内部治理函数、结算后处理、观察确认、状态迁移等被动动态信息承接。
进入主动因果补齐前，必须先提取：
    本能方法中现有的主动动态信息；
    内部治理函数中现有的被动动态信息。
再根据动态信息缺口列出因果需求，
最后按因果需求复用已有本能方法或提出缺失本能方法候选。
```

只有命中主动动作致变因果后，任务筹办才允许生成真正可任务化的原子需求：

```text
让某个被需求存在的目标特征从当前状态达到目标状态。
```

若主动因果命中但方法结构不完整，生成的不是普通业务需求，而是方法补齐类缺口：

```text
缺方法；
缺方法动作入口；
缺条件节点；
缺结果节点；
缺条件结果对；
缺参数绑定条件；
缺验证证据条件。
```

## 3. 内部治理真正闭环

### 3.1 目标闭环

```text
自我根特征当前状态读取
-> 与最大值目标比较
-> 根需求活动性刷新
-> 根任务承接
-> 根任务筹办
-> 读取目标变化因果视图
-> 被动链追溯到主动链
-> 主动链生成原子任务 / 方法补齐任务
-> 安全 / 服务因果链生成正式扫描需求
-> 任务管理执行
-> 方法动作动态 D0 / 任务状态动态 D1 / 服务治理判断 G0 / 结算动态 D2
-> 因果信息生成或增强
-> 安全 / 服务账务变化或候选
-> 下一轮自我状态判断
```

### 3.2 不闭环的情况如何处理

```text
追溯停在被动因果：
    记录被动因果闭环状态和缺上游主动因果；
    不生成普通任务；
    可进入等待事实、补证据、观察、学习或诊断。

追溯停在内部治理函数：
    不生成需求；
    进入开发诊断或逻辑错误处理。

追溯停在方法结构缺口：
    生成方法补齐类缺口；
    不包装成安全 / 服务业务目标。

追溯停在服务直接触发事实缺失：
    只能生成间接服务维护需求；
    不生成当前服务对象、服务目标、G0、D2 或服务值入账任务。
```

### 3.3 缺口处理矩阵

| 命中状态 | 可生成内容 | 禁止生成内容 | 下一步 |
| --- | --- | --- | --- |
| 只有被动因果，缺上游主动因果 | 被动因果闭环状态、缺上游主动因果回执、等待事实 / 补证据 / 观察候选 | 普通业务需求、主动方法候选、服务成功候选 | P2 闭合被动证据链；必要时进入观察或补证据 |
| 命中主动因果，但方法入口不可执行 | 方法补齐缺口、学习缺口、方法状态改变类任务 | 直接服务任务、任务完成结算、服务值入账 | P3 识别缺方法 / 缺动作 / 缺条件 / 缺条件结果对 |
| 命中主动因果，方法入口可执行 | 原子目标需求、任务承接、候选方法 | 跳过任务筹办的裸执行、裸写需求满足 | P4/P5 走需求入树和任务筹办 |
| 根特征存在当前值与最大值差距 | 根需求活动、根任务承接壳 | 固定安全清单、凭空服务任务 | P1a/P1b 闭合根目标和根任务策略 |
| 服务根缺口存在但无直接服务触发事实 | 间接服务维护、监听、机会检查、能力校准、休眠 / 唤醒候选 | 当前服务对象需求、服务目标需求、G0、D2 | P7 校验触发事实准入 |
| 执行期发现目标语义缺失、协议缺入口或字段账写不回 | 开发诊断、逻辑错误、对应类纠偏计划 | 普通需求、学习需求、服务维护需求 | 停止当前业务链，按所属类追根因 |
| 缺口属于任务筹办四类 | 缺方法、缺条件、缺动作、缺条件结果对 | 任务筹办子任务、任务执行子任务 | P5 结构化回执，必要时进入学习链 |

### 3.4 安全 / 服务治理主轴

安全值只调节治理优先级，不改服务根目标值：

```text
安全值高：
    服务优先级提升；
    服务衰减压力、服务候选排序和休眠压力可以更充分展开。

安全值低：
    安全优先级提升；
    服务优先级降低；
    服务仍可在安全边界内保留等待 / 监听 / 校准需求。
```

实现上只能影响：

```text
需求列表排序主轴；
任务调度优先级；
服务衰减压力；
休眠阈值；
单次服务入账上限；
间接服务维护敏感度。
```

禁止影响：

```text
自我_服务值 最大值目标；
服务对象是否存在；
服务目标是否明确；
服务成功是否成立；
服务值结算证据是否充分。
```

### 3.5 闭环必需因果信息清单

内部治理闭环不是只要“有因果信息”即可，至少需要以下因果信息分层齐备；某一层缺失时，闭环只能降级为部分闭环或待补闭环。

| 因果信息 | 作用 | 最低字段 / 证据 | 不足时处理 |
| --- | --- | --- | --- |
| 根闭环因果信息 | 说明安全 / 服务根需求为什么能从自我定义域和根特征缺口进入当前治理链 | 根因果坐标、来源定义或遗传因果模板、当前事实挂载、根需求引用、派生来源因果主键 | 不能直接生成当前主动需求；进入根闭环因果补齐 |
| 状态变化因果 / 状态变化线索 | 证明目标宿主的目标特征确实发生了当前状态 -> 结果状态变化 | 目标宿主、目标特征、初始状态、结果状态、来源动态、时间 / 状态端点、同源变化证据组 | 只能作为观察、学习、证据补齐线索，不得作为方法候选 |
| 主动动作致变因果 | 证明某个自我方法 / 动作能够造成目标状态变化，是可任务化承接点 | D0、动作主体、方法 / 动作入口、被作用对象、目标特征、动作前后状态、输入 / 输出场景、同源变化证据组、副作用约束 | 不能生成可执行原子任务；按缺方法 / 缺动作 / 缺条件 / 缺条件结果对处理 |
| 被动动作致变因果 | 解释提交、观察、结算、衰减等被动变化如何发生 | 被动动作动态、提交入口或观察入口、状态前后值、来源动态、同源变化证据组、不可主动调用标记 | 只能用于解释、审查、诊断或补证据，不得进入普通方法候选 |
| 同源变化证据组 | 把同一次特征变化的状态迁移动态、动作致变动态、状态变化因果和动作致变因果绑定在一起，用于互证和去重 | 显式证据组句柄，或可由动态、状态端点时间、目标宿主和目标特征复算出的同源组 | 不允许结算、需求满足或安全 / 服务账务重复入账 |
| 因果样本 / 因果族样本 | 支持从单次变化到候选因果、再到已验证因果的稳定化 | 主果变化锚点、候选条件项、正反样本、证据动态样本、验证状态 | 单次样本不得直接标记为已验证因果 |
| 服务触发事实来源因果 | 证明直接服务任务来自当前会话 / 外部请求 / 服务事实，而不是服务根需求凭空生成 | 服务对象、服务目标、权限边界、安全边界、验证方式、归因方式、来源动态 / 来源事实 | 只能生成间接服务维护、监听、机会检查或能力校准 |
| 结算回写因果 | 证明任务完成、G0 判断、D2 结算和下一轮根状态判断之间的账务链 | D1、G0、D2、任务价值反馈、账务变化状态、同源变化去重、下一轮根状态读取证据 | 不能把任务完成反推服务成功，不能把服务值变化反推服务对象改善 |

### 3.6 因果信息如何生成

生成链必须按因果类型区分，不得用同一个“生成因果信息”口号覆盖所有情况：

```text
根闭环因果信息：
    自我觉醒 / 自我定义域
    -> 根闭环因果模板或遗传因果信息组
    -> 当前事实挂载
    -> 缺口候选
    -> 根需求 / 派生需求来源因果引用

状态变化因果 / 状态变化线索：
    状态动态 / 观察动态 / 提交动态 / 结算动态
    -> 提取目标宿主、目标特征、初始状态、结果状态
    -> 查找或创建状态变化线索
    -> 追加证据动态样本
    -> 候选因果样本进入因果族样本树

主动动作致变因果：
    方法执行产生 D0
    -> 输出结果场景 / 被作用对象特征发生状态迁移
    -> D0 与状态变化因果绑定同源变化证据组
    -> 生成动作致变因果候选
    -> 经过验证、复现、反例过滤或明确动作来源可归因后，才允许沉淀为已验证因果

被动动作致变因果：
    任务状态提交、观察提交、结算后处理、服务衰减等被动动态
    -> 若动作语义明确，可生成被动动作致变因果
    -> 标记为不可主动调用
    -> 只供解释、审查、缺口定位和补证据

同源变化证据组：
    状态迁移动态、动作致变动态、状态变化因果、动作致变因果属于同一次特征变化时
    -> 优先写入显式证据组句柄
    -> 暂无显式结构时，必须能按动态、状态端点时间、目标宿主、目标特征复算同源组
    -> 结算、需求满足、账务变化按同源组单次入账
```

### 3.7 闭环检查口径

闭环检查必须回答“因果信息是否足以让下一步合法发生”，而不是只检查节点是否存在。

| 检查项 | 必须成立 | 不成立时 |
| --- | --- | --- |
| 根来源检查 | 根需求能追溯到根闭环因果信息、来源定义或遗传因果信息组 | 根需求只保留活动状态，不进入当前主动需求 |
| 因果分类检查 | 明确是状态变化因果、主动动作致变因果、被动动作致变因果、候选样本还是已验证因果 | 不允许进入任务筹办候选或结算证据 |
| 状态变化检查 | 当前状态、目标状态、目标宿主和目标特征均可从项目结构回查 | 进入观察 / 证据补齐 / 开发诊断 |
| 动作归因检查 | D0、方法 / 动作入口、被作用对象、状态迁移和同源变化证据组闭合 | 不生成可任务化原子需求 |
| 被动禁用检查 | 被动动作致变因果不得被任务筹办召回为普通可调用方法 | 标记缺上游主动因果或进入诊断 |
| 同源去重检查 | 同一次变化只允许一个同源组参与需求满足、结算和账务变化 | 暂停结算，补同源组或复算规则 |
| 服务触发检查 | 服务对象、服务目标、权限、安全、验证、归因和来源事实齐备 | 不生成直接服务上下文需求 |
| 结算双钥匙检查 | 同时具备结果状态迁移证据和自我动作归因证据，并通过副作用审查 | 不允许安全 / 服务值入账 |
| 回写检查 | 结算或候选结果能进入下一轮根特征状态判断 | 只能写待回写缺口，不得宣称闭环 |

### 4.1 闭环证据矩阵

每个实现切片必须用同一套矩阵验收，不得只用构建通过或日志存在替代：

| 证据项 | 必须回答的问题 | 不合格情况 |
| --- | --- | --- |
| 输入入口 | 谁触发了这条链，入口参数是什么，是否是真实路径 | 伪造入口、手工 SQL、测试夹具冒充业务入口 |
| 核心处理 | 哪个类、哪个函数做了裁决或状态推进 | 只在日志、UI 或临时 JSON 中计算 |
| 项目结构承载 | 事实写入了存在 / 场景 / 特征 / 特征值 / 动态 / 因果 / 需求 / 任务中的哪一类结构 | 只有字符串摘要、说明字段或控制台输出 |
| 结构体准入 | 是否证明无需新增持久业务结构体，或新增辅助结构不承载权威事实 | 新结构体替代已有项目结构进入机器判断 |
| 布尔特征展开 | 布尔型综合状态是否展开子特征集合、值域、判定规则、写入方、来源动态和验证方式 | 裸建 `是否 / 已 / 可 / 成功 / 开 / 关 / 连接` 等叶子结论 |
| 输出 / 状态变化 | 哪个状态、动态、任务或需求发生了可回查变化 | 只有函数返回成功，没有结构变化 |
| 调用路径 | 从入口到写入方、读取方的调用链是否闭合 | 函数孤立存在，没有被真实链路调用 |
| 真实验证 | 用什么命令、日志锚点、SQL 只读查询或运行证据证明 | 只说“理论可行”或“构建通过” |

### 4.2 阶段通用止损条件

任一阶段命中以下条件，必须先写断点清单，不继续扩大修改：



工作项：

```text
1. P3c：提取本能方法中的现有主动动态信息。
   只统计真实本能方法执行链中写出的 D0 / 方法动作动态 / 对象作用动态 / 方法状态改变动态；
   记录方法入口、动作主体、被作用对象、目标特征、动作前后状态、输出场景、同源证据和验证方式。
2. P3d：提取内部治理函数中的现有被动动态信息。
   只统计治理普通函数、结算后处理、观察确认、状态迁移、回执同步等被动动态；
   记录其来源动态、证据对象、状态迁移、上游主动因果引用和是否缺上游主动因果。
3. P3e：从 P3c / P3d 的盘点结果列出因果需求。
   因果需求至少分为：
       缺主动动作来源；
       缺被作用对象；
       缺目标特征或目标方向；
       缺动作前 / 后状态；
       缺方法入口或动作句柄；
       缺同源变化证据组；
       缺验证状态；
       缺上游主动因果；
       缺副作用 / 安全 / 权限约束。
4. P3f：按因果需求映射已有本能方法或缺失本能方法候选。
   能由已有本能方法产生的，复用现有方法入口；
   能由普通治理函数读取或复核的，不新增本能方法；
   只有需要自我真实作用对象或改变方法状态时，才提出本能方法候选。
5. 建立或复用主动因果生成函数：
   从本能方法主动动态信息 + 状态迁移账 + 同源变化证据组生成主动动作致变因果。
6. 建立或复核同源变化证据组绑定：
   D0、状态迁移动态、状态变化因果和动作致变因果必须能回解到同一组；
   不能回解时，不允许结算或需求满足入账。
7. 建立主动因果验证状态检查：
   单次样本只能是候选；
   经过复现、反例过滤或明确归因后才可标记已验证。
8. 建立主动因果可任务化判定：
   有正式方法入口 -> 可生成原子需求 / 任务；
   有方法头但不可执行 -> 方法补齐缺口；
   无方法入口 -> 学习或方法头承接；
   只有被动状态变化 -> 不可任务化。
```

主动因果证据卡：

| 字段 | 要求 |
| --- | --- |
| 动态信息来源清单 | 已列出本能方法主动动态和治理函数被动动态，不用概念推断代替 |
| 因果需求清单 | 能说明缺哪类因果证据、由谁生产、由谁复核 |
| D0 方法动作动态 | 证明自我实际执行了某个方法动作 |
| 方法 / 动作入口 | 能定位到方法头、方法虚拟存在或动作句柄 |
| 动作主体 | 明确自我或自我组成部分，不用线程代替 |
| 被作用对象 | 明确存在 / 场景 / 输出结果场景 / 运行存在 |
| 目标特征 | 明确特征类型和目标方向 |
| 动作前 / 后状态 | 能从项目结构回查，不用描述文本替代 |
| 同源变化证据组 | 能连接 D0 与状态迁移账 |
| 副作用约束 | 明确安全、权限、服务边界或缺失状态 |
| 可任务化裁决 | 输出可生成原子需求、方法补齐缺口、学习缺口或不可任务化 |

验收预测：

```text
能从现有代码列出本能方法主动动态信息和内部治理函数被动动态信息。
能从动态信息缺口列出因果需求，并映射为复用已有本能方法、普通治理函数补齐或缺失本能方法候选。
真实方法执行后能查到主动动作致变因果。
任务筹办能从主动因果读出目标宿主、目标特征、目标状态和方法承接。
被动因果不会进入方法候选集。
主动因果缺方法结构时，只生成方法补齐类缺口，不包装成普通安全 / 服务业务目标。
```


### 6.2 可补本能方法的边界

只有真正对象作用或方法状态改变，才考虑补本能方法；补之前必须先查 `说明书/函数功能说明文档.md` 和现有注册表，并先完成因果需求清单。

补本能方法的前置顺序固定为：

```text
提取现有主动 / 被动动态信息
-> 列出因果需求
-> 尝试复用已有本能方法
-> 尝试用普通治理函数读取 / 复核 / 回执
-> 仍缺真实对象作用或方法状态改变时，才提出缺失本能方法候选
```

严格意义上的内部治理本能方法候选只保留学习 / 方法状态改变类，且优先复用既有注册：

```text
自我_尝试学习
自我_定向学习
自我_练习
```

安全 / 服务类更准确是内外接口或对象作用方法，不归入严格内部治理本能方法；只有确实需要自我对对象产生动作，且已有方法头 / 条件 / 结果 / 验证链可承接时，才复核是否注册为本能方法：

```text
服务_监听服务触发事实
服务_检查服务机会
服务_校准服务能力
服务_读取服务对象当前状态
服务_验证服务结果
服务_归因服务结果
安全_评估当前场景安全性
安全_确认权限边界
安全_执行降级保护
```

默认不作为本能方法新增、优先作为方法域普通提交入口或维护函数复核的内容：

```text
自我_提交方法可执行入口
自我_建立条件结果对
被动因果闭环状态标记
主动因果可任务化裁决
需求入树拒绝回执
开发诊断拒绝回执
```

### 6.3 明确不补成本能方法

```text
需求树生长
任务筹办
任务执行
同步筹办回执到任务
同步执行回执到任务
回写需求满足的只读判断
因果追溯
因果视图展开
根需求活动性刷新
安全 / 服务优先级裁决
服务值衰减计算
休眠阈值判断
控制面板显示刷新
```

这些是治理普通函数、提交入口、维护器或显示层，不得进入方法候选集。

## 7. 执行顺序建议

```text
第一轮只执行 P0：
    只读对账并产出现状差距表，不改代码。

第二轮执行 P1a-P1c：
    先修根目标最大值读取，再唯一化根任务承接策略，最后验证根需求到根任务最小闭环。

第三轮执行 P2-P3：
    先证明被动因果闭环，再盘点本能方法主动动态和治理函数被动动态，列出因果需求，并映射已有 / 缺失本能方法。

第四轮执行 P4-P5：
    在 P3 动态盘点和因果需求清单完成后，简化需求树生成入口和任务筹办因果消费。

第五轮执行 P6-P8：
    安全 / 服务治理主轴、直接服务准入、安全 / 服务到扫描需求硬判据、结算回写闭环。

第六轮执行 P9：
    真实运行验证和索引归档。
```

每轮必须单独提交，且不能混入当前工作树中其它未完成计划的改动。
