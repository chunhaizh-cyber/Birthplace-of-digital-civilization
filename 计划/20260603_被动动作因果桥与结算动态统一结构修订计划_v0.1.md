# 被动动作因果桥与结算动态统一结构修订计划 v0.1

日期：2026-06-03

## 0. 定位

本计划用于修订安全 / 服务值结算、任务状态提交、需求满足回写等被动动作动态的结构与因果生成链。

本计划不替换 `计划/计划索引.md` 中的当前主动队列。当前主动队列仍以计划索引为准；本计划作为独立待执行修订项，后续只有在用户明确切换到本计划或计划索引调整后才进入实施。

## 2. 本轮确认口径

```text
1. 被动动作不是普通任务候选，不进入主动方法选择、学习目标、练习目标或自我动作组合。
2. 被动动作是自我可见的事实类型；自我不需要知道如何调用、何时生成或如何生成。
3. 被动的含义是：只要被动因正式出现并满足对应被动规则，被动果就自动出现。
4. 被动因已具备但被动果未出现时，这是提交链、后处理链或结算链缺口，不是等待任务筹办的普通缺口。
5. 被动动作的检查方式必须看代码中是否存在因到果的自动执行路径，且中间没有无法执行的阻塞点。
6. 被动动作动态仍必须使用统一动作动态结构，不能降级成普通日志。
7. 所有动作动态转入因果信息的逻辑必须一致；被动动作只是动作语义不可主动调用。
8. 被动动作因果关系主要承上启下：知道为什么，知道需要什么。
9. 安全 / 服务值结算在叶子任务完成后由任务价值反馈链触发，不走普通任务链。
10. 结算动态的因应具体落到 `任务虚拟存在.任务状态 = 已结算`，并串入需求满足、实际结果状态和权重来源。
11. 结算动态的果应保留结算前值、结算后值、实际变化量和二次特征方向。
12. 抽象到安全 / 服务目标投影时，可以只保留二次特征方向。
13. 一个任务完成可能同时满足多个不同需求；结算时必须按需求路径分别追溯预算、AND / OR 关系和防重复令牌。
14. 需求列表类型安全 / 服务汇总权重只用于任务优先级和列表排序，不作为结算预算。
```

## 3. 当前代码风险假设

本计划进入实施前，需要以代码对账确认以下风险是否仍成立：

```text
1. 创建方法动作动态的统一入口未完整写入初始状态 / 结果状态。
2. 结算叶子任务价值动态已构造旧值 / 新值，但未落入动态节点状态字段。
3. 提交任务状态变化动态已拿到旧任务状态 / 新任务状态，但未落入动态节点状态字段。
4. 回写需求满足动态、OR路径令牌动态等被动动态可能缺少可抽象的状态迁移字段。
5. 结算动态生成后没有稳定调用动作动态到因果信息的统一入口。
6. 安全 / 服务目标投影未稳定消费结算动态生成的因果材料。
7. 多需求共享同一任务完成事实时，结算预算、令牌和防重复键可能仍需拆分。
8. 被动因已具备但被动果缺失时，日志和缺口归类可能还没有区分“被动链缺口”和“普通任务缺口”。
9. 现有代码可能有结算判断或日志，但缺少从被动因到被动果的自动执行调用链。
```

以上是待复核假设，不作为已确认缺陷结论。

## 4. 修订切片

### P0 规范落点

目标：

```text
把被动动作因果桥、结算动态因果桥和多需求结算口径落入规范。
```

范围：

```text
规范/方法动作动态硬规则规范20260512.md
规范/动作动态即因果账本规范20260512.md
规范/因果信息用途与用法规范20260516.md
规范/安全服务值结算规范20260518.md
本计划文件
```

验收：

```text
规范明确被动动作不进入普通候选 / 学习 / 练习；
规范明确被动因正式出现后，被动果必须自动出现；
规范明确被动动作动态仍必须记录初始状态和结果状态；
规范明确结算因 = 任务虚拟存在.任务状态 = 已结算；
规范明确结算果 = 旧值 / 新值 / 变化量 / 二次特征方向。
```

### P1 动作动态结构代码对账

目标：

```text
列出所有会生成被动动作动态的入口，确认哪些入口缺初始状态、结果状态、来源低层动态或输入 / 输出事实场景。
同时确认每条被动动作是否存在因到果的自动执行代码路径。
```

优先入口：

```text
创建方法动作动态
输出任务状态提交动作动态
输出需求满足动作动态
输出需求OR路径令牌动作动态
输出叶子任务价值结算动作动态
结算叶子任务价值
按动态创建因果信息
```

产物：

```text
实施记录/20260603_被动动作动态结构代码对账记录.md
```

检查方式：

```text
只以代码链路为准：
    被动因入账位置；
    自动触发或后处理扫描入口；
    从因到果的函数调用链；
    幂等 / 防重复判断；
    被动果写入位置；
    动作动态生成位置；
    因果抽象入口。

以下内容不能作为被动动作已成立的证据：
    规范声明；
    日志文案；
    候选记录；
    需要普通任务筹办才能继续的路径；
    需要人工触发或学习补入口才能继续的路径。
```

### P2 统一动作动态状态字段写入

目标：

```text
在不破坏现有主动动作动态的前提下，为统一动态生成入口补齐可选初始状态 / 结果状态写入能力。
```

边界：

```text
不得把线程作为动作来源；
不得把被动动作改成可调用候选；
不得新增第二套因果账本；
不得用普通日志替代动作动态。
```

验收：

```text
被动状态动作动态能在动态节点上回解初始状态和结果状态。
主动动作动态原有行为不退化。
```

### P3 结算链被动动态补齐

目标：

```text
补齐任务状态已结算、需求满足、叶子任务价值结算三段动态之间的来源低层动态链。
保证结算被动因正式出现后，结算被动果自动出现。
```

重点：

```text
任务状态动态：
    旧任务状态 -> 已结算。

需求满足动态：
    未满足 / 阶段满足 -> 满足或对应满足状态。

结算动态：
    旧安全 / 服务值 -> 新安全 / 服务值；
    保留实际变化量和二次特征方向；
    来源低层动态引用任务已结算、需求满足和实际结果动态。
```

验收：

```text
D0 / D1 / D2 可以通过来源低层动态回解；
D2 的因可追溯到 `任务虚拟存在.任务状态 = 已结算`；
D2 的果可读取旧值、新值和方向。
结算被动因已具备时，不需要新增普通任务即可生成 D2。
从结算被动因到 D2 的代码调用链中没有缺入口、缺参数、缺状态、缺权重来源、缺权限或缺防重复键等无法执行阻塞点。
结算被动因重复触发时，不重复入账，只引用已有结算动态或记录已处理。
```

### P4 动态到因果信息被动生成

目标：

```text
在结算动态生成后，通过动作动态到因果信息的统一流程被动沉淀因果材料。
```

边界：

```text
不能绕过动作动态直接增强安全因果链；
不能为被动动作生成可调用动作模板；
因果反推读到被动动作时，只能生成上游事实需求、条件需求或证据补齐需求。
```

验收：

```text
结算动态能生成状态变化线索或完整因果材料；
结算动态生成后，不需要普通任务筹办即可自动沉淀因果材料；
安全 / 服务目标投影能读到该材料；
学习链不会把 `被动动作` 当成主动动作。
```

### P5 多需求共享任务完成事实结算

目标：

```text
当一个已完成任务同时满足多个不同需求时，按需求列表和来源需求引用找到所有候选需求路径，并分别判断是否可结算。
```

规则：

```text
AND关系：
    子需求 / 子任务平分父需求预算。

OR关系：
    每条活跃路径继承父需求完整候选预算；
    同一OR组只允许取得令牌的路径进入真实结算。

多需求共享同一任务完成动态：
    可以共用上游任务完成证据；
    不得共用同一份结算预算；
    不得跳过各需求路径的防重复键。

结算顺序：
    先完成任务自身结算；
    自身结算内部包含自身对应需求回写、父任务缺口满足程度判断、父需求 / 父任务链收束；
    自身结算完成后，才进入横向同目标任务结算。

缺口变化闸门：
    根据被满足缺口的满足程度计算结算；
    如果被满足缺口相对完成前没有变化，不进入核心安全 / 服务值结算。

横向触发：
    来源任务自身结算后，先计算 来源满足差 = 目标值 - 实际值；
    只有 来源满足差 < 0 时，才进入横向候选扫描；
    横向外溢量 = abs(来源满足差)。

横向候选结果：
    候选 before / 之前实际值 = 来源任务完成后候选需求目标的当前值；
    候选 actual / result = 候选当前值 + 横向外溢量；
    候选 target = 候选需求自己的目标状态；
    候选完成度继续复用任务管理工作线程的既有完成度算法。

横向结算排序：
    横向候选任务按任务权重高者优先；
    每个横向候选也按“需求 + 其父链 / 父缺口处理”作为一个独立结算单元；
    不使用需求列表汇总权重作为结算预算。

横向阻塞：
    候选缺口没有变化时不结算；
    候选任务未形成完成 / 已结算被动因时，不由自我线程裸写完成，只记录待补被动完成桥。
```

验收：

```text
同一任务完成事实可以解释多个需求满足；
每条需求路径的结算预算、令牌和防重复记录独立；
需求列表汇总权重只影响任务优先级，不进入结算公式。
```

## 6. 暂停条件

出现以下情况时暂停实施，先回到规范确认：

```text
1. 现有上级规范要求被动动作不得生成因果材料。
2. 动态到因果信息流程要求动作必须可主动调用。
3. 任务状态已结算与任务完成状态存在枚举口径冲突。
4. 多需求结算与预算守恒规则发生冲突。
5. 需要把任务筹办 / 任务执行恢复为本能方法才能继续。
```
