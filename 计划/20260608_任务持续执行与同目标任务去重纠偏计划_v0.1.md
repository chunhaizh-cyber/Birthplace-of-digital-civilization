## 1. 背景

本计划原先只制定任务管理语义纠偏方案，不修改代码。2026-06-09 起当前主动切片以 `计划/计划索引.md` 登记为准；进入实现前需要单独断点和预测，避免混入相机四本能方法专项优化。

本轮口径：

```text
1. 任务管理执行回路必须是通用能力，不按观察、服务、安全等业务方法单独设计。
2. 方法声明不增加执行形态；界面线程按结构化消息分类处理。
3. 任务处于执行中时，允许方法返回部分结果并做阶段性结果入账；任务自身继续保持执行中。
4. 已结算仍只表示任务完成后的价值结算后处理，不用于部分结果。
5. 为新需求承接任务时，必须先查当前任务树中是否已有同目标任务；可复用时不新建并行任务。
6. 同目标任务严格检查目标宿主、目标特征类型和目标方向；目标值不作为同任务身份硬等值条件，只进入覆盖 / 升级判断。
7. 工作线程和界面线程之间只通报状态、控制、批次和触发信号；不得传输真实世界存在、特征、状态、二次特征等事实载荷。
8. 方法运行结果和输出结果场景写回任务虚拟存在是正确方向，但写回时机必须由工作线程完成事实入账后发送消息触发检查。
9. 真实世界信息的增删改查全部由工作线程侧或正式提交入口完成；界面线程只做调度、合流、控制和状态推进编排。
10. 工作线程之间不能直接通信，只能通过界面线程统一调度和整合。
```

## 2. 当前代码逻辑梳理

### 2.1 任务状态与回执基础已经具备

`任务主信息类.h` 已定义 `执行中`、`待重筹办`、`完成`、`已结算` 等状态，其中 `已结算` 注释为“任务目标已完成，且任务完成后的价值结算后处理已执行”。

`任务模块.筹办.ixx` 的 `结构_任务推进回执` 已包含：

```text
当前任务目标达成
本轮是否有推进
本轮推进量
剩余差距
完成度百万分比
执行结果类型
```

并且 `执行结果类型` 已区分：

```text
目标已达成
有推进未达成
无推进未达成
退步
不可比较
```

结论：持续执行所需的基础回执字段已存在，不需要新增“方法声明执行形态”。

### 2.2 执行结果评价已经能识别部分推进

`任务模块.管理工作线程.ixx` 中，执行结果会比较实际状态、目标状态和之前状态：

```text
目标达成 -> 目标结果符合 / 目标已达成
未达成但有推进 -> 目标结果不符合 / 有推进未达成
未达成且无推进 -> 目标结果不符合 / 无推进未达成
退步 -> 退步
```

同时上行 `结构_任务管理结果状态消息` 已有 `部分完成` 结果状态。

结论：代码已经有“部分结果 / 部分完成”的表达基础，但状态推导仍未完全按通用部分结果协议收束。

### 2.3 当前持续执行纠偏仍带业务特判

`任务模块.管理工作线程.ixx` 当前有 `私有_方法是持续观察批次方法`，按本能方法 ID 判断：

### 2.4 `执行中` 已经能进入运行派发

`任务模块.管理界面线程.impl.cpp` 的调度裁决中，`就绪`、`排队中`、`执行中` 都会被判定为执行工作项。

结论：一旦通用状态推导能把部分推进结果保持为 `执行中`，现有派发路径可以继续运行，不需要新增任务状态。

### 2.5 任务创建入口目前只做需求主键幂等，不做同目标任务复用

自我线程发起任务时，`自我线程模块.impl.cpp` 构造：

```text
请求类型 = 发起任务
来源需求 = 当前需求
允许创建任务信息节点 = true
允许复用等待任务 = true
幂等键 = 发起任务|需求=<需求主键>
```

任务管理界面线程接收请求后，先调用 `私有_尝试复用幂等承接结果`。该函数只按幂等键查历史承接结果，并且只复用等待态承接结果。若未命中，则在 `发起任务` 分支中直接调用 `私有_按需求创建任务并初始化` 创建新任务。

结论：当前复用范围是“同一需求主键的等待承接幂等”，不是“同目标任务复用”。新需求即使目标宿主、目标特征类型、目标方向相同，也会走新任务创建。

### 2.6 自我线程有局部去重，但不是通用任务去重

自我线程活动需求任务化前会检查当前需求自己的 `对应任务 / 任务列表`，避免同一需求重复发起任务。

另外学习缺口有 `私有_查找同方法活跃学习任务_线程侧`，但它是学习任务专用，签名包含来源方法和目标状态键，不能作为通用同目标任务复用规则。

结论：现有去重是局部防重复，不是任务管理入口的通用同目标复用能力。

### 2.7 需求层已有目标语义和方向基础

`需求主信息类.h` 已明确：

`需求类` 已提供：

### 2.8 当前线程协议仍携带过多事实载荷

`任务模块.管理线程协议.ixx` 当前跨界结构仍携带大量领域对象指针：

```text

    上行消息集
    外设观察报告ID / 等待项ID
```

`任务模块.工作线程消息协议.ixx` 当前上行消息也携带真实世界或语义细节：

```text
派生需求消息：
    方法虚拟存在指针
    来源因果 / 来源动态 / 来源方法
    父需求

结果状态消息：

```

结论：当前协议能传递运行结果，但边界过宽。界面线程会看见并转运存在、特征、状态、二次特征、结果场景等真实世界细节；这与“两个线程只通报各自状态，真实世界信息不在线程间交互”的口径冲突。

### 2.9 当前方法结果写回位置需要收束

`任务模块.管理界面线程.impl.cpp` 当前在普通整理回执到任务壳阶段，从 `结构_任务工作结果` 读取 `方法运行结果` 和 `输出结果场景`，再写入任务虚拟存在：

```text
当前方法运行存在
最近运行虚拟存在
输出结果场景
```

该写回方向本身正确，但问题在于：

```text
1. 方法运行结果 / 输出结果场景以指针形式跨工作线程和界面线程边界传递。
2. 界面线程直接根据工作结果指针执行任务虚拟存在写回。
3. 状态检查和下一轮派发不是严格由“工作线程已完成事实入账”的消息触发。
```

正确收束应为：

```text
工作线程完成方法执行；
工作线程完成真实世界事实、输出结果场景、方法运行存在和任务虚拟存在写回；
工作线程发送“本轮事实已入账 / 可检查状态 / 是否需要下一轮”的轻量消息；
界面线程只按该消息触发状态检查、任务状态提交、派发下一轮或等待控制。
```

## 3. 目标口径

### 3.1 持续执行目标口径

通用规则：

```text
执行阶段结果消息 = 部分完成
且目标未达成
且本轮有推进
且执行结果类型 = 有推进未达成
且没有阻塞性派生需求 / 等待条件 / 显式重筹办请求 / 失败
=> 任务状态保持 执行中
=> 结果按批次提交和阶段性入账
=> 下一步继续进入运行
```

以下情况才进入 `待重筹办`：

```text
目标 / 作用对象 / 参数 / 方法有效性 / 前置条件 / 安全约束发生变化
需要重新选择方法或重新组织条件
方法明确返回重筹办请求
本轮无推进且需要换路径
```

以下情况进入 `等待中`：

```text
缺条件
等待子需求
等待外部支撑
阻塞性派生需求已提交
```

以下情况进入 `完成 -> 已结算`：

```text
目标达成
任务状态通过 提交任务状态变化 进入完成
完成后价值反馈链执行
任务状态通过 提交任务状态变化 进入已结算
```

### 3.2 同目标任务复用目标口径

同任务身份严格匹配：

```text
目标宿主一致
目标特征类型一致
目标方向一致
作用范围 / 场景范围兼容
事实时点 / 有效期兼容
```

目标值不是同任务身份硬条件。目标值只用于判断：

```text
已有任务目标是否覆盖新需求
新需求目标是否强于已有任务，需要升级任务目标
两者是否不可合并
```

判断规则：

```text
目标特征类型不同 -> 不复用
目标方向不同 -> 不复用
目标值不同但方向一致 -> 进入覆盖 / 升级判断
```

复用策略：

```text
已有任务目标覆盖新需求 -> 新需求挂接已有任务，不新建
新需求目标更强 -> 提交任务目标升级 / 待重筹办，不新建并行任务
目标区间仅重叠或精确等于目标值冲突 -> 不合并，或等待上层规则裁决
已有任务已完成 / 已结算 -> 只能复用结果事实或结算证据，不能复用执行中任务壳
已有任务失败 / 取消 / 结果失效 -> 不复用
```

### 3.3 线程消息边界目标口径

界面线程和工作线程之间只允许传递：

```text
任务ID / 工作项ID / 请求ID / 批次ID
工作项类型
工作线程运行状态
控制意图与控制响应
本轮结果分类
是否已完成事实入账
是否需要状态检查
是否需要下一轮
是否需要等待 / 取消 / 收束 / 重试
错误码和诊断日志ID
```

线程消息中不得传递或依赖：

```text
存在节点指针
特征节点指针
状态节点指针
二次特征证据结构
输出结果场景指针
方法运行存在指针
真实世界事实变化明细
用自然语言摘要参与机器判断
```

分层目标：

```text
工作线程事实层：
    执行方法；
    读取和写入真实世界事实；
    写入输出结果场景；
    写入方法运行存在；
    写回任务虚拟存在中的方法运行结果和输出结果场景引用；
    生成正式提交入口需要的动作动态输入或事件ID。

界面线程调度层：
    接收工作线程状态消息；
    根据消息触发状态检查；
    调用提交任务状态变化；
    控制派发、重排、暂停、取消、收束和下一轮；
    不读取或改写真实世界事实载荷。

上行治理层：
    界面线程只转发“有新结果 / 有派生材料 / 有观察事实材料已入账”的事件ID、批次ID或不含事实语义的回查令牌；
    自我线程或治理提交入口按任务ID / 批次ID重新触发检查已入账材料；
    不把线程消息本身当世界事实或需求满足证据。
```

### 3.4 写回与状态检查触发口径

`方法运行结果` 和 `输出结果场景` 写回任务虚拟存在应保留，但必须满足：

```text
1. 写回由工作线程完成，或由工作线程调用任务域正式写回入口完成。
2. 界面线程收到“写回已完成 / 可检查状态”消息后，才触发状态检查和任务状态提交。
3. 界面线程不通过跨线程指针读取方法运行存在或输出结果场景。
4. 若工作线程未发出“事实已入账”消息，界面线程不得按猜测推进完成、结算或下一轮。
5. 工作线程状态由界面线程控制消息驱动；工作线程之间不直接通信。
```
