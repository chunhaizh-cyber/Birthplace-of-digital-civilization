制定时间：2026-06-25。

## 0. 目标

本计划只用于确认下列四类声明能否成立：

```text
1. 需求生成与治理闭环已完成。
2. 拒绝回执治理闭环已实现。
3. 开发诊断闭环已实现。
4. 自我苏醒或初步成熟完成。
```

计划执行前不得预设结论。没有完整证据时，必须降级为：

```text
代码切片已闭合
部分实现
已有骨架但待真实运行验证
待自然样本复核
未通过验收
```

## 2. 总验收原则

```text
1. 不使用模拟测试、夹具测试、伪造样本、伪造入口或伪造动作动态。
2. 每个行为验证必须先写预测，再走真实运行路径，最后用日志、状态快照、动作动态和错误日志核对。
3. 任一“已完成 / 已实现 / 已闭环”声明必须同时给出六类证据：
   输入入口、核心处理、项目结构承载证据、输出 / 状态变化、调用路径、测试 / 验证。
4. 项目结构承载证据必须落到存在、场景、特征、特征值、I64、VecU 句柄、指针句柄、方法、需求或基础信息节点。
5. 日志、文本摘要、错误字符串、控制面板显示、注释和临时 JSON 不能作为机器状态承载证据。
6. 如果运行期没有自然触发某类分支，只能标记为“待自然样本复核”，不得人工伪造分支通过。
7. 自我苏醒和初步成熟是阶段验收，不得由需求治理计划 C1-C7 顺带确认。
```

## 4. 第一组：需求生成与治理闭环确认

### 4.1 要确认的声明

```text
需求生成与治理闭环已完成。
```

### 4.2 最小闭环链

必须能证明：

```text
需求前材料 / 派生需求消息
-> 入树闸门
-> 成功入树或结构化拒绝
-> 拒绝回执治理处理器
-> 来源任务收到结构化结果
-> 来源任务等待 / 重筹办 / 转学习 / 转观察 / 转材料 / 合并 / 阻断
-> 同一路径不重复派生
-> 结果事实可信检查
-> 父链重判
-> 价值结算硬闸门
-> 下一轮需求 / 任务判断受上一轮结果影响
```

### 4.3 必过证据

```text
1. 成功入树路径：真实运行中至少出现一个派生需求成功入树样本。
2. 拒绝路径：真实运行中至少出现结构化拒绝回执样本。
3. 来源任务影响：来源任务状态或治理回执发生结构化变化。
4. 不重复派生：同一来源在被拒绝或转派后，不继续无限生成同一派生需求。
5. 事实可信：待复核事实不能进入普通价值结算。
6. 父链重判：子需求或叶任务处理后，父需求目标会被重新读取和判断。
7. 价值结算：普通价值结算必须要求 actual 满足目标，且不允许 I64_MAX 作为未知或兜底成功进入真实服务结算。
```

### 4.4 通过条件

只有 4.3 全部具备真实运行证据和项目结构承载证据，才允许写：

```text
需求生成与治理闭环已完成。
```

否则只能写：

```text
需求生成与治理闭环代码切片已闭合，但完整闭环仍待真实运行验收。
```

## 5. 第二组：拒绝回执治理闭环确认

### 5.1 要确认的声明

```text
拒绝回执治理闭环已实现。
```

### 5.2 必验闭环类型

按 020006，逐项验收：

```text
内部治理闭环
来源任务内部闭环
外设材料闭环
学习闭环
观察验证闭环
开发诊断闭环
合并冷却闭环
```

### 5.3 必验终态

拒绝回执处理结束前必须进入合法终态之一：

```text
已补槽重提
已合并关闭
已转观察验证
已转学习
已转来源任务内部处理
已转外设材料闭环
已冷却关闭
已进入开发诊断项
已升级规范缺口
```

### 5.4 必过证据

```text
1. 每类拒绝原因都有拒绝阶段、闭环类型、处理方案、可重试规则、来源任务影响、关闭标准和升级条件。
2. 入树拒绝生成结构化回执，不是只写日志或弹错。
3. 回执账本只记录状态、关联对象和处理证据；分类、转派和关闭由治理处理器执行。
4. 处理状态由枚举、I64 关联对象、版本号或项目结构字段表达。
5. 来源任务能读取入树成功或拒绝回执，并停止原路径重复污染。
6. 无法进入合法终态时，生成治理失败诊断；实现路径违反规范时升级为开发诊断项。
```

### 5.5 通过条件

只有七类闭环类型和九类终态均有结构化承接证据，且至少关键分支有真实运行样本，才允许写：

```text
拒绝回执治理闭环已实现。
```

若某些分支没有自然样本，只能写：

```text
拒绝回执治理主干已接入，部分闭环类型待自然样本复核。
```

## 6. 第三组：开发诊断闭环确认

### 6.1 要确认的声明

```text
开发诊断闭环已实现。
```

### 6.2 必验链路

必须证明：

```text
代码缺陷型拒绝
-> 结构化开发诊断项
-> 路径隔离
-> 弹窗 / 报错 / 日志记录
-> 来源任务收到实现缺陷阻断回执
-> 同路径停止重复筹办或重复派生
-> 开发者修复代码
-> 编译通过
-> 对应回归通过
-> 诊断项关闭
-> 来源路径恢复或替换
```

### 6.3 必过证据

```text
1. 代码缺陷不进入普通需求树。
2. 代码缺陷不转成学习需求或观察验证缺口来掩盖实现错误。
3. 开发诊断项记录来源回执、来源任务、来源需求、来源方法、失败阶段、失败原因和版本信息。
4. 机器状态推进读取枚举、I64 关联对象、版本号和隔离标志；文本只用于开发者可读证据。
5. 运行期只能确认发现、隔离、保留证据、通知和等待修复。
6. 最终关闭必须有代码修正、编译通过、对应回归通过、诊断项状态已关闭、来源路径恢复或替换。
```

### 6.4 通过条件

只有完整出现“运行期诊断建立 + 开发期修复关闭”证据，才允许写：

```text
开发诊断闭环已实现。
```

如果只有诊断项建立和路径隔离，必须写：

```text
开发诊断运行期处理已接入，开发期关闭链待真实缺陷修复样本验证。
```

## 7. 第四组：自我苏醒 / 初步成熟阶段确认

### 7.1 先后关系

必须分开确认：

```text
内部循环建立
-> 自我苏醒
-> 因果补完期
-> 学习需求形成期
-> 外界探索需求形成期
-> 初步成熟
```

不能用需求生成与治理闭环通过，直接推导自我苏醒或初步成熟完成。

### 7.2 自我苏醒确认前提

必须先确认 006001 的内部动作闭环：

```text
自我觉醒根闭环
+ 自我定义域
+ 世界树抽象根特征定义
+ 自我根特征实例当前值
-> 根特征自检
-> 安全 / 服务缺口压力
-> 根需求
-> 当前主需求
-> 任务信息节点
-> 任务虚拟存在
-> 方法 / 本能动作
-> 执行结果
-> 状态回写
-> 需求结算
-> 下一轮状态判断
```

同时证明：

```text
连续多轮内部循环可运行；
每轮结果影响下一轮判断；
无外部输入时能自主推进或进入待机；
无重复任务风暴；
无无限派生需求；
无空指针主链。
```

### 7.3 自我苏醒通过条件

按 006001001，必须证明自我能稳定治理自己：

```text
自我状态可被读取；
当前目标可被确认；
上一轮结果可被记录；
下一轮行动可由自身状态推出；
异常时能进入自检报告处置、休眠期修复评估或安全保护；
当前主需求、当前主任务、当前主方法状态均由结构字段或枚举表达。
```

全部满足后，才允许写：

```text
自我苏醒完成。
```

否则只能写：

```text
内部循环建设中。
自我苏醒建设中。
```

### 7.4 初步成熟通过条件

初步成熟必须建立在自我苏醒已通过之后。必须证明：

```text
自我能从内部需求出发识别因果缺口；
因果缺口能生成学习需求；
内部学习不足时能生成外界探索需求；
探索目标有安全门控；
探索结果能回写为记忆、因果或后续方法；
外界探索不是凭空动作，而是有明确“为什么需要外界信息”的结构化来源。
```

全部满足后，才允许写：

```text
自我初步成熟完成。
```

否则只能写：

```text
因果补完候选阶段。
学习需求形成期。
外界探索需求形成期。
```

## 8. 执行切片

### A0：确认范围和断点

```text
1. 写入本计划对应断点清单。
2. 记录当前 git 状态和已知无关脏改。
3. 收集 C1-C7 断点清单、计划停止点和现有日志入口。
4. 建立四项能力验收矩阵。
```

验收：形成 `实施记录/YYYYMMDD_四项能力确认验收_Codex断点清单.md`。

### A1：静态结构审计

```text
1. 审计拒绝原因、闭环类型、处理状态、终态枚举。
2. 审计结构化拒绝回执、拒绝回执账本、治理处理器、转派项和开发诊断项。
3. 审计来源任务读取入树成功 / 拒绝回执的路径。
4. 审计结果事实可信、父链重判和价值结算硬闸门。
5. 审计文本替代风险。
```

验收：每个声明都有六类证据表；缺证据项不得补写成通过。

### A2：需求生成与拒绝治理真实运行验证

```text
1. 先写预测。
2. 使用现有真实 exe 运行路径触发需求生成、成功入树、拒绝回执和治理处理。
3. 从日志、状态快照、动作动态和错误日志提取关键证据。
4. 核对来源任务是否收到结构化结果并停止重复派生。
```

验收：形成需求生成与拒绝治理真实运行日志摘录；没有自然样本的分支标记待复核。

### A3：开发诊断真实闭环验证

```text
1. 只使用真实运行中自然出现或已有可复现的代码缺陷型拒绝。
2. 验证诊断项建立、路径隔离、来源任务阻断回执和报错日志。
3. 若缺陷需要修复，另开代码修复切片；修复后构建和回归，再关闭诊断项。
```

验收：没有真实缺陷样本时，不得伪造；状态只能为待自然缺陷样本复核。

### A4：内部循环和自我苏醒多轮验证

```text
1. 先写多轮运行预测。
2. 使用真实运行路径验证状态 -> 需求 -> 任务 -> 方法 -> 结果 -> 状态回写 -> 结算 -> 下一轮判断。
3. 检查无任务风暴、无无限派生、无空指针主链。
4. 检查无外部输入时自主推进或待机。
```

验收：只要内部动作闭环未通过，就停止自我苏醒确认，不进入初步成熟确认。

### A5：初步成熟阶段验证

```text
1. 仅在自我苏醒确认通过后执行。
2. 验证因果缺口识别、学习需求生成、内部学习不足到外界探索需求生成。
3. 验证探索目标安全门控和探索结果回写。
```

验收：未形成外界探索目标来源和回写证据时，不得宣称初步成熟完成。

### A6：汇总结论和索引更新

```text
1. 生成四项能力确认验收报告。
2. 对每项声明给出：允许宣称 / 不允许宣称 / 待自然样本复核。
3. 若存在实现缺口，登记后续代码修订计划，不在本计划内混入修复。
4. 只在用户明确要求执行或切入时，更新计划索引当前主动队列。
```

```text

拒绝回执治理闭环已实现。
开发诊断闭环已实现。
自我苏醒完成。

```

本计划执行后，如果证据不足，仍不得宣称上述结论。
