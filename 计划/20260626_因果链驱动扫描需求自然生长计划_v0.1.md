## 1. 本计划只解决什么

本计划只解决一条链：

```text
当前需求目标
-> 因果类读取世界树因果信息
-> 生成可解释因果路径 / 条件缺口 / 证据缺口
-> 任务筹办形成派生需求草案
-> 自我线程和需求类裁决入树
-> 需求树自然生长到扫描事实 / 动态取得需求
```

目标扫描链收束为：

```text
当前观察范围可观测单位存在对应事实
-> 扫描可启动状态
-> 当前观察范围稳定对应存在扫描事实 / 动态取得状态
-> 自我_扫描当前场景 / 6146 承接
-> 首次扫描建立当前状态基准
-> 后续扫描在可比历史存在时生成状态变化或结构化缺口
```

## 2. 本计划不解决什么

```text
1. 不恢复旧因果边类型、旧目标投影维度、旧状态转换因果边查询逻辑。
2. 不新增因果主信息摘要字段、显示字段或平行因果链结构。
3. 不让因果类直接创建正式需求、任务、需求满足或安全 / 服务账务值。
4. 不把扫描写成 当前场景特征值明确状态 的完成子需求。
5. 不用模拟测试、夹具测试、伪造外设材料、伪造动作动态或旧式 --*-check 验收。
6. 不在任务筹办器内按扫描、观察、外设等领域词硬编码固定派生链。
```

### 3.2 主要缺口

```text
缺口 A：因果类缺少面向“需求临时因果视图”的组合功能函数。
    当前因果类只提供低层查询；临时视图组合、角色划分、缺口归类仍在任务筹办本地完成。
    这不必然违规，但后续若涉及因果信息解释，应把主果命中、条件目标、动作来源、证据状态
    的组合解释收口为因果类功能函数，再由任务筹办翻译成派生需求草案。

缺口 B：扫描分支的因果信息不完整。
    data/initial_causal_templates.tsv 目前只有 D455观察确认路径 -> 当前场景特征值明确 / 可观测单位取得
    以及 D455观察确认路径内部材料与对应事实闭合。
    未看到 扫描可启动状态 -> 当前观察范围稳定对应存在扫描事实 / 动态取得状态 的因果模板。

缺口 C：初始因果模板种子文件当前不能直接当作有效入账证据。
    2026-06-17 因果三分口径修正记录显示旧初始因果种子读取、解析、应用和跳过路径已删除。
    因此只修改 data/initial_causal_templates.tsv 不能证明因果链会生效，必须先确认当前正式因果模板来源。

缺口 D：扫描需求应由“结构化需求目标”生成，而不是由外设等待项或目标特征名硬编码生成。
    旧计划已要求目标特征到外设观察模式的固定映射迁移为方法条件、方法结果能力、来源因果或需求侧条件。

缺口 E：首次扫描语义需要在因果链中显式区分。
    首次扫描只能建立当前特征值和当前状态基准；后续有可比历史时才生成状态变化。
```

### P1：因果类需求目标解释功能函数缺口补齐

目标：

```text
在不新增因果主信息字段、不恢复旧结构体的前提下，补齐因果类组合查询能力。
因果类只输出因果解释材料、条件目标状态、动作来源、证据状态和缺失证据；
任务筹办仍负责把这些材料翻译为派生需求消息草案。
```

候选函数方向：

```text
因果类::查询需求目标因果解释材料(...)
    输入：目标比较、是否包含未验证路径、最大层级等。
    输出：同向命中因果、反向命中因果、条件目标状态、方法来源状态、证据状态、缺失证据。

要求：
    不返回自然语言摘要作为机器结果。
    不创建正式需求。
    不写任务状态。
    不直接写需求满足。
```

### P2：扫描需求因果模板缺口补齐

目标：

```text
让“扫描可启动状态”之后能够自然生长到“当前观察范围稳定对应存在扫描事实 / 动态取得状态”。
```

需要表达的因果关系：

```text
当前观察范围可观测单位存在稳定对应事实取得状态
稳定对应存在数量明确状态
扫描可启动状态
    -> 当前观察范围稳定对应存在扫描事实 / 动态取得状态

当前观察范围稳定对应存在扫描事实 / 动态取得状态
    -> 首次扫描当前状态基准建立状态
    -> 外设当前数据集取得状态
    -> 自我内部场景基准读取状态
    -> 稳定对应关系比较状态
    -> 观察存在当前状态事实提交状态
    -> 观察存在特征值变化事实提交状态
    -> 扫描比较需求来源记录状态
```

约束：

```text
1. 若这是冷启动被动因果，必须使用当前正式的被动触发初始因果模板入口或正式替代入口。
2. 若只能由真实扫描运行后沉淀，则先记录为后天证据增强缺口，不伪造初始因果。
3. 首次扫描只生成基准建立相关目标，不生成变化动态目标。
```

### P3：任务筹办调用边界收口

目标：

```text
任务筹办不再本地拆读因果主信息，不新增领域词硬编码扫描链。
它只调用因果类 / 世界树因果包装函数取得因果解释材料，再生成结构化派生需求消息。
```

检查点：

```text
1. 任务模块.筹办.ixx 是否仍直接解释因果主信息字段。
2. 是否存在按“扫描 / 观察 / 外设”等词硬编码固定派生链。
3. 派生消息是否保留来源因果、父需求、目标主体、目标特征、当前状态、目标状态。
4. 入树拒绝是否有结构化回执，不重复派生同一缺口。
```

### P4：真实运行验证

验证原则：

```text
先写预测，再真实运行，再用日志、状态快照、动作动态和错误日志核对。
不得新增或依赖模拟测试、夹具测试、伪造样本、伪造入口或旧式 --*-check 命令。
```

预测日志锚点：

```text
因果路径筹办入口准备
因果路径筹办查询壳统计
因果条件缺口目标化统计
因果路径筹办派生消息草案统计
因果路径筹办派生需求消息进入筹办结果
派生需求入树回执
扫描可启动状态
当前状态基准
扫描比较需求来源
```

## 6. 验收标准

```text
1. 能说明当前因果信息的正式来源，历史 TSV 或旧种子路径不再被误当运行依据。
2. 因果信息解释、主果命中、条件目标枚举、动作来源和证据状态均通过因果类功能函数完成。
3. 需求树中扫描需求来源是结构化因果解释 / 派生需求消息，不是目标特征名硬编码。
4. 扫描可启动之后能形成扫描事实 / 动态取得需求候选，且由提交入口裁决入树。
5. 首次扫描只建立基准；后续扫描有可比历史时才生成变化动态。
6. Debug x64 构建通过；真实运行日志能匹配预测锚点。
7. 不宣称自我苏醒完成、初步成熟完成或全扫描业务闭环完成。
```
