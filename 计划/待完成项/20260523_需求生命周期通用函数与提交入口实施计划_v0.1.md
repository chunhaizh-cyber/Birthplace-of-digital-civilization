## 2. 定案

前一版“通用需求生命周期本能方法”的叫法取消。

更准确的分工是：

```text
筹办 = 判断和选择。
执行 = 做对象作用并验证结果。
提交 = 正式改账。
动态 = 留证据。
```

也就是：

```text
需求生命周期判断
-> 落入筹办模块 / 需求调度代码。

任务执行后的结果验证
-> 落入执行模块 / 结果回执处理代码。

正式改写需求树、任务状态、满足状态、价值账
-> 保留提交入口，生成正式动作动态。

观察交互环境、识别服务对象、检查资源、检查风险等
-> 才是任务真正可选择的对象作用方法。
```

一句话：

```text
读定义、定位、读状态、比对、查缺口、查方法是算法步骤；
生成子需求、登记任务意图、创建任务、提交状态、回写满足、价值结算是提交入口；
服务 / 安全观察检查等才是用于满足二层需求的对象作用方法。
```

## 3. 主线目标

把自我安全 / 自我服务二层需求链整理成任意需求可复用的生命周期函数：

```text
任意需求
-> 筹办模块普通函数判断是否已满足、缺什么、能否任务化、用什么对象作用方法
-> 执行模块调用对象作用方法并处理输出结果场景
-> 提交入口正式改写需求树、任务状态、满足状态和价值账
-> 动作动态 / 过程记录 / 日志证据共同支撑因果账本和价值投影
```

通用需求第一版仍围绕四个槽位：

```text
需求主体：谁需要。
被需求存在：目标特征挂在哪个存在上。
目标特征：要改变或确认哪个特征。
目标状态：该特征要达到什么状态。
```

自我安全和自我服务只是两个根需求实例：

```text
需求主体 = 自我
被需求存在 = 自我
目标特征 = 自我_安全值 / 自我_服务值
目标状态 = 抽象特征树中的目标状态
```

服务对象、交互者、权限者、服务结果验证、风险状态等不写死进通用骨架；它们由服务 / 安全适配器和抽象特征必要条件集提供。

## 4. 当前必须纠偏的口径

```text
1. 任务筹办 / 任务执行不是本能方法。
   它们是任务管理生命周期普通函数，只形成过程回执。

2. 同步筹办回执 / 同步执行回执按 2026-05-22 修订退回普通同步函数。
   它们不进入方法树、候选集、学习目标、练习目标或动作组合反推候选。

3. 读取、比对、检查、查找等只读判断不生成正式方法动作动态。
   它们可以生成筹办过程记录、诊断日志、缺口报告和候选方法报告。

4. 正式改写账本不能只生成被动动态。
   需求树、任务状态、需求满足、价值账必须走提交入口。

5. 任务状态变化唯一正式动作来源仍是 提交任务状态变化。

6. 需求满足唯一正式动作来源仍是 回写需求满足。

7. 需求树生长必须走 需求类::执行更新指令，不绕过统一入口裸接子节点。

8. 通用写入逻辑、状态节点创建器、动作动态创建器、改变特征值 等底层工具不得成为任务当前方法。

9. 新增结构优先做运行期上下文、只读投影或诊断结果，不新增业务语义主信息权威字段。
```

若后续确实要恢复“同步回执提交方法”的动作动态语义，必须先修订 003003 / 030003 的 2026-05-22 口径。

## 5. 四层结构

### 5.1 筹办模块普通函数

这些函数不进方法树、不进候选方法集、不被任务选择。

第一版函数清单：

```text
筹办_构造需求上下文
筹办_读取目标特征定义
筹办_定位被需求存在
筹办_读取当前状态
筹办_判定需求满足状态
筹办_生成必要条件缺口报告
筹办_按因果反推必要状态
筹办_检索候选对象作用方法
筹办_判定能否任务化
```

它们输出：

```text
需求上下文
目标特征定义视图
当前状态视图
满足判断
必要条件缺口报告
因果反推缺口报告
候选对象作用方法报告
任务化建议
```

它们不得输出：

```text
正式方法动作动态
正式需求满足
正式任务状态变化
正式安全 / 服务价值入账
```

### 5.2 执行模块普通函数

这些函数也不进方法树、不被任务选择。它们处理对象作用方法执行后的结果回执。

第一版函数清单：

```text
执行_提取结果状态变化
执行_验证结果满足
执行_构造归因证据
执行_生成结果缺口报告
```

它们输出：

```text
结果状态视图
结果是否满足来源需求
完成度
归因证据候选
结果证据不足 / 不可验证 / 未满足等缺口报告
```

这些输出仍只是执行回执处理事实，不直接关闭需求、不直接结算价值。

### 5.3 提交入口

这些入口负责正式改写系统账本。可以不是任务可选方法，但必须是明确提交入口，并在正式改写时生成动作动态。

第一版提交入口：

```text
提交_生成缺口子需求
提交_登记任务发起意图
提交_承接需求创建任务
提交_任务状态变化
提交_需求满足状态
提交_叶子任务价值结算
提交_方法状态变化
提交_方法可执行入口
提交_条件结果对
```

现有兼容名称：

```text
需求类::执行更新指令
自我_提交任务状态变化
自我_回写需求满足
自我_结算叶子任务价值
自我_提交方法状态变化
自我_提交方法可执行入口
自我_建立条件结果对
```

提交入口生成的正式动作动态才能证明：

```text
需求树已生长
任务状态已改变
需求满足已登记
价值账已入账
方法状态 / 入口 / 条件结果对已提交
```

## 6. 建议接口

第一版只新增运行期上下文，不作为持久主信息权威字段。

```cpp
struct 结构_需求生命周期上下文
{
    需求节点类* 来源需求 = nullptr;

    基础信息节点类* 治理主体 = nullptr;   // 通常是自我
    基础信息节点类* 需求主体 = nullptr;
    基础信息节点类* 被需求存在 = nullptr;

    词性节点类* 目标特征 = nullptr;
    状态节点类* 当前状态 = nullptr;
    状态节点类* 目标状态 = nullptr;

    基础信息节点类* 当前上下文 = nullptr;
    基础信息节点类* 权限上下文 = nullptr;

    场景节点类* 输入场景 = nullptr;
    场景节点类* 输出结果场景 = nullptr;

    std::string 来源定义键;
    std::string 来源因果键;
};

struct 结构_筹办生命周期判断结果
{
    bool 可判断 = false;
    bool 需求已满足 = false;
    bool 需要生成子需求 = false;
    bool 可以任务化 = false;
    bool 权限阻断 = false;
    bool 安全阻断 = false;

    std::vector<结构_需求缺口> 缺口集;
    std::vector<方法节点类*> 候选对象作用方法集;

    std::string 诊断摘要; // 仅供程序调试 / 日志展示，绝不能作为逻辑语义、业务判断、去重、结算或因果依据。
    std::string 等待原因; // 仅供程序调试 / 日志展示，绝不能作为逻辑语义、业务判断、去重、结算或因果依据。
};

struct 结构_执行结果验证视图
{
    bool 可验证 = false;
    bool 满足来源需求 = false;
    I64 完成度 = 0;

    状态节点类* 执行前状态 = nullptr;
    状态节点类* 执行后状态 = nullptr;
    场景节点类* 输出结果场景 = nullptr;

    std::string 证据摘要;
    std::string 缺口原因;
};
```

`来源因果键` 使用规则：

```text
1. 直接读取目标定义得到的缺口，填写 来源定义键。
2. 因果反推得到的缺口，必须填写 来源因果键。
3. 来源因果键应指向命中的现有因果信息节点 / 抽象因果模板 / 来源为“遗传”的因果信息。
4. 缺口报告还必须携带反推路径摘要、父目标特征、中间必要状态和当前缺失证据。
5. 提交_生成缺口子需求 入树时，应把 来源因果键 写入派生归因或可追溯来源字段。
6. 任务化、执行回执和需求满足回写不得丢失该来源因果键；后续日志应能回答“为什么需要这个子需求”。
```

落地要求：

```text
1. 结构放在筹办 / 执行相关模块或局部命名空间，先不写入主信息类。
2. 若需要持久引用，优先使用已有特征、状态、场景、动态引用链。
3. 只读读取和显式确保必须分开命名。
4. 诊断和回归检查不得通过只读路径隐式创建结构。
5. 过程记录和诊断日志不得伪装成正式方法动作动态。
6. `诊断摘要`、`等待原因` 等字符串字段只能服务程序调试、日志展示和人工排错；不得作为逻辑语义、业务分支、需求去重、状态提交、价值结算或因果归因依据。
```

## 7. 修正后的主链

```text
需求进入调度
-> 筹办_构造需求上下文
-> 筹办_读取目标特征定义
-> 筹办_定位被需求存在
-> 筹办_读取当前状态
-> 筹办_判定需求满足状态

若已满足：
    -> 提交_需求满足状态

若未满足且有必要条件缺口：
    -> 提交_生成缺口子需求

若未满足且无直接必要条件缺口：
    -> 筹办_按因果反推必要状态

若因果反推发现中间必要状态缺失：
    -> 输出缺口报告 / 子需求建议
    -> 提交_生成缺口子需求

若因果反推发现因果路径绑定对象作用方法：
    -> 输出候选对象作用方法报告
    -> 筹办_检索候选对象作用方法

若未满足、无直接缺口且无因果反推缺口：
    -> 筹办_检索候选对象作用方法
    -> 筹办_判定能否任务化
    -> 提交_登记任务发起意图
    -> 任务管理线程通过 提交_承接需求创建任务 创建任务

任务执行：
    -> 执行模块调用对象作用方法
    -> 对象作用方法生成输出结果场景 / 运行存在 / 被作用对象事实变化

任务完成后：
    -> 执行_提取结果状态变化
    -> 执行_验证结果满足
    -> 执行_构造归因证据
    -> 提交_需求满足状态
    -> 因果 / 价值模块投影服务或安全价值候选
    -> 满足闸门后 提交_叶子任务价值结算
```

## 8. 实施阶段

### P0 命名与边界收口

目标：

```text
把“通用需求生命周期本能方法”改为“筹办 / 执行普通函数 + 提交入口 + 对象作用方法”。
```

动作：

```text
1. 在计划执行前复核 003003 / 030003 的 2026-05-22 修订。
2. 将读定义、定位、读状态、比对、查缺口、查候选统一命名为筹办普通函数。
3. 将提取结果、验证满足、构造归因证据统一命名为执行普通函数。
4. 将生成子需求、登记任务意图、创建任务、提交任务状态、回写需求满足、价值结算统一命名为提交入口。
5. 明确对象作用方法才允许进入方法树和候选方法集。
6. 明确同步回执普通函数不注册进默认本能方法表。
```

验收预测：

```text
本能方法表中不出现 任务筹办、任务执行、同步筹办回执、同步执行回执。
读定义 / 比对 / 查缺口 / 查候选 不作为任务当前方法。
计划和代码注释不再把生命周期算法步骤称为可选本能方法。
```

### P1 筹办上下文与只读视图

目标：

```text
从任意需求节点构造可读的需求生命周期上下文。
```

实现要点：

```text
1. 从 需求主信息类 读取需求主体、被需求存在、当前状态、目标状态、满足关系和目标特征类型缓存。
2. 若目标特征类型缓存缺失，按状态节点主信息只读解析。
3. 被需求存在缺失时只返回缺口，不隐式创建目标宿主。
4. 当前状态缺失时只返回 当前状态未知，不用目标状态反填当前状态。
```

涉及文件：

```text
需求类.h
需求类.cpp
需求主信息类.h
自我线程模块.impl.cpp
任务模块.筹办.ixx
```

验收预测：

```text
完整需求可生成上下文摘要。
缺被需求存在 / 目标特征 / 当前状态时分别输出明确缺口。
无新增业务语义主信息权威字段。
```

### P2 筹办生命周期判断函数

目标：

```text
把读定义、定位对象、读当前状态、比对目标、检查必要条件、按因果反推必要状态、查候选方法落入筹办模块普通函数。
```

实现要点：

```text
1. 筹办_读取目标特征定义：
       从世界树抽象特征树读取目标特征定义、比较策略、必要条件集和缺口映射。

2. 筹办_定位被需求存在：
       验证需求已给出的被需求存在；缺失时从当前上下文解析候选并记录证据。

3. 筹办_读取当前状态：
       只读目标特征实例；必要时从当前场景、任务回执或输出结果场景读取证据。

4. 筹办_判定需求满足状态：
       复用特征比较 / 状态比较能力，只输出满足、部分满足、未满足、不可判断。

5. 筹办_生成必要条件缺口报告：
       遍历目标特征定义中的必要条件，只为未知 / 未满足 / 阻断条件产出缺口项。

6. 筹办_按因果反推必要状态：
       从当前需求目标特征 / 目标状态出发，查找主果匹配的抽象因果或来源为“遗传”的现有因果信息。
       反推因侧状态、条件侧状态和可产生中间状态的对象作用方法。
       对缺失的前置状态只输出缺口报告 / 子需求建议。
       对可由对象作用方法产生的中间状态只输出候选对象作用方法报告。
       不直接生成需求节点。
       不直接创建任务。
       不直接回写需求满足。
       不直接结算安全值 / 服务值。
       不生成正式方法动作动态。

       因果反推产生的缺口必须携带：
           来源因果键；
           命中因果模板 / 因果信息节点；
           因果来源类型，至少区分 遗传 / 推断生成 / 后天验证；
           反推路径摘要；
           父目标特征；
           中间必要状态；
           中间状态当前满足状态；
           当前缺失证据。

       提交_生成缺口子需求 入树时，应把 来源因果键 写入派生归因或可追溯来源字段。

7. 筹办_检索候选对象作用方法：
       查找能作用于被需求存在目标特征的对象作用方法；排除生命周期函数、被动同步函数和底层写入工具。
```

涉及文件：

```text
特征类.cpp
世界树类.cpp
需求类.cpp
任务模块.筹办.ixx
自我线程模块.impl.cpp
自检线程模块.impl.cpp
```

验收预测：

归因后置规则：

```text
服务结果可归因于自我动作状态 不作为服务启动前置对象作用需求。
它只在服务动作完成、输出结果场景存在、服务对象外在特征状态变化存在、服务对象反馈信息存在、来源动作动态存在后进入执行后归因 / 结算链。
若当前树中已有该需求节点，第一版应标记为后置结算条件或非阻塞需求，避免阻塞服务对象识别、服务目标解析和服务任务执行。
```

## 9. 注册与不注册策略

允许注册为任务可选方法：

```text
服务 / 安全对象作用方法第一版清单
后续学习沉淀出的解释、整理、修改、规划等对象作用方法
```

允许作为提交入口并生成正式动作动态：

```text
提交任务状态变化
回写需求满足
结算叶子任务价值
提交方法状态变化
提交方法可执行入口
建立条件结果对
承接需求创建任务
挂起任务等待子需求
唤醒任务重筹办
取消任务
任务超时处理
```

明确不注册为任务可选方法：

```text
任务筹办
任务执行
同步筹办回执到任务
同步执行回执到任务
筹办_构造需求上下文
筹办_读取目标特征定义
筹办_定位被需求存在
筹办_读取当前状态
筹办_判定需求满足状态
筹办_生成必要条件缺口报告
筹办_检索候选对象作用方法
执行_提取结果状态变化
执行_验证结果满足
执行_构造归因证据
改变特征值
状态节点创建器
动作动态创建器
控制面板展示函数
诊断汇总函数
```

迁移策略：

```text
1. 先保留旧枚举 ID 和旧动作名的兼容入口，避免破坏既有日志和方法头。
2. 生命周期算法步骤只做普通函数命名，不新增方法头。
3. 旧自我专用方法逐步退化为服务 / 安全 / 自我根特征适配器。
4. 每新增一个对象作用方法，必须补方法头、条件场景、结果场景、动作句柄和日志证据。
5. 每新增一个提交入口，必须说明改写哪类账本、生成哪类正式动作动态、是否允许被任务主动选择。
```

## 10. 动态与证据边界

只读判断可以产生：

```text
筹办过程记录
执行过程记录
诊断日志
缺口报告
候选方法报告
归因证据候选
```

这些记录用于：

```text
调试
复盘
解释为什么生成子需求或任务
构造因果候选
```

这些记录不得直接证明：

```text
需求已满足
服务值应该增加
安全值应该增加
任务状态已经改变
```

正式证明必须来自：

```text
对象作用方法动态
提交动作动态
结果状态变化
需求满足回写
因果归因
价值结算闸门
```

## 11. 验证计划

验证只用真实运行、日志、状态快照、动作动态和错误日志，不新增 `--*-check` 回归入口，不使用模拟样本、夹具样本或伪造动作动态。

构建命令：

```powershell
msbuild .\鱼巢.vcxproj /p:Configuration=Debug /p:Platform=x64 /p:LinkIncremental=false /m
```

每个阶段验证前先写预测单：

```text
计划：
真实触发路径：
预测结果：
必查日志：
禁止出现：
缺自然样本判定：
实际日志证据：
结论：
下一步：
```

最小必查项：

```text
1. 默认本能方法注册表不包含任务筹办、任务执行、同步筹办回执、同步执行回执。
2. 筹办_读取 / 筹办_比对 / 筹办_查缺口 / 筹办_查候选 不出现在任务候选方法集。
3. 执行_提取结果 / 执行_验证满足 / 执行_构造归因证据 不出现在任务候选方法集。
4. 需求缺口入树必须出现完整父需求、目标宿主、目标特征、当前状态、目标状态、满足关系和派生归因。
5. 候选对象作用方法选择必须先有候选集填充日志。
6. 任务状态动作动态来源为 提交任务状态变化。
7. 需求满足动作动态来源为 回写需求满足。
8. 世界事实变化不以线程、改变特征值或外部变化伪装成自我方法动作动态。
9. 服务值结算缺服务对象 / 目标 / 实际改善 / 归因时被拒绝或仅记录候选。
10. I64_MAX 若进入安全 / 服务分量值，必须证明其为合法满刻度，不得作为未知 / 默认成功 / 异常兜底。
11. 筹办按因果反推必要状态时，必须记录：
    来源需求ID；
    目标特征 / 目标状态；
    命中的因果模板ID / 因果信息键；
    因果来源类型，尤其是遗传 / 推断生成 / 后天验证；
    来源因果键；
    反推出的中间必要状态；
    中间状态当前满足状态；
    产出的缺口报告；
    是否调用 提交_生成缺口子需求。
12. 因果反推函数不得直接：
    生成需求节点；
    创建任务；
    写需求满足；
    写价值账；
    生成正式方法动作动态。
13. 遗传因果只允许导出观察 / 验证 / 明确类中间需求；
    不允许直接导出安全值增加、服务值增加或风险已处置。
```

## 12. 完成判据

```text
1. 任意完整原子需求都能构造需求生命周期上下文。
2. 目标特征定义、被需求存在、当前状态、目标状态和满足关系能被筹办模块统一读取和比对。
3. 必要条件缺口和因果反推必要状态缺口能按缺口映射生成报告，并由提交入口生成二层子需求。
4. 自我安全 / 自我服务根需求只作为通用需求实例和领域适配器存在。
5. 服务事实类二层需求能通过对象作用方法明确交互者、权限者、服务对象、服务目标，并在需要时尝试获取服务对象反馈信息。
6. 安全事实类二层需求能通过对象作用方法明确运行状态、资源状态、权限边界、外设观察验证、已确认观察存在、当前场景存在集合、当前场景风险安全值和风险状态。
7. 任务化只发生在需求真实未满足、权限允许、安全未阻断之后。
8. 任务完成、结果验证、需求满足回写和价值结算分账清楚。
9. 筹办 / 执行算法函数不进入方法树、候选集、学习目标或练习目标。
10. 正式账本变化全部绑定明确提交入口或对象作用方法，不出现线程裸写或被动整理动作作为主链动作来源。
11. 不提前宣称自我苏醒完成或初步成熟完成。
```
