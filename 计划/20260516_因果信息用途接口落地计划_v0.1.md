## 1. 目标

让因果类逐步具备七类用途：

```text
解释状态变化
预测动作后果
反推可用动作
生成需求候选
执行前因果审查
执行后因果验收
更新因果模板稳定度
```

边界：

```text
因果类不直接写任务状态。
因果类不直接写正式需求节点。
因果类不直接写安全值 / 服务值。
因果类不直接创建任务。
```

接口实现边界：

```text
因果解释、预测、反推、缺口诊断、候选排序、风险评分和验收判断，
若只返回结果结构，不持久改写方法、任务、需求或世界树特征状态，
均作为普通逻辑接口实现。

因果接口输出被正式入树、写入方法入口、写入条件结果对、写入方法状态、
写入任务回执或参与安全 / 服务结算时，
必须转交对应领域的提交方法 / 本能方法处理。
```

## 1.1 因果学习六小闭环接口

因果学习不新增“学习大函数”。第一版按六个小接口接入现有任务、方法和动态链路：

```text
1. 按动态补完因果：
   动态 / 状态变化 -> 状态变化线索 / 完整因果模板 / 因果实例。

2. 诊断学习缺口：
   判断缺条件、缺动作、缺结果、缺参数、缺副作用、缺适用范围或缺验证证据。

3. 从因果缺口生成学习需求候选：
   把缺口转成候选信息，不直接写正式需求树。

4. 反推可达动作：
   从目标结果反推候选动作 / 方法。

5. 预测动作结果：
   执行前预测收益、风险、副作用和硬边界。

6. 验收动作结果：
   执行后比较预测结果和实际结果，形成成立 / 失败 / 副作用评价。
```

核心路线：

```text
动态 / 状态变化
-> 因果补完
-> 诊断学习缺口
-> 生成学习需求候选
-> 学习任务执行
-> 验收是否补上因果缺口
-> 更新方法 / 因果模板稳定度
```

其中：

```text
学习任务执行仍由现有任务 / 方法链路承接；
因果类只提供候选、预测、验收和证据；
正式需求入树、任务状态、方法状态和价值结算仍由对应领域方法提交。
因果类本身不因为“负责解释或预测”而成为动作来源。
```

## 1.2 因果转自我方法的判定口径

因果信息转化为自我方法前，必须先判断：

```text
自我能否制造因果模板的触发条件。
```

标准形式：

```text
条件状态 C + 动作 A -> 结果状态 R
```

只有当：

```text
1. 自我能产生或维持 C；
2. 自我能执行、诱发或请求 A；
3. 自我能观测并验收 R；
```

才能生成候选方法，并在尝试和验收通过后固化为自我方法。

最短口径：

```text
能造因，能控动，验得果，才成法。
```

状态变化线索：

```text
C -> R，动作未知
```

不能直接固化为方法，只能生成补动作或找动作的学习需求。

若动作已知但自我不能执行或诱发，则应生成：

```text
补执行能力；
请求外部动作；
寻找替代动作；
或确认动作来源。
```

好结果因果用于正向达成；坏结果或物理不安全因果用于反向阻断，不能生成制造危险条件的方法。

## 1.3 与当前可执行入口阻塞的关系

当前 `--learning-demand-condition-result-check` 受真实可执行入口缺失阻塞。

按本口径，不能把占位方法直接伪造成可执行方法。必须先证明：

```text
占位方法对应的动作 A 已确定；
该动作 A 可由当前自我通过本能方法执行或诱发；
执行后的结果 R 可观测并验收。
```

因此，“补可执行入口”不是写：

```text
方法可执行入口数量 = 1
```

而是补：

```text
具体动作来源已确定；
动作来源可执行；
提交方法可执行入口后动作句柄有效。
```

## 1.4 尝试 / 练习启动收益链

尝试学习和练习必须证明自己不是空转。启动前至少要能说明：

```text
尝试 / 练习动作
-> 产生因果证据
-> 补全或验证因果模板
-> 方法状态 / 稳定度 / 适用范围改善
-> 父任务可继续
-> 父需求有机会满足
```

接口落地时应新增或复用只读判定：

```text
判定是否可启动尝试或练习
```

该判定只返回门控结果，不写需求树、不写任务状态、不写方法状态、不生成动作动态。

返回状态至少区分：

```text
可启动尝试学习
可启动练习
不可启动_缺父目标链
不可启动_缺动作候选
不可启动_结果不可观察
不可启动_风险过高
不可启动_缺可满足条件
```

门控规则：

```text
练习需要已有完整因果模板 C + A -> R，且稳定度不足。
尝试学习需要候选因果，且至少有可尝试的条件或动作。
缺动作且无候选动作时，不启动尝试 / 练习，只生成寻找候选动作或外部信息的候选。
```

## 3. 分步计划

### P1. 因果沉淀入口改名与兼容

目标：

```text
用 按动态补完因果 替代 按动态补全两层因果 的主叙述。
```

动作：

```text
1. 保留旧接口兼容。
2. 新增 按动态补完因果 包装入口。
3. 动作未知时只生成状态变化线索。
4. 动作已知时生成完整因果模板和因果实例。
```

验收：

```text
有动作动态 -> 完整因果模板。
无动作状态变化 -> 状态变化线索。
```

### P2. 因果学习缺口诊断接口

目标：

```text
根据已有因果材料判断缺条件、缺动作、缺结果或缺验证证据。
```

动作：

```text
1. 新增 结构_因果学习诊断输入。
2. 新增 枚举_因果学习缺口类型。
3. 新增 诊断学习缺口 接口。
4. 对状态变化线索优先诊断为缺动作。
5. 对动作 + 结果但无条件诊断为缺条件。
6. 对条件 + 动作但无结果诊断为缺结果。
7. 对三者齐全但证据不足诊断为缺验证证据。
```

验收：

```text
缺口诊断不创建需求、不写任务、不改方法状态。
缺口诊断不生成动作动态。
```

### P2b. 尝试 / 练习启动门控接口

目标：

```text
判断一次尝试学习或练习是否具备从学习动作到父任务解阻的收益链。
```

动作：

```text
1. 新增 结构_学习启动判定输入。
2. 新增 枚举_学习启动判定结果。
3. 新增 判定是否可启动尝试或练习 接口。
4. 检查父任务 / 父需求来源。
5. 检查卡点是否能表达成因果缺口。
6. 检查条件是否可满足、动作是否可执行或有候选、结果是否可观察。
7. 检查风险是否触发安全硬边界。
8. 返回可启动尝试、可启动练习或不可启动原因。
```

验收：

```text
该接口只读，不直接创建学习需求、不写任务、不改方法状态、不生成动作动态。
无父目标链、无可观察结果、风险过高、缺动作且无候选动作时，必须拒绝启动。
```

### P3. 因果学习需求候选接口

目标：

```text
把因果学习缺口转换成学习需求候选信息。
```

动作：

```text
1. 新增 结构_学习需求候选。
2. 新增 结构_学习需求候选结果。
3. 新增 从因果缺口生成学习需求候选 接口。
4. 输出目标宿主、目标特征类型、当前状态、目标状态、来源因果模板或状态变化线索。
5. 不直接入树。
```

验收：

```text
候选信息字段完整；
正式入树仍由自我线程按需求树规范裁决。
若正式入树，需要走派生需求入树方法；本接口只返回候选。
```

### P4. 因果解释接口

目标：

```text
给定结果状态，反查可能原因链。
```

动作：

```text
1. 根据结果状态查找命中的完整因果模板。
2. 递归读取条件状态和上游模板。
3. 返回解释链，不生成需求。
```

验收：

```text
解释结果只读，不写需求树、不创建任务。
```

### P5. 因果预测接口

目标：

```text
给定当前条件状态和候选动作，预测结果、风险和副作用。
```

动作：

```text
1. 按动作模板 / 动作语义键查完整因果模板。
2. 匹配条件状态。
3. 返回预测结果状态和副作用状态。
```

验收：

```text
候选动作审查可读取预测结果。
```

### P6. 因果反推接口

目标：

```text
给定目标结果状态，反推出候选动作 / 方法。
```

动作：

```text
1. 按结果状态查完整因果模板。
2. 提取动作模板和条件模板。
3. 生成候选动作 / 方法列表。
```

验收：

```text
任务筹办可消费反推结果作为候选方法来源之一。
反推结果只用于本轮候选时不需要本能方法；
只有写入方法动作入口或动作序列入口时才进入提交动作。
```

### P7. 因果需求投影接口

目标：

```text
从不良状态 / 风险状态 / 未满足目标的因果解释链生成需求候选信息。
```

动作：

```text
1. 从解释链选择可干预节点。
2. 生成需求候选信息。
3. 不直接入树。
```

验收：

```text
正式入树仍由自我线程和需求域方法完成。
```

### P8. 执行前因果审查接口

目标：

```text
候选方法执行前检查收益、风险、副作用和硬边界。
```

动作：

```text
1. 调用因果预测。
2. 匹配安全 / 服务边界。
3. 返回允许执行或禁止执行结果。
```

验收：

```text
审查结果不能直接改任务状态，只能作为任务筹办 / 执行前门控依据。
```

### P9. 执行后验收与稳定度更新

目标：

```text
比较预测结果与实际输出，更新因果模板成立 / 失败 / 副作用统计。
```

动作：

```text
1. 根据动作动态、输出结果场景和来源需求目标生成因果实例评价。
2. 更新因果模板成立次数、失败次数和稳定度。
3. 输出需求满足和价值结算可引用的因果证据链。
```

验收：

```text
任务完成和需求满足判断可引用因果验收结果；
真实安全 / 服务结算仍由结算方法完成。
```

### P10. 结算因果证据接入

目标：

```text
把叶子任务结果、需求满足和安全值变化串成可解释的因果证据链。
```

核心口径：

```text
结算叶子任务价值是本能提交方法；
它不是根任务可选择的业务方法；
它不负责解决安全问题；
它只负责把“问题已解决”这个事实入安全账。
```

标准因果链：

```text
D0：叶子任务业务动作动态
    说明安全问题如何被解决。

D1：回写需求满足动作动态
    说明该结果满足了哪个安全需求。

D2：结算叶子任务价值动作动态
    读取 D0 / D1 / 输出结果场景 / 来源任务 / 来源需求，
    写入安全值变化，
    说明安全值为什么增加。
```

动作：

```text
1. 为结算输入明确来源叶子任务、来源需求、任务完成动态、需求满足动态、输出结果场景。
2. 结算前检查叶子任务已完成、来源需求已满足、结算值合法、未重复结算。
3. 结算动作动态必须引用来源业务动作动态和需求满足动态。
4. 禁止任务筹办把结算叶子任务价值选为根任务的业务当前方法。
```

验收：

```text
根任务不能通过结算方法凭空完成；
安全值增加必须能追溯到叶子任务解决问题和需求满足证据；
结算本能方法只作为治理提交链调用，不进入普通业务候选选择。
```

## 5. 停止条件

```text
1. 若实现需要因果类直接写需求树，暂停。
2. 若实现需要因果类直接写任务状态，暂停。
3. 若实现需要绕过动作动态证据直接从底层状态生成完整因果，暂停。
4. 若状态变化线索被当成完整因果模板使用，暂停。
5. 若与 001 方法动作动态硬规则冲突，暂停。
6. 若学习需求候选被因果类直接写入正式需求树，暂停。
7. 若方法运行成功被直接当成因果成立或学习完成，暂停。
```

## 6. 最终口径

```text
因果信息是自我内部循环的解释与预测层。
它不替代需求、任务、方法和结算的提交动作；
它提供为什么、会怎样、该找什么、能不能做、做完算不算数。
结算叶子任务价值是本能提交方法，不是根任务业务方法；
安全值增加必须由“叶子任务解决问题 -> 需求满足 -> 结算入账”的证据链支撑。
```
